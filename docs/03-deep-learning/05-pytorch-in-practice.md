## 1. Две идеи, на которых стоит PyTorch

Первая идея: **тензор — это не массив, а вид на кусок памяти**. Один и тот же буфер чисел может
быть представлен как матрица 4×6, как вектор из 24 элементов и как транспонированная матрица 6×4 —
без единого копирования. Отсюда и скорость, и целый класс багов, где изменение одного тензора
внезапно меняет другой.

Вторая идея: **граф вычислений строится динамически, во время выполнения**. Когда вы пишете
`z = x * y`, PyTorch не только считает произведение, но и запоминает, из чего оно получено.
Никакой отдельной фазы «компиляции графа» нет: граф — побочный продукт обычного выполнения
Python-кода. Поэтому в модели можно писать `if`, `for` и `print`, отлаживать её обычным
отладчиком — и поэтому же граф случайно утекает в память, если хранить не то, что нужно.

Всё остальное — `nn.Module`, `DataLoader`, оптимизаторы — надстройки над этими двумя идеями.
Разбираем по порядку.

## 2. Тензор: форма, тип, устройство, память

У тензора четыре характеристики, которые надо держать в голове одновременно:
**форма** (shape), **тип** (dtype), **устройство** (device) и **раскладка в памяти**
(strides + contiguity).

```python
import torch

x = torch.arange(24, dtype=torch.float32).reshape(4, 6)
print(x.shape, x.dtype, x.device)          # torch.Size([4, 6]) torch.float32 cpu
print(x.stride())                          # (6, 1): шаг по строке — 6 элементов, по столбцу — 1
print(x.is_contiguous())                   # True

y = x.t()                                  # транспонирование: НОВЫХ данных не создаётся
print(y.shape, y.stride(), y.is_contiguous())   # (6, 4) (1, 6) False
print(y.data_ptr() == x.data_ptr())        # True — общий буфер памяти

y[0, 0] = 999.0                            # запись через "вид" меняет исходный тензор
print(x[0, 0])                             # tensor(999.)
```

**Stride** — сколько элементов надо перешагнуть в буфере, чтобы сдвинуться на 1 по данной оси.
Транспонирование просто меняет местами страйды. Тензор **contiguous**, если его страйды
соответствуют обычной построчной раскладке; многие операции (в первую очередь `view`)
требуют именно этого.

Отсюда практическое правило, которое стоит выучить:

| Операция | Копирует данные? | Когда падает |
|---|---|---|
| `view(...)` | никогда | если тензор не contiguous — бросает ошибку |
| `reshape(...)` | если нужно | не падает, но может незаметно скопировать |
| `transpose`, `permute` | нет | — |
| `contiguous()` | если нужно | — |
| `clone()` | всегда | — |
| индексирование срезом `x[1:3]` | нет (вид) | — |
| индексирование маской/списком `x[[0,2]]` | всегда | — |

> ⚠️ **Типичная ошибка.** `x.transpose(1, 2).view(B, n, d)` падает с `view size is not compatible
> with input tensor's size and stride`. Причина: после `transpose` тензор перестал быть contiguous.
> Правильно — `x.transpose(1, 2).contiguous().view(...)` или просто `.reshape(...)`.
> Именно поэтому в реализациях attention вы постоянно видите `.contiguous()` перед `.view()`
> (см. [код в главе про трансформер](04-attention-and-transformer.md#10-реализация-с-нуля)).

**Про dtype.** По умолчанию `torch.float32`. Три вещи, которые надо знать: индексы всегда
`int64` (`long`), маски — `torch.bool`, а смешение типов в одной операции приводит к
приведению по правилам продвижения типов, из-за чего `float16 * float32` тихо станет `float32`
и съест память. Полная арифметика половинной точности — в
[главе про масштабирование](06-scaling-and-efficiency.md).

**Про память.** Считать её просто: `x.numel() * x.element_size()` байт. Тензор
$(32, 3, 224, 224)$ в fp32 — это $32\cdot3\cdot224^2\cdot4 \approx 19$ МБ. Держите этот
подсчёт в пальцах: он мгновенно отвечает на вопрос «почему OOM».

## 3. Broadcasting и как он молча ломает лосс

Broadcasting — правило автоматического расширения форм при поэлементных операциях. Формулируется
в две строки, но именно из-за него случается самый обидный класс багов: код работает,
ошибок нет, а модель учится не тому.

**Правило.** Формы выравниваются **справа**. Затем по каждой оси размеры должны либо совпадать,
либо один из них должен быть равен 1 — тогда он «растягивается». Если ось отсутствует у одного
из тензоров, она считается равной 1.

```
(B, n, d)  и  (d,)      -> (B, n, d)     ок: (d,) читается как (1, 1, d)
(B, n, 1)  и  (1, n, d) -> (B, n, d)     ок
(B, n)     и  (B, 1)    -> (B, n)        ок
(32,)      и  (32, 1)   -> (32, 32)      ФОРМАЛЬНО ОК — и это катастрофа
```

Последняя строка — классика:

```python
import torch
import torch.nn.functional as F

pred = torch.randn(32)         # (32,)  — модель вернула плоский вектор
target = torch.randn(32, 1)    # (32,1) — а таргет пришёл из pandas колонкой

diff = pred - target           # (32, 32)!!! посчитаны ВСЕ попарные разности
loss = (diff ** 2).mean()      # скаляр — ошибки нет, но это не MSE
print(diff.shape)              # torch.Size([32, 32])
```

Лосс посчитан, `backward()` отработает, обучение пойдёт. Только градиент будет от совершенно
другой функции: вместо среднего по 32 ошибкам вы минимизируете среднее по 1024 попарным
разностям, что тянет все предсказания к среднему таргету. Модель «учится», метрики плохие,
причину ищут неделю.

**Защита — одна строка в начале каждого лосса:**

```python
def mse(pred: torch.Tensor, target: torch.Tensor) -> torch.Tensor:
    assert pred.shape == target.shape, f"формы разошлись: {pred.shape} vs {target.shape}"
    return ((pred - target) ** 2).mean()
```

Современные версии PyTorch выдают `UserWarning` для встроенных лоссов при несовпадении форм —
но предупреждения в логах обучения тонут. Ассерт не тонет.

> 💬 **На собеседовании.** Спросят: «Что вернёт `torch.randn(3, 1) + torch.randn(1, 4)`?»
> Хороший ответ: тензор формы $(3, 4)$ — обе оси растянулись, получилась «таблица сумм».
> И сразу добавить, что именно этот механизм — главный источник тихих багов в лоссах
> и метриках, поэтому формы предсказаний и таргетов надо проверять ассертом, а не глазами.
> Провал: «ошибку размерности» — показывает, что человек не читал правила broadcasting.

## 4. Autograd: граф, backward, detach, no_grad

### Как строится граф

Каждый тензор, полученный операцией над тензором с `requires_grad=True`, помнит функцию,
которая его породила, — это поле `grad_fn`. Цепочка `grad_fn` и есть граф вычислений,
направленный ациклический, с **листьями** (leaf) — тензорами, которые никем не порождены
(параметры модели и входные данные).

```python
import torch

x = torch.tensor([2.0], requires_grad=True)   # лист: is_leaf=True, grad_fn=None
y = x ** 3                                    # grad_fn=<PowBackward0>
z = 5 * y                                     # grad_fn=<MulBackward0>

z.backward()          # dz/dx = 5 * 3x^2 = 15 * 4 = 60
print(x.grad)         # tensor([60.])

z2 = 5 * x ** 3
z2.backward()
print(x.grad)         # tensor([120.]) — НЕ 60: градиенты НАКОПИЛИСЬ
```

Последние две строки — ответ на вопрос «зачем нужен `zero_grad`». Градиенты **прибавляются**
к `.grad`, а не перезаписываются. Это не недосмотр, а сознательное решение: накопление позволяет
(а) складывать градиенты от нескольких функций потерь, (б) обучать RNN, где один и тот же
параметр участвует на всех шагах, (в) делать gradient accumulation для эмуляции большого
батча (см. [главу 06](06-scaling-and-efficiency.md)). Плата — обязанность обнулять руками.

Ещё две вещи про `backward()`:

- Вызывать можно только на **скаляре**. Для нескалярного тензора нужно передать вектор
  «весов» — `z.backward(gradient=v)`, что вычисляет $v^\top J$ (векторно-якобианово произведение).
  Именно поэтому лосс всегда сводят к скаляру через `.mean()` или `.sum()`.
- После `backward()` **граф освобождается**. Повторный вызов упадёт с
  `Trying to backward through the graph a second time`. Если это действительно нужно —
  `backward(retain_graph=True)`, но в 95 % случаев такая ошибка означает, что вы случайно
  сохранили тензор с графом между итерациями.

### Четыре разных способа «выключить градиент»

Их путают постоянно, а это четыре разные вещи с разными последствиями.

| Инструмент | Что делает | Типичное применение |
|---|---|---|
| `tensor.detach()` | возвращает тензор с теми же данными, но без связи с графом | отсоединить скрытое состояние RNN, логировать значения |
| `with torch.no_grad():` | внутри блока граф не строится вообще | валидация, инференс, ручное обновление весов |
| `with torch.inference_mode():` | то же плюс отключение версионирования тензоров — быстрее | только инференс, если результат не пойдёт в autograd |
| `param.requires_grad_(False)` | параметр не получает градиента | заморозка слоёв при дообучении |

И отдельно: `model.eval()` **не делает ничего из этого** — см. [§7](#7-train-против-eval-что-именно-меняется). Это самое частое заблуждение
во всей теме.

```python
import torch

w = torch.randn(3, requires_grad=True)
x = torch.randn(3)

# 1. detach: значение то же, градиент дальше не пойдёт
y = (w * x).sum()
y_det = y.detach()
print(y.requires_grad, y_det.requires_grad)   # True False

# 2. no_grad: граф не строится — экономия памяти и времени
with torch.no_grad():
    y2 = (w * x).sum()
print(y2.requires_grad)                        # False

# 3. ручное обновление весов ОБЯЗАНО быть под no_grad,
#    иначе PyTorch запретит in-place изменение листа, требующего градиент
y.backward()
with torch.no_grad():
    w -= 0.1 * w.grad
    w.grad.zero_()
```

### Параметры, буферы и nn.Module

`nn.Module` — это, по сути, контейнер, который умеет находить внутри себя тензоры и рекурсивно
обходить вложенные модули. Тензоров внутри модуля бывает два сорта, и путать их дорого.

**Параметр** (`nn.Parameter`) — обучаемый лист графа. Автоматически получает
`requires_grad=True`, попадает в `model.parameters()` (то есть в оптимизатор) и в `state_dict`.

**Буфер** (`register_buffer`) — тензор, который является частью состояния модели, но не обучается:
скользящие статистики BatchNorm, причинная маска, таблица частот RoPE. Попадает в `state_dict`
(то есть сохраняется и загружается) и переезжает вместе с моделью при `.to(device)`,
но в оптимизатор не попадает.

```python
import torch
import torch.nn as nn


class Head(nn.Module):
    def __init__(self, d: int, max_len: int):
        super().__init__()
        self.proj = nn.Linear(d, d)                      # параметры: веса и смещение
        self.scale = nn.Parameter(torch.ones(d))         # обучаемый вектор
        # маска — часть состояния, но обучать её нечему. persistent=False означает
        # "не сохранять в state_dict": маску всегда можно построить заново,
        # а вот несовпадение max_len при загрузке чекпоинта сломает load_state_dict
        self.register_buffer(
            "causal_mask",
            torch.ones(max_len, max_len, dtype=torch.bool).triu(1),
            persistent=False,
        )

    def forward(self, x):                                # x: (B, n, d)
        n = x.size(1)
        mask = self.causal_mask[:n, :n]                  # едет на нужное устройство сам
        return self.proj(x) * self.scale
```

Если бы `causal_mask` был обычным атрибутом (`self.causal_mask = torch.ones(...)`), он
остался бы на CPU после `model.to("cuda")` — и вы получили бы `Expected all tensors to be
on the same device` на первом же forward. Это самый частый способ узнать о существовании буферов.

> ⚠️ **Типичная ошибка, которую невозможно заметить глазами.** Сложить слои в обычный
> питоновский список:
>
> ```python
> self.layers = [nn.Linear(d, d) for _ in range(L)]        # ПЛОХО
> self.layers = nn.ModuleList(nn.Linear(d, d) for _ in range(L))   # правильно
> ```
>
> Обычный список — не модуль, поэтому PyTorch про эти слои **не знает**: они не появятся
> в `model.parameters()` (оптимизатор их не обновит), не попадут в `state_dict`
> (не сохранятся) и не переедут на GPU при `.to(device)`. Модель при этом полностью
> работоспособна: forward отработает, лосс посчитается, обучение пойдёт — просто часть сети
> навсегда останется со случайными весами. Тот же капкан со словарями (нужен `nn.ModuleDict`)
> и с последовательностями модулей (`nn.Sequential`). Защита — привычка сверять
> `sum(p.numel() for p in model.parameters())` с расчётом на бумаге: расхождение мгновенно
> вскрывает потерянные слои.

> 💬 **На собеседовании.** Спросят: «Чем `nn.Parameter` отличается от буфера и от обычного
> атрибута-тензора?»
> Хороший ответ: параметр обучается — он в `parameters()`, значит в оптимизаторе, и в `state_dict`.
> Буфер — состояние, которое сохраняется и переезжает на устройство вместе с моделью,
> но не обучается: running-статистики BatchNorm, маски, позиционные таблицы. Обычный атрибут
> не делает ни того, ни другого: он не сохранится и останется на CPU, что даст ошибку устройства
> на первом forward. Сильное продолжение — упомянуть `persistent=False` для буферов, которые
> можно восстановить вычислением, и рассказать про ловушку с обычным списком вместо `ModuleList`.
> Провал: «буфер — это что-то для оптимизации памяти».

> 💬 **На собеседовании.** Спросят: «В чём разница между `torch.no_grad()` и `model.eval()`?»
> Хороший ответ: это ортогональные вещи. `no_grad` — про **построение графа**: он выключает
> запись операций, экономит память и время, но не меняет поведение слоёв. `eval()` — про
> **режим слоёв**: он выключает Dropout и переводит BatchNorm на накопленные статистики,
> но граф продолжает строиться и память продолжает расходоваться. На валидации нужны **оба**:
> без `eval()` получите зашумлённые предсказания и, что хуже, испорченные running-статистики
> BatchNorm; без `no_grad()` — лишний расход памяти вплоть до OOM. Провал: «это одно и то же»
> или «eval отключает градиенты».

## 5. Dataset, DataLoader и num_workers

Разделение обязанностей: `Dataset` умеет отдать **один** объект по индексу, `DataLoader` умеет
собрать из объектов батч, перемешать, распараллелить чтение и подготовить память.

```python
import torch
from torch.utils.data import Dataset, DataLoader


class SequenceDataset(Dataset):
    """Map-style датасет: знает свою длину и умеет отдать элемент по индексу."""

    def __init__(self, texts: list[str], labels: list[int], tokenizer):
        # ВАЖНО: тяжёлые данные храним в numpy/torch, а не в питоновских списках —
        # почему, объясняется ниже, в пункте про num_workers и copy-on-write
        self.labels = torch.tensor(labels, dtype=torch.long)
        self.encoded = [torch.tensor(tokenizer(t), dtype=torch.long) for t in texts]

    def __len__(self) -> int:
        return len(self.labels)

    def __getitem__(self, idx: int):
        # никакой рандомизации через глобальный np.random здесь — см. §12
        return self.encoded[idx], self.labels[idx]


def collate_pad(batch, pad_id: int = 0):
    """Собираем батч из последовательностей разной длины: паддинг до максимума В БАТЧЕ,
    а не до глобального максимума — экономит вычисления в разы."""
    seqs, labels = zip(*batch)
    lengths = torch.tensor([len(s) for s in seqs])
    max_len = int(lengths.max())
    padded = torch.full((len(seqs), max_len), pad_id, dtype=torch.long)
    for i, s in enumerate(seqs):
        padded[i, : len(s)] = s
    attn_mask = torch.arange(max_len)[None, :] < lengths[:, None]   # (B, max_len), bool
    return padded, attn_mask, torch.stack(labels)


loader = DataLoader(
    dataset,
    batch_size=32,
    shuffle=True,           # ОБЯЗАТЕЛЬНО для train: иначе батчи коррелированы по порядку файла
    num_workers=8,          # процессы-читатели; 0 = читать в главном процессе
    pin_memory=True,        # закреплённая память: нужна для быстрого асинхронного копирования
    drop_last=True,         # выкинуть неполный последний батч (важно для BatchNorm)
    persistent_workers=True,  # не убивать воркеров между эпохами
    prefetch_factor=2,      # сколько батчей воркер готовит вперёд
    collate_fn=collate_pad,
)
```

### num_workers: как выбирать

`num_workers=0` — данные читаются в главном процессе, **синхронно**: пока грузится батч, GPU
простаивает. Годится только для отладки (зато трассировки исключений читаемые).

`num_workers=k` — поднимается $k$ процессов (не потоков — процессов, GIL обходится честно),
каждый готовит свои батчи заранее. Правило выбора: начать с числа физических ядер CPU, делённого
на число процессов обучения, и **измерить**. Больше — не всегда лучше:

- каждый воркер — копия процесса Python со своими копиями данных, память умножается;
- при большом $k$ растёт нагрузка на диск и на межпроцессную передачу (батчи сериализуются);
- если препроцессинг лёгкий, а батч большой, накладные расходы на передачу съедают выигрыш.

Диагностика простая: если увеличение `num_workers` не ускоряет эпоху — узкое место не в данных,
и дальше крутить его бессмысленно.

> ⚠️ **Типичная ошибка: взрыв памяти при `num_workers > 0`.** Воркеры создаются через `fork`,
> и данные родителя формально не копируются (copy-on-write). Но CPython хранит счётчик ссылок
> **внутри** объекта, и любое обращение к элементу списка изменяет страницу памяти — она
> копируется. Питоновский список из миллиона строк «размножится» по всем воркерам за пару минут
> работы. Лечение: хранить данные в `numpy`-массивах, `torch`-тензорах или memory-mapped
> файлах — там счётчик ссылок один на весь массив, страницы не трогаются.

**`pin_memory=True`** размещает батч в «закреплённой» (page-locked) памяти хоста. Только из такой
памяти GPU умеет копировать асинхронно, через DMA, не занимая CPU. Работает в паре с
`non_blocking=True` при переносе (см. [§8](#8-устройства-и-перемещение-данных)): по отдельности ни то, ни другое эффекта не даёт.

## 6. Канонический обучающий цикл

Ниже — цикл, который стоит уметь написать по памяти на собеседовании. Каждая строка тут
не случайна; комментарии объясняют почему, а не что.

```python
import torch
import torch.nn as nn
from torch.utils.data import DataLoader


def train_one_epoch(model, loader, optimizer, scheduler, criterion, device, max_norm=1.0):
    model.train()                       # включаем dropout и обновление статистик BatchNorm
    total_loss, total_n = 0.0, 0

    for x, y in loader:
        # non_blocking работает ТОЛЬКО в паре с pin_memory=True в DataLoader
        x = x.to(device, non_blocking=True)
        y = y.to(device, non_blocking=True)

        # set_to_none=True (значение по умолчанию с версии 2.0): вместо записи нулей
        # градиенты просто освобождаются — меньше памяти и на одну операцию меньше
        optimizer.zero_grad(set_to_none=True)

        logits = model(x)               # (B, K) для классификации на K классов
        loss = criterion(logits, y)     # скаляр

        loss.backward()                 # накопить градиенты в .grad параметров

        # клиппинг ВСЕГДА между backward и step, иначе он не на что не влияет
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm)

        optimizer.step()                # обновить веса
        scheduler.step()                # шаг расписания LR — ПОСЛЕ optimizer.step()

        # .item() отрывает число от графа: без него в total_loss утечёт весь граф батча
        total_loss += loss.item() * y.size(0)
        total_n += y.size(0)

    return total_loss / total_n


@torch.no_grad()                        # декоратор эквивалентен обёртке всего тела в no_grad
def evaluate(model, loader, criterion, device):
    model.eval()                        # dropout выключен, BatchNorm — на running-статистиках
    total_loss, correct, total_n = 0.0, 0, 0

    for x, y in loader:
        x = x.to(device, non_blocking=True)
        y = y.to(device, non_blocking=True)
        logits = model(x)
        total_loss += criterion(logits, y).item() * y.size(0)
        correct += (logits.argmax(dim=-1) == y).sum().item()
        total_n += y.size(0)

    return total_loss / total_n, correct / total_n


def fit(model, train_loader, val_loader, epochs=10, lr=3e-4, device="cuda"):
    device = torch.device(device if torch.cuda.is_available() else "cpu")
    model = model.to(device)            # модель на устройство ДО создания оптимизатора

    optimizer = torch.optim.AdamW(model.parameters(), lr=lr, weight_decay=0.01)
    # T_max в шагах, а не в эпохах, потому что scheduler.step() зовётся каждый батч
    scheduler = torch.optim.lr_scheduler.CosineAnnealingLR(
        optimizer, T_max=epochs * len(train_loader)
    )
    criterion = nn.CrossEntropyLoss()   # принимает СЫРЫЕ логиты, softmax внутри

    best_acc = 0.0
    for epoch in range(epochs):
        train_loss = train_one_epoch(model, train_loader, optimizer, scheduler,
                                     criterion, device)
        val_loss, val_acc = evaluate(model, val_loader, criterion, device)
        print(f"epoch {epoch}: train {train_loss:.4f} | val {val_loss:.4f} | acc {val_acc:.4f} "
              f"| lr {scheduler.get_last_lr()[0]:.2e}")

        if val_acc > best_acc:          # чекпоинт по метрике, а не по последней эпохе
            best_acc = val_acc
            torch.save({"model": model.state_dict(),
                        "optimizer": optimizer.state_dict(),
                        "scheduler": scheduler.state_dict(),
                        "epoch": epoch,
                        "val_acc": val_acc}, "best.pt")
    return best_acc
```

Несколько неочевидных решений в этом коде:

- **`criterion` принимает логиты.** `nn.CrossEntropyLoss` внутри делает `log_softmax` + NLL.
  Если подать в него уже применённый softmax, получите двойную нормализацию: обучение
  формально пойдёт, но градиенты будут слабые и качество заметно хуже. Симметричная ошибка —
  `nn.BCELoss` вместо `nn.BCEWithLogitsLoss`: вторая численно устойчива (log-sum-exp внутри),
  первая даёт NaN при уверенных предсказаниях.
- **Клиппинг между `backward` и `step`.** Поставите после `step()` — он не повлияет ни на что.
- **`scheduler.step()` после `optimizer.step()`.** Обратный порядок пропускает первое значение
  LR и вызывает предупреждение; на длинном обучении разница мала, но на коротком — заметна.
- **Смешанная точность** добавляется в этот цикл тремя строками (`autocast`, `GradScaler`) —
  разбор в [главе про масштабирование](06-scaling-and-efficiency.md).

## 7. train() против eval(): что именно меняется

`model.train()` и `model.eval()` делают ровно одну вещь: рекурсивно проставляют флаг
`self.training` всем подмодулям. Дальше каждый модуль сам решает, что с этим флагом делать.
Модулей, которые реагируют, всего два с половиной — но именно они и создают все проблемы.

**Dropout.**

- `train`: генерируется бернуллиевская маска, часть активаций зануляется, остальные умножаются
  на $1/(1-p)$, где $p$ — вероятность зануления. Это «инвертированный dropout»: масштабирование
  делается на обучении, чтобы математическое ожидание активации не менялось.
- `eval`: тождественная операция. Ничего не зануляется, ничего не масштабируется.

**BatchNorm.**

- `train`: нормализация по статистикам **текущего батча**; параллельно обновляются
  скользящие средние: $\mu_{\text{run}} \leftarrow (1-m)\mu_{\text{run}} + m\,\mu_{\text{batch}}$,
  где $m$ — momentum (по умолчанию 0,1).
- `eval`: нормализация по **накопленным** $\mu_{\text{run}}, \sigma^2_{\text{run}}$;
  обновление не происходит.

**Половинка** — это модули вроде `nn.LSTM` с параметром `dropout`, а также ваши собственные
модули, если вы в них проверяете `self.training`.

Чего `eval()` **не делает**:

- не отключает вычисление градиентов (нужен `torch.no_grad()`);
- не замораживает веса (для этого `requires_grad_(False)`);
- не влияет на LayerNorm, RMSNorm, GroupNorm — они не зависят ни от батча, ни от режима,
  что и есть одна из причин их популярности в трансформерах (см.
  [§7.2 главы о трансформере](04-attention-and-transformer.md#72-остаточные-связи-и-нормализация-pre-ln-против-post-ln));
- не влияет на оптимизатор.

> ⚠️ **Типичная ошибка, стоящая дороже всех.** Забыть вернуть `model.train()` после валидации
> внутри эпохи. Симптом: качество внезапно перестаёт расти после первой валидации, лосс
> «залипает». Причина: остаток обучения идёт без dropout и с замороженными статистиками BN —
> модель переобучается и получает рассогласование train/eval. Защита — структурировать код так,
> чтобы `train()` и `eval()` вызывались строго в начале соответствующих функций,
> как в [§6](#6-канонический-обучающий-цикл), а не по ходу.

> 🧠 **Middle+. BatchNorm при дообучении.** При fine-tuning на маленьком датасете статистики BN
> из предобученной модели часто лучше, чем пересчитанные на ваших 500 примерах. Стандартный
> приём — заморозить BN: перевести именно эти модули в `eval()` даже во время обучения
> (`for m in model.modules(): if isinstance(m, nn.BatchNorm2d): m.eval()`) и, при желании,
> отключить градиент их аффинным параметрам. Отдельно: при распределённом обучении обычный BN
> считает статистику **по локальному батчу каждой GPU**, что при батче 2–4 на устройство даёт
> шум; лечится `nn.SyncBatchNorm.convert_sync_batchnorm(model)`.

## 8. Устройства и перемещение данных

```python
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")

model = model.to(device)        # для nn.Module — операция IN-PLACE, возврат для удобства
x = x.to(device)                # для тензора — НЕ in-place, обязательно присвоить результат
```

Разница в поведении `to()` для модуля и для тензора — источник немого бага: `x.to(device)`
без присваивания не делает ничего, и через пару строк вы получаете
`Expected all tensors to be on the same device`.

**Асинхронность.** Все операции CUDA ставятся в очередь и выполняются асинхронно относительно
Python. Строка `y = model(x)` возвращает управление до того, как вычисления закончены.
Из этого следуют два важных следствия:

1. **Замер времени без синхронизации бессмыслен.** `t0 = time.time(); y = model(x);
   print(time.time() - t0)` измерит время постановки задачи в очередь, а не время работы.
   Перед замером нужен `torch.cuda.synchronize()`.
2. **Любое обращение к значению тензора синхронизирует** — `.item()`, `.cpu()`, `print(tensor)`,
   `if tensor > 0`. В цикле обучения каждая такая операция останавливает конвейер. Один `.item()`
   на батч для логирования — нормально; десять — уже заметно.

**Асинхронное копирование.** `x.to(device, non_blocking=True)` возвращает управление сразу,
не дожидаясь окончания копирования, — но **только если память источника закреплена**
(`pin_memory=True` в DataLoader). Без закрепления флаг игнорируется молча. Правильная связка:
`pin_memory=True` в `DataLoader` + `non_blocking=True` в `.to()`. Тогда пока GPU считает батч $i$,
батч $i+1$ уже копируется.

> 💬 **На собеседовании.** Спросят: «GPU загружена на 30 %, обучение медленное. Ваши действия?»
> Хороший ответ — по шагам, от дешёвого к дорогому. Первое: проверить, не упирается ли всё
> в загрузку данных — поднять `num_workers`, включить `pin_memory` + `non_blocking`, а для
> проверки гипотезы прогнать эпоху на одном заранее загруженном батче: если скорость взлетела,
> виноват пайплайн данных. Второе: поискать синхронизации в цикле — `.item()`, `.cpu()`,
> печать тензоров, ассерты на значениях. Третье: увеличить размер батча, чтобы ядра GPU
> получали больше работы за вызов. Четвёртое: включить смешанную точность и `torch.compile`.
> И только потом — переписывать модель. Профилировать до, а не вместо.
> Провал: сразу «взять GPU помощнее».

## 9. Сохранение и загрузка

**`state_dict`** — обычный словарь `{имя_параметра: тензор}`. Сохраняют именно его, а не модель
целиком:

```python
# ПРАВИЛЬНО
torch.save(model.state_dict(), "model.pt")

model = MyModel(**config)                       # архитектуру создаём из кода
state = torch.load("model.pt", map_location="cpu", weights_only=True)
model.load_state_dict(state)
model.eval()

# ПЛОХО: torch.save(model, "model.pt") — pickle сохранит ссылку на класс,
# и файл перестанет читаться при переименовании модуля или обновлении библиотеки
```

Четыре детали, о которых спрашивают:

- **`map_location="cpu"`.** Без него загрузка чекпоинта, сохранённого с `cuda:3`, на машине
  с одной GPU упадёт. Привычка «всегда грузить на CPU, потом `.to(device)`» экономит время.
- **`weights_only=True`.** `torch.load` исторически использовал `pickle`, то есть загрузка
  чужого чекпоинта означала исполнение произвольного кода. В свежих версиях PyTorch
  безопасный режим стал значением по умолчанию; указывайте флаг явно, чтобы код вёл себя
  одинаково на разных версиях.
- **Префикс `module.`.** Модель, обученная в `DistributedDataParallel`, сохраняет ключи вида
  `module.layer1.weight`. Загрузка в обычную модель падает. Лечится сохранением
  `model.module.state_dict()` либо снятием префикса при загрузке.
- **`strict=False`** позволяет загрузить частично совпадающие веса (типично при смене головы
  модели). Опасность в том, что при опечатке в имени слоя веса **молча** не загрузятся.
  Всегда смотрите на возвращаемое значение: `missing, unexpected = model.load_state_dict(sd, strict=False)`.

**Полный чекпоинт** для продолжения обучения обязан содержать больше, чем веса:

```python
torch.save({
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),     # моменты Adam: без них рестарт даёт скачок лосса
    "scheduler": scheduler.state_dict(),     # иначе LR откатится к начальному
    "scaler": scaler.state_dict(),           # состояние GradScaler при mixed precision
    "epoch": epoch,
    "global_step": step,
    "rng": {                                  # для воспроизводимого продолжения
        "torch": torch.get_rng_state(),
        "cuda": torch.cuda.get_rng_state_all(),
    },
    "config": config,                        # гиперпараметры рядом с весами
}, "ckpt.pt")
```

Пропуск состояния оптимизатора — самая частая ошибка при возобновлении обучения: моменты Adam
обнуляются, и первые сотни шагов после рестарта модель фактически деградирует.

## 10. Подводные камни: каталог типичных багов

Этот раздел стоит перечитать перед собеседованием: вопрос «расскажите про баг, который долго
искали» задают почти всегда, а половина списка ниже — готовые истории. Формат:
**симптом → причина → что делать**.

**1. Забыли `optimizer.zero_grad()`.**
Симптом: лосс ведёт себя странно с первых шагов, при большом LR — сразу расходится;
норма градиента растёт от шага к шагу примерно линейно.
Причина: градиенты накапливаются со всех предыдущих итераций (см. [§4](#4-autograd-граф-backward-detach-no_grad)), эффективный шаг растёт.
Что делать: `optimizer.zero_grad(set_to_none=True)` в начале каждой итерации. Диагностика:
залогируйте `clip_grad_norm_` — она возвращает норму **до** обрезки; монотонный рост
подтверждает диагноз.

**2. Накопление лосса без `.item()`.**
Симптом: потребление памяти растёт линейно в течение эпохи, OOM ближе к концу; после `del`
и `empty_cache()` память не возвращается.
Причина: `total_loss += loss` сохраняет тензор **вместе со всем графом** батча. Через 1000
итераций в памяти висит 1000 графов.
Что делать: `total_loss += loss.item()` или `loss.detach()`. То же касается любых списков,
в которые вы складываете предсказания: `preds.append(logits)` в цикле обучения — та же утечка,
нужно `logits.detach().cpu()`.

**3. Валидация без `torch.no_grad()`.**
Симптом: OOM на валидации при том, что батч там меньше, чем на обучении.
Причина: строится граф для backward, который никогда не случится; активации всех слоёв висят
в памяти.
Что делать: декоратор `@torch.no_grad()` на функции валидации (или `inference_mode`).
Экономия памяти — в разы.

**4. Не вернули `model.train()` после валидации.**
Симптом: качество растёт до первой валидации, потом выходит на плато; train-лосс падает
подозрительно быстро.
Причина: остаток обучения идёт с выключенным dropout и замороженными статистиками BatchNorm.
Что делать: см. [§7](#7-train-против-eval-что-именно-меняется) — вызывать режим в начале функции, а не по ходу.

**5. Забыли `model.eval()` на инференсе.**
Симптом: предсказания для одного и того же входа отличаются от запуска к запуску; метрики
в проде хуже офлайновых на несколько процентов.
Причина: активен dropout; BatchNorm пересчитывает и **портит** running-статистики боевым
трафиком.
Что делать: `model.eval()` сразу после загрузки весов; в сервисе — юнит-тест
«два одинаковых запроса дают идентичный ответ».

**6. Неверный порядок `optimizer.step()` и `scheduler.step()`.**
Симптом: предупреждение `Detected call of lr_scheduler.step() before optimizer.step()`;
первое значение LR из расписания пропущено.
Причина: расписание считает шаги оптимизатора, а его дёрнули раньше.
Что делать: строго `optimizer.step()` → `scheduler.step()`. Отдельная ловушка: `ReduceLROnPlateau`
вызывается **раз в эпоху и с метрикой** (`scheduler.step(val_loss)`), а не каждый батч.

**7. Клиппинг не в том месте (или без `unscale_`).**
Симптом: `clip_grad_norm_` стоит, а NaN всё равно появляются; либо клиппинг никогда
не срабатывает.
Причина: вызов после `optimizer.step()` (уже поздно) или при mixed precision без
`scaler.unscale_(optimizer)` — норма считается по отмасштабированным градиентам, и порог
не имеет смысла.
Что делать: `backward()` → (`scaler.unscale_`) → `clip_grad_norm_` → `step()`.

**8. `shuffle=True` на валидации, `shuffle=False` на обучении.**
Симптом (первое): метрики валидации слегка «плавают» от запуска к запуску, примеры для ручного
разбора каждый раз разные, а с `drop_last=True` часть валидации вообще теряется.
Симптом (второе): обучение идёт рывками, лосс пилообразный; модель «забывает» ранние классы.
Причина: данные на диске часто отсортированы по классу/дате; без перемешивания батч состоит
из одного класса, и градиент каждого батча смещён.
Что делать: `shuffle=True` и `drop_last=True` на train, `shuffle=False` и `drop_last=False`
на val/test. Правило простое: перемешивание нужно там, где считается градиент,
и вредно там, где считается метрика.

**9. BatchNorm при батче 1 или при сильно неоднородных батчах.**
Симптом: `Expected more than 1 value per channel when training` — прямая ошибка; или тихая
деградация при батче 2–4.
Причина: дисперсия по батчу из одного элемента не определена; из четырёх — крайне шумная.
Что делать: `drop_last=True` (чтобы не осталось батча из одного элемента), увеличить батч,
либо GroupNorm/LayerNorm.

**10. `non_blocking=True` без `pin_memory=True`.**
Симптом: никакого ускорения от «асинхронного» копирования.
Причина: асинхронное копирование возможно только из закреплённой памяти; иначе флаг
игнорируется.
Что делать: включать обе опции вместе; проверять профайлером, что копирование перекрывается
с вычислениями.

**11. Оптимизатор создан до переноса модели на GPU.**
Симптом: работает, но при загрузке чекпоинта — `Expected all tensors to be on the same device`;
или моменты Adam остаются на CPU и обучение необъяснимо медленное.
Причина: `model.to(device)` меняет параметры на месте, но состояние оптимизатора создаётся
на устройстве параметра в момент первого `step()`.
Что делать: `model.to(device)` **до** создания оптимизатора — это дешёвая привычка,
снимающая целый класс проблем.

**12. Утечка памяти через хранение тензоров с графом.**
Симптом: `torch.cuda.memory_allocated()` растёт от итерации к итерации.
Причина: тензор с `grad_fn` попал в список, словарь метрик, атрибут модуля или скрытое
состояние RNN, переносимое между батчами.
Что делать: `detach()` на всём, что переживает итерацию. Диагностика:
`print(torch.cuda.memory_allocated() / 2**20)` в конце каждой итерации — если число растёт,
ищите, что вы сохранили.

**13. Фрагментация памяти вместо утечки.**
Симптом: OOM при том, что `memory_allocated()` показывает вдвое меньше, чем есть на карте;
`memory_reserved()` при этом велик.
Причина: кэширующий аллокатор CUDA держит зарезервированные блоки неподходящего размера
(типично при переменной длине последовательностей).
Что делать: фиксированные размеры батча/длины (bucketing по длине), переменная окружения
`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, в крайнем случае `torch.cuda.empty_cache()`
между фазами (но не в цикле — это дорого и не лечит причину).

**14. Одинаковые аугментации во всех воркерах.**
Симптом: при `num_workers=4` эффективное разнообразие аугментаций падает вчетверо, качество хуже,
чем при `num_workers=0`.
Причина: `numpy.random` и `random` наследуют состояние генератора при `fork`, и все воркеры
выдают одну и ту же последовательность случайных чисел. PyTorch свой генератор в воркерах
пересевает, а numpy — нет.
Что делать: `worker_init_fn`, который сеет numpy/random уникальным значением на воркер
(код — в [§13](#13-воспроизводимость)), либо использовать только `torch`-генераторы внутри `Dataset`.

**15. Двойной softmax.**
Симптом: модель обучается, но медленно и до худшего качества; логиты подозрительно маленькие.
Причина: `nn.CrossEntropyLoss` применяется к выходу, к которому уже применён `softmax`
или `log_softmax`.
Что делать: `CrossEntropyLoss` принимает сырые логиты. Для бинарной задачи —
`BCEWithLogitsLoss` вместо `Sigmoid + BCELoss`.

**16. Использование `.data` вместо `detach()`.**
Симптом: неверные градиенты без каких-либо ошибок и предупреждений.
Причина: `.data` обходит систему версионирования тензоров, и autograd не замечает, что данные
изменились под ним.
Что делать: никогда не использовать `.data`; для отсоединения — `detach()`, для изменения
весов — блок `with torch.no_grad():`.

**17. Слои в обычном списке вместо `nn.ModuleList`.**
Симптом: модель обучается, но качество как у гораздо более слабой архитектуры; после загрузки
чекпоинта часть сети ведёт себя как необученная; иногда — ошибка устройства на forward.
Причина: `self.layers = [...]` не регистрирует модули, они не попадают ни в `parameters()`,
ни в `state_dict`, ни под `.to(device)`.
Что делать: `nn.ModuleList` / `nn.ModuleDict` / `nn.Sequential`. Диагностика: сравнить
`sum(p.numel() for p in model.parameters())` с расчётом на бумаге.

**18. Метрики усредняются по батчам, а не по объектам.**
Симптом: валидационная метрика чуть-чуть отличается от посчитанной вручную по всему датасету;
расхождение растёт, если последний батч сильно неполный.
Причина: `np.mean(batch_losses)` даёт невзвешенное среднее, где неполный батч из 3 объектов
весит столько же, сколько полный из 128. Для отношений (precision, F1) ошибка ещё грубее:
среднее по батчам — не то же самое, что метрика по всему набору.
Что делать: накапливать числитель и знаменатель отдельно (`total_loss += loss.item() * y.size(0)`,
как в [§6](#6-канонический-обучающий-цикл)), а для F1-подобных метрик — копить счётчики TP/FP/FN и считать метрику один раз в конце.

## 11. Профилирование: где на самом деле уходит время

Правило номер один: **не оптимизируйте по интуиции**. Типичное распределение «где на самом деле
проблема» в реальных проектах: примерно половина случаев — пайплайн данных, четверть —
неоправданные синхронизации и мелкие ядра, и только оставшееся — собственно модель.

### Чем мерить: wall clock против CUDA-событий

Всё в этом разделе опирается на замеры, поэтому начнём с того, как их не испортить. Из
[§8](#8-устройства-и-перемещение-данных) мы знаем, что вызовы CUDA асинхронны: `model(x)`
возвращает управление, поставив работу в очередь. Отсюда три разных «времени», которые легко
перепутать:

- `time.perf_counter()` **без** синхронизации меряет только постановку задач в очередь —
  десятки микросекунд вместо десятков миллисекунд;
- `time.perf_counter()` **с** `torch.cuda.synchronize()` меряет сквозное время: и работу CPU,
  и работу GPU, и все простои между ними;
- **CUDA-события** (`torch.cuda.Event`) — это метки времени, которые ставятся в поток GPU
  и срабатывают, когда до них дойдёт очередь. Разница между двумя событиями — время, прошедшее
  на стороне GPU, включая дыры, если очередь опустела.

Полезны все три, и именно вместе: сравнение стенного времени с временем событий сразу говорит,
кто кого ждёт.

```python
import time
import torch


def bench_cuda(fn, n_warmup: int = 10, n_iter: int = 50):
    """Три числа вместо одного: постановка в очередь, время GPU, сквозное время."""
    for _ in range(n_warmup):
        fn()                                   # прогрев: аллокатор, автотюнинг cuDNN, компиляция
    torch.cuda.synchronize()

    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)

    t0 = time.perf_counter()
    start.record()                             # событие СТАВИТСЯ В ОЧЕРЕДЬ, а не срабатывает сейчас
    for _ in range(n_iter):
        fn()
    end.record()
    enqueue = (time.perf_counter() - t0) / n_iter * 1e3   # сколько CPU потратил на запуск ядер
    torch.cuda.synchronize()                   # только теперь события гарантированно случились
    wall = (time.perf_counter() - t0) / n_iter * 1e3
    gpu = start.elapsed_time(end) / n_iter     # elapsed_time отдаёт миллисекунды

    print(f"постановка в очередь: {enqueue:.3f} мс | GPU: {gpu:.3f} мс | сквозное: {wall:.3f} мс")
    return wall, gpu
```

Читается результат так. Если `enqueue` близко к `wall`, значит, CPU не успевает запускать ядра —
модель состоит из мелких операций, и вы упёрлись в накладные расходы запуска (launch-bound);
лечится большим батчем, `torch.compile` и CUDA-графами ([§12](#12-torchcompile-что-он-делает-физически-и-когда-ломается)).
Если `gpu` близко к `wall`, а `enqueue` мало — узкое место действительно на карте, и дальше
работает roofline из [главы про масштабирование](06-scaling-and-efficiency.md#1-как-устроена-gpu-и-почему-она-простаивает).
Если оба заметно меньше `wall` — время уходит между итерациями: данные, логирование,
синхронизации.

> ⚠️ **Типичная ошибка.** Ставить `torch.cuda.synchronize()` внутрь цикла, чтобы «померить
> каждую итерацию честно». Синхронизация запрещает перекрытие копирования с вычислениями
> и запуска следующих ядер с текущими — вы измеряете не свой цикл, а его искалеченную версию,
> обычно на 10–30 % медленнее. Правильно: синхронизировать один раз до замера и один раз после,
> а поитерационную разбивку брать из CUDA-событий или из профайлера.

> 💬 **На собеседовании.** Спросят: «Как правильно замерить время forward-прохода на GPU?»
> Хороший ответ: сначала прогрев не меньше десяти итераций — первый вызов включает аллокацию,
> автотюнинг cuDNN и компиляцию ядер, и он не репрезентативен. Затем замер по нескольким
> десяткам итераций с `torch.cuda.synchronize()` **до** и **после** блока, а не внутри цикла.
> Лучше — `torch.cuda.Event(enable_timing=True)`: события ставятся в поток и меряют время
> именно на GPU, не блокируя CPU. Сильное продолжение: сравнить стенное время с временем
> событий — если стенное заметно больше, вы упираетесь не в карту, а в Python или в данные,
> и оптимизировать модель бессмысленно.
> Провал: `time.time()` вокруг вызова без синхронизации — так меряют скорость постановки задач
> в очередь и получают «ускорение в 50 раз», которого нет.

### Шаг 0: быстрая триажная проверка

Прежде чем запускать профайлер, две минуты диагностики:

```python
import time
import torch

def time_epoch(loader, model, device, n_batches=50):
    """Сравниваем: время с реальным DataLoader против времени на одном
    заранее загруженном батче. Разница = стоимость пайплайна данных."""
    model.train()
    batch = next(iter(loader))
    x0, y0 = batch[0].to(device), batch[1].to(device)

    torch.cuda.synchronize()            # без этого измерим постановку в очередь, а не работу
    t0 = time.perf_counter()
    for i, (x, y) in enumerate(loader):
        if i >= n_batches:
            break
        x, y = x.to(device, non_blocking=True), y.to(device, non_blocking=True)
        model(x).sum().backward()
    torch.cuda.synchronize()
    with_data = time.perf_counter() - t0

    torch.cuda.synchronize()
    t0 = time.perf_counter()
    for _ in range(n_batches):
        model(x0).sum().backward()      # тот же самый батч: данные не грузятся вообще
    torch.cuda.synchronize()
    compute_only = time.perf_counter() - t0

    print(f"с данными: {with_data:.2f} c | только вычисления: {compute_only:.2f} c")
    print(f"доля пайплайна данных: {(with_data - compute_only) / with_data:.0%}")
```

Если доля пайплайна велика — крутите `num_workers`, `pin_memory`, формат хранения данных
и препроцессинг, а модель не трогайте.

### Шаг 1: `torch.profiler`

```python
import torch
from torch.profiler import profile, ProfilerActivity, schedule, record_function

prof_schedule = schedule(wait=1, warmup=1, active=3, repeat=1)
# wait — пропускаем прогрев, warmup — греем без записи, active — собираем.
# Без прогрева в статистику попадут разовые аллокации и компиляция ядер.

with profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
    schedule=prof_schedule,
    record_shapes=True,          # формы тензоров в отчёте: сразу видно "узкие" ядра
    profile_memory=True,         # пики аллокаций по операциям
    with_stack=False,            # стеки Python — полезно, но заметно замедляет
) as prof:
    for step, (x, y) in enumerate(loader):
        if step >= 5:
            break
        x, y = x.to(device, non_blocking=True), y.to(device, non_blocking=True)
        with record_function("forward"):     # свои метки в трассе
            loss = criterion(model(x), y)
        with record_function("backward"):
            loss.backward()
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
        prof.step()                          # обязательно: двигает расписание профайлера

print(prof.key_averages().table(sort_by="self_cuda_time_total", row_limit=15))
prof.export_chrome_trace("trace.json")       # открыть в chrome://tracing или perfetto.dev
```

**Смотреть в первую очередь надо не на таблицу, а на трассу.** Откройте `trace.json`
в [perfetto.dev](https://ui.perfetto.dev/) и посмотрите на дорожку GPU: если на ней **дыры** —
никакая оптимизация ядер не поможет, карта просто ждёт. Дыры отвечают на вопрос «данные
или вычисления» быстрее, чем любые числа. И только когда дорожка плотная, имеет смысл
разбираться, чем именно она заполнена, — тогда идёт таблица.

Сортировать таблицу надо по **`self_cuda_time_total`** — времени в самом ядре, без вложенных
вызовов; `cuda_time_total` для верхнеуровневых операций всегда покажет «модель целиком»
и ничего не объяснит. Дальше — по симптомам:

| Что видно | Диагноз | Что делать |
|---|---|---|
| дыры на дорожке GPU, `cudaStreamSynchronize` в топе | карта голодает: узкое место на хосте | `num_workers`, `pin_memory`, вынести препроцессинг из `__getitem__` |
| `aten::copy_`, `cudaMemcpyAsync` среди верхних строк | тензоры гоняются между CPU и GPU каждый шаг | искать `.item()`, `.cpu()`, `.numpy()`, `print(tensor)`, ассерты на значениях |
| сотни ядер по 3–20 мкс, ни одно не выделяется | launch-bound: модель из мелких операций | больше батч, `torch.compile`, CUDA-графы ([§12](#12-torchcompile-что-он-делает-физически-и-когда-ломается)) |
| в топе `vectorized_elementwise_kernel`, `at::native::layer_norm` | memory-bound хвост блока | слияние ядер |
| в топе ядра GEMM (`cutlass`, `ampere_bf16_...`), суммарно больше 60 % | это норма | дальше — точность, размерности, FlashAttention |
| ядра `nccl` на критическом пути | коммуникация не перекрыта с обратным проходом | см. [главу про масштабирование](06-scaling-and-efficiency.md#7-ddp-как-работает-all-reduce) |
| заметное время в `cudaMalloc` / `cudaFree` | аллокатор перевыделяет память | стабилизировать формы, бакетинг по длине |

Отдельно про режим `with_stack=True`: он привязывает ядра к строкам Python-кода, и это
единственный способ понять, **какой именно** `nn.Module` породил ядро, которое вы видите
в топе. Плата — замедление в разы, поэтому включают его на 3–5 шагах, а не на всём обучении.

### Профиль памяти: Memory Snapshot

Профайлер отвечает на вопрос «куда уходит время». На вопрос «куда уходит память» отвечает
другой инструмент, о существовании которого знают гораздо реже, — **Memory Snapshot**.
Он записывает каждую аллокацию и освобождение вместе со стеком Python и рисует картинку
«память во времени».

```python
import torch

# Запись стоит времени и памяти, поэтому включаем её вокруг нескольких шагов, а не навсегда.
torch.cuda.memory._record_memory_history(max_entries=100_000)

for step, (x, y) in enumerate(loader):
    train_step(model, optimizer, x, y)
    if step >= 3:
        break

torch.cuda.memory._dump_snapshot("snapshot.pickle")
torch.cuda.memory._record_memory_history(enabled=None)      # выключить запись
# Открыть snapshot.pickle на https://pytorch.org/memory_viz — страница работает локально,
# файл никуда не отправляется.
```

Что на этой картинке видно сразу и не видно больше нигде:

- **утечка** — пилообразный график с растущим основанием: после каждой итерации остаётся
  чуть больше, чем было. Клик по «лишнему» блоку показывает стек, который его удерживает
  (типично — накопление `loss` без `.item()`, см. [§10](#10-подводные-камни-каталог-типичных-багов));
- **настоящая структура пика**: сколько занимают активации, сколько состояние оптимизатора,
  сколько временные буферы. Это единственный честный способ узнать, что именно чинить,
  прежде чем включать пересчёт активаций или шардинг;
- **фрагментация** — разрывы между занятыми блоками. Её отличают от утечки по паре чисел:

```python
mb = 2 ** 20
print(f"allocated {torch.cuda.memory_allocated()/mb:.0f} МиБ, "
      f"reserved {torch.cuda.memory_reserved()/mb:.0f} МиБ")
```

Если `reserved` заметно больше `allocated`, а OOM всё равно случается — память есть,
но она нарезана кусками неподходящего размера. Причина и лечение разобраны
в [§10](#10-подводные-камни-каталог-типичных-багов), пункт 13; главное средство —
`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` и стабилизация форм.

### Питоновская сторона: py-spy

`torch.profiler` видит операции PyTorch. Он **не видит** того, что происходит в чистом Python:
токенизацию, аугментации на CPU, сборку `pd.DataFrame` в `__getitem__`, медленный `collate_fn`.
А именно там чаще всего и обнаруживается «дыра на дорожке GPU». Инструмент для этой половины
работы — `py-spy`: сэмплирующий профайлер, который подключается к **уже запущенному** процессу
и не требует ни правки кода, ни рестарта.

```bash
py-spy top --pid 12345                       # что процесс делает прямо сейчас, обновляется вживую
py-spy dump --pid 12345                      # стеки всех потоков разово: чем занят зависший процесс
py-spy record --pid 12345 --duration 60 --subprocesses \
       --format speedscope -o prof.json      # --subprocesses обязателен: воркеры DataLoader — отдельные процессы
```

Два сценария, ради которых стоит держать `py-spy` под рукой. Первый: трасса показывает дыры,
а в топе профайлера нет ни одной тяжёлой операции — значит, время в Python, и `py-spy record`
за минуту покажет, в какой функции. Второй: обучение **зависло** — DDP молчит, ошибок нет.
`py-spy dump` по каждому процессу мгновенно показывает, кто стоит в коллективной операции,
а кто ушёл вперёд; это самый быстрый способ отладки зависаний из
[главы про масштабирование](06-scaling-and-efficiency.md#12-подводные-камни).

### Шаг 2: быстрые победы

Прежде чем переписывать модель, есть несколько изменений на одну-две строки, которые почти
всегда дают выигрыш и почти ничего не стоят:

```python
# 1. На Ampere и новее матмулы можно считать в tf32 — почти вдвое быстрее fp32
#    ценой точности на уровне fp16. Для обучения это обычно приемлемо.
torch.set_float32_matmul_precision("high")

# 2. cuDNN подберёт лучший алгоритм свёртки под ваши формы. Работает ТОЛЬКО если формы
#    постоянны: при переменной длине входа автотюнинг перезапускается и всё становится хуже.
torch.backends.cudnn.benchmark = True

# 3. Для свёрточных сетей раскладка NHWC ("channels_last") лучше ложится на тензорные ядра
model = model.to(memory_format=torch.channels_last)
x = x.to(memory_format=torch.channels_last)

# 4. Компиляция графа: слияние мелких операций в одно ядро, меньше запусков и обращений
#    к памяти. Первый вызов долгий (компиляция), поэтому мерить надо со второй эпохи.
#    Разбор того, что при этом происходит физически, — в §12.
model = torch.compile(model)
```

Порядок применения — именно такой: сначала самое дешёвое. И после каждого изменения замер,
иначе вы не узнаете, что именно помогло (а что-то из этого списка на вашей задаче может
и навредить — `cudnn.benchmark` при переменных формах, `torch.compile` при динамических
формах и частых перекомпиляциях). Смешанная точность, накопление градиента и распределённое
обучение — следующий уровень ускорения, им посвящена
[глава 06](06-scaling-and-efficiency.md).

> 💬 **На собеседовании.** Спросят: «Как вы искали узкое место в обучении?»
> Хороший ответ звучит как протокол: сначала проверяю утилизацию GPU и сравниваю время эпохи
> с временем на фиксированном батче — это за минуту разделяет «данные» и «вычисления».
> Если данные — смотрю `num_workers`, формат хранения, тяжёлый препроцессинг в `__getitem__`.
> Если вычисления — запускаю `torch.profiler`, сортирую по `self_cuda_time_total`, смотрю трассу
> на предмет дыр и синхронизаций. Дальше по результату: батч, mixed precision, `torch.compile`,
> и только в последнюю очередь — изменение архитектуры. Обязательно упомянуть, что замеры
> на GPU требуют `torch.cuda.synchronize()`.
> Провал: «смотрю в nvidia-smi» как единственный инструмент — утилизация 100 % ещё не значит,
> что вы делаете полезную работу.

## 12. torch.compile: что он делает физически и когда ломается

Из предыдущего раздела вы выходите с одним из двух диагнозов: «слишком много мелких ядер»
или «слишком много запусков». `torch.compile` лечит ровно эти два, и полезно понимать, каким
способом, — иначе непонятно, почему на одной модели он даёт 40 %, а на другой ноль или минус.

### Что происходит внутри

Вспомним первую идею главы: граф в PyTorch **не строится заранее**, он побочный продукт
выполнения Python-кода. Это удобно для отладки и катастрофично для оптимизации: пока модель —
это последовательность вызовов Python, никто не может увидеть, что три соседние операции
можно слить в одну.

`torch.compile` вставляет в этот процесс четыре шага.

1. **TorchDynamo** перехватывает исполнение байткода Python и **записывает** операции
   в граф FX — вместо того чтобы сразу их выполнять. Всё, что он не может записать
   (обращение к внешнему объекту, `print`, `.item()`, условие по значению тензора), становится
   **разрывом графа** (graph break): Dynamo возвращает управление обычному Python, а после
   разрыва начинает новый граф.
2. **AOTAutograd** заранее строит из прямого графа ещё и **обратный** — поэтому компилируется
   не только forward, но и backward.
3. **Inductor** — компилятор — принимает решение, какие операции слить, и генерирует под них
   ядра. На GPU он генерирует их на **Triton**, на CPU — на C++/OpenMP.
4. Полученные ядра компилируются и кэшируются под конкретный набор **форм и типов** входа.

Отсюда прямо следует, что он умеет и чего не умеет. Умеет: слить цепочку поэлементных операций
в одно ядро (главный источник выигрыша, механику см. в
[главе про масштабирование](06-scaling-and-efficiency.md#1-как-устроена-gpu-и-почему-она-простаивает)),
убрать промежуточные аллокации, свернуть константы, а в режиме `mode="reduce-overhead"` —
записать последовательность запусков в **CUDA-граф** и воспроизводить её одним вызовом,
что убивает накладные расходы на запуск. Не умеет: ускорить одно большое матричное умножение —
там уже работает cuBLAS, и сливать нечего.

Практический вывод, который стоит произносить вслух: **выигрыш от `torch.compile` примерно
равен доле времени, которая уходила на мелкие memory-bound ядра и на запуски**. Для большого
трансформера с длинными последовательностями это 5–20 %, для маленькой модели с батчем 32,
где GPU не насыщается, — иногда в разы.

### Где он ломается

```python
import torch
import torch._dynamo as dynamo

model = torch.compile(model)                    # по умолчанию mode="default"

# Диагностика — прежде чем разбираться в замерах: сколько получилось графов,
# где именно Dynamo сдался и почему. Один граф — идеал, десять — компиляция бессмысленна.
explanation = dynamo.explain(model)(x)
print(explanation.graph_count, explanation.break_reasons)
```

```bash
# Логи компилятора: два самых полезных ключа за всё время работы с torch.compile
TORCH_LOGS="graph_breaks,recompiles" python train.py
```

Четыре причины, по которым он не даёт обещанного.

**Разрывы графа.** Каждый `print`, `.item()`, `if loss > threshold`, обращение к `numpy`,
вызов непонятной ему сторонней функции разрезает граф. Десяток разрывов в forward — и сливать
уже почти нечего: каждый кусок компилируется отдельно, а между ними возвращается интерпретатор.
Симптом: `graph_count` больше единицы-двух. Лечение: убрать из `forward` всё, что не является
вычислением, — логирование, ассерты на значениях, ветвления по данным.

**Динамические формы.** Компиляция кэшируется по формам. Тексты произвольной длины — это новая
компиляция на каждую длину, по 20–120 секунд каждая. После нескольких перекомпиляций одного
и того же участка Dynamo сдаётся и переходит в режим динамических форм (или вовсе
в eager) — вы получаете предупреждение и потерянные минуты. Лечение: паддинг к фиксированному
набору длин (64/128/256/512), бакетинг или явное `torch.compile(model, dynamic=True)`,
которое сразу компилирует форм-независимую версию — чуть медленнее, зато один раз.

**Первый шаг стоит дорого.** 20–120 секунд на компиляцию, а с `mode="max-autotune"` — минуты,
потому что Inductor перебирает варианты ядер и замеряет их. Мерить надо со второй эпохи,
а в сервисе — прогревать на всех типичных формах до того, как пойдёт трафик.

**Взаимодействие с остальным стеком.** Пересчёт активаций требует `use_reentrant=False`;
хуки на модулях часто дают разрыв; кастомные `autograd.Function` без правильных аннотаций
выпадают в eager. Это не приговор, но каждый такой случай надо проверять замером, а не верой.

> ⚠️ **Типичная ошибка.** Обернуть модель в `torch.compile`, увидеть на первой итерации время
> в сто раз хуже и сделать вывод, что «компиляция не работает». Первая итерация — это и есть
> компиляция. Вторая ошибка того же рода — замерить «до» и «после» на разных длинах входа
> и получить, что скомпилированная версия медленнее: вы измерили не модель, а перекомпиляцию.
> Протокол честного замера: прогрев не меньше 10 итераций на **тех же** формах, потом
> замер по 50 итерациям (`bench_cuda` из [§11](#11-профилирование-где-на-самом-деле-уходит-время)),
> и обязательно проверка `TORCH_LOGS="recompiles"` на отсутствие перекомпиляций в замеряемом окне.

### Triton в двух абзацах

**Triton** — язык для написания GPU-ядер на Python, в котором вы оперируете не отдельными
нитями, а блоками элементов; распределение по нитям, работу с shared memory и векторизацию
компилятор берёт на себя. Именно на нём Inductor генерирует ядра, и именно на нём написан
референсный FlashAttention — то есть это не игрушка, а рабочий инструмент, на котором пишут
ядра уровня библиотеки.

Когда его писать руками? Почти никогда — и это честный ответ. Порядок такой: сначала
`torch.compile`, потом готовые слитые реализации (`F.scaled_dot_product_attention`,
`AdamW(fused=True)`, ядра из `xformers`/`flash-attn`), и только если профиль показывает,
что конкретный участок memory-bound, а автоматическое слияние его не взяло, — своё ядро.
Типичный реальный повод: нестандартная функция потерь или экзотическая нормализация,
которую Inductor разбивает на пять ядер вместо одного. Для собеседования достаточно уметь
сказать, что такое Triton, почему Inductor генерирует именно его и в каком случае вы бы
за него взялись.

> 💬 **На собеседовании.** Спросят: «Что делает `torch.compile` и почему он не всегда ускоряет?»
> Хороший ответ: он превращает динамический граф в статический (Dynamo перехватывает байткод
> и записывает FX-граф), достраивает к нему обратный проход (AOTAutograd) и генерирует
> под получившийся граф слитые Triton-ядра (Inductor). Выигрыш идёт от двух вещей: меньше
> обращений к памяти, потому что цепочки поэлементных операций считаются за один проход,
> и меньше накладных расходов на запуск ядер. Значит, он помогает там, где время уходило
> на мелкие memory-bound ядра, и почти ничего не даёт, если время в больших матмулах —
> там уже cuBLAS. Ломается на разрывах графа (`print`, `.item()`, ветвления по значениям)
> и на динамических формах — каждая новая форма это новая компиляция. Диагностика:
> `TORCH_LOGS="graph_breaks,recompiles"` и `torch._dynamo.explain`.
> Провал: «это JIT, он ускоряет код» — не объясняет ни источник выигрыша, ни причины отказов.

## 13. Воспроизводимость

Начнём с честного утверждения: **полная битовая воспроизводимость в глубоком обучении
недостижима** между разными версиями PyTorch/CUDA, разными GPU и разным числом устройств.
Достижима — воспроизводимость в фиксированном окружении, и её достаточно для отладки
и для сравнения экспериментов.

Что нужно зафиксировать:

```python
import os
import random
import numpy as np
import torch


def set_seed(seed: int = 42, deterministic: bool = True) -> None:
    """Фиксируем все генераторы. Вызывать ДО создания модели и DataLoader."""
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)              # покрывает и CPU, и все видимые CUDA-устройства

    if deterministic:
        # некоторые cuBLAS-ядра недетерминированы без этой переменной;
        # выставлять её надо ДО первого CUDA-вызова, поэтому лучше — в окружении процесса
        os.environ.setdefault("CUBLAS_WORKSPACE_CONFIG", ":4096:8")
        torch.use_deterministic_algorithms(True)   # бросит ошибку на недетерминированной операции
        torch.backends.cudnn.deterministic = True
        torch.backends.cudnn.benchmark = False     # автотюнер выбирает разные ядра — это шум


def seed_worker(worker_id: int) -> None:
    """DataLoader пересевает torch-генератор в воркере, но НЕ numpy и НЕ random."""
    worker_seed = torch.initial_seed() % 2 ** 32
    np.random.seed(worker_seed)
    random.seed(worker_seed)


g = torch.Generator()
g.manual_seed(42)
loader = torch.utils.data.DataLoader(
    dataset, batch_size=32, shuffle=True, num_workers=4,
    worker_init_fn=seed_worker,   # чинит одинаковые аугментации во всех воркерах
    generator=g,                  # фиксирует порядок перемешивания
)
```

Что здесь важно понимать, а не просто скопировать:

- **`torch.backends.cudnn.benchmark`**. При `True` cuDNN на первом вызове перебирает несколько
  алгоритмов свёртки и выбирает быстрейший. Это даёт реальное ускорение, если формы входа
  постоянны, — и делает результат невоспроизводимым. При переменных формах вдобавок вредит:
  автотюнинг запускается заново на каждую новую форму. Правило: `benchmark=True`
  для продакшен-обучения с фиксированными формами, `False` для отладки и воспроизводимости.
- **`use_deterministic_algorithms(True)`** не «делает всё детерминированным», а **запрещает**
  недетерминированные операции: если в модели есть, например, `scatter_add` на CUDA
  (он использует атомарные сложения, порядок которых не определён), вы получите явную ошибку.
  Это полезно: лучше узнать о недетерминизме, чем гадать. Ценой может быть замедление —
  детерминированные варианты ядер иногда медленнее.
- **Порядок редукции в float неассоциативен**: $(a+b)+c \ne a+(b+c)$ в арифметике
  с плавающей точкой. Поэтому изменение числа GPU или размера батча меняет результат
  даже при одинаковых сидах — и это нормально, а не баг.

Что фиксировать в реальном проекте, если гнаться за битовой идентичностью не нужно:
сид для **разбиения данных** (иначе сравнение экспериментов бессмысленно), сид для
**инициализации весов** (иначе разброс качества между запусками спутается с эффектом
изменений), версии библиотек и данных. Разброс качества между сидами полезно измерить один раз:
если ваш «прирост +0,3 %» меньше межсидового разброса, прироста нет. Подробнее об этом —
в [главе про воспроизводимость и трекинг](../07-mlops/02-reproducibility-and-tracking.md).

## 14. Проверь себя

<details>
<summary><b>🌱 Вопрос.</b> Зачем нужен optimizer.zero_grad() и что будет, если его забыть?</summary>

**Короткий ответ.** PyTorch **накапливает** градиенты в `.grad`, а не перезаписывает.
Без обнуления на шаге $t$ в градиенте окажется сумма градиентов всех предыдущих батчей,
эффективный шаг будет расти, и обучение расходится.

**Развёрнуто.** Накопление — сознательное дизайнерское решение: оно нужно, чтобы складывать
градиенты нескольких лоссов, чтобы обучать RNN (один параметр участвует на всех шагах)
и чтобы эмулировать большой батч через gradient accumulation. Флаг `set_to_none=True`
(по умолчанию с версии 2.0) вместо записи нулей освобождает тензоры — чуть быстрее и экономит
память; побочный эффект — `param.grad` становится `None`, что надо учитывать, если вы читаете
градиенты вручную. Диагностика забытого обнуления: логировать возвращаемое значение
`clip_grad_norm_` — оно будет монотонно расти.

**Чего ждёт интервьюер:** понимания, что накопление — фича, а не баг, и что вы можете назвать
сценарии, где оно нужно.

**Провал:** «чтобы градиенты не путались» без механизма.
</details>

<details>
<summary><b>🎯 Вопрос.</b> Что именно делает model.eval()? Заменяет ли он torch.no_grad()?</summary>

**Короткий ответ.** Проставляет флаг `self.training = False` всем подмодулям. Реагируют на него
Dropout (становится тождественным) и BatchNorm (переходит на накопленные статистики и перестаёт
их обновлять). Градиенты он не выключает — `no_grad()` нужен отдельно.

**Развёрнуто.** LayerNorm, RMSNorm, GroupNorm, свёртки и линейные слои от режима не зависят.
На валидации нужны оба вызова: без `eval()` предсказания зашумлены dropout-ом и, что хуже,
BatchNorm обновит running-статистики валидационными данными — это утечка; без `no_grad()`
строится граф, память расходуется на активации всех слоёв, легко получить OOM.
Симметричная ошибка — забыть `model.train()` обратно, после чего остаток обучения идёт
без регуляризации.

**Чего ждёт интервьюер:** чёткого разделения «режим слоёв» и «построение графа». Вопрос
задают почти на каждом собеседовании, где есть PyTorch.

**Провал:** «eval отключает градиенты и dropout».
</details>

<details>
<summary><b>🎯 Вопрос.</b> В цикле обучения написано `total_loss += loss`. Что произойдёт?</summary>

**Короткий ответ.** Утечка памяти: `loss` — тензор со ссылкой на весь граф вычислений батча,
и суммирование удерживает графы всех итераций. К концу эпохи — OOM.

**Развёрнуто.** Каждый тензор с `requires_grad=True` держит `grad_fn`, а тот — ссылки
на сохранённые активации, нужные для backward. Обычно после `backward()` граф освобождается,
но здесь на него остаётся внешняя ссылка. Правильно: `total_loss += loss.item()`
(вернёт число Python) или `loss.detach()` (вернёт тензор без графа). Та же ошибка встречается
при сборе предсказаний: `preds.append(logits)` вместо `preds.append(logits.detach().cpu())`.
Оборотная сторона: `.item()` синхронизирует CPU и GPU, поэтому вызывать его сотни раз за батч
не стоит.

**Чего ждёт интервьюер:** что вы понимаете, что тензор — это не число, и что граф держится
ссылками.

**Провал:** «ничего, просто сложатся значения».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Как выбрать num_workers? Что даёт pin_memory?</summary>

**Короткий ответ.** `num_workers` подбирается замером: начать с числа физических ядер
(делённого на число процессов обучения) и увеличивать, пока время эпохи падает. `pin_memory=True`
кладёт батч в закреплённую память, откуда GPU умеет копировать асинхронно; работает только
в паре с `non_blocking=True` при `.to(device)`.

**Развёрнуто.** Воркеры — отдельные процессы (GIL обходится), каждый готовит `prefetch_factor`
батчей вперёд. Слишком много воркеров вредит: растёт память (каждый — копия процесса),
растут накладные расходы на сериализацию батчей и нагрузка на диск. Отдельная ловушка —
хранение данных в питоновских списках: из-за счётчиков ссылок copy-on-write не работает
и память умножается на число воркеров; данные надо держать в numpy/torch. Проверка гипотезы
«упираюсь в данные»: прогнать N шагов на одном заранее загруженном батче и сравнить время.

**Чего ждёт интервьюер:** что вы измеряете, а не подставляете магическое число, и знаете
про связку `pin_memory` + `non_blocking`.

**Провал:** «ставлю 4, так везде пишут».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Чем detach() отличается от no_grad() и от requires_grad_(False)?</summary>

**Короткий ответ.** `detach()` — про **один тензор**: копия без связи с графом. `no_grad()` —
про **область кода**: внутри неё граф не строится вообще. `requires_grad_(False)` —
про **параметр**: он перестаёт получать градиент, то есть замораживается.

**Развёрнуто.** Практические сценарии различаются. `detach()`: усечённый BPTT
(`h = h.detach()`), логирование, target-сеть в RL. `no_grad()`: валидация, инференс, ручное
обновление весов (без него PyTorch запретит in-place изменение листа). `requires_grad_(False)`:
заморозка backbone при дообучении — заодно снижает память, потому что для замороженных ветвей
не нужно хранить промежуточные активации (при условии, что вся ветвь заморожена).
`inference_mode()` — более агрессивный вариант `no_grad()`: дополнительно отключает
версионирование тензоров, поэтому такие тензоры нельзя потом использовать в autograd.
Отдельно: `model.eval()` не относится к этому списку вообще, он про режим слоёв.

**Чего ждёт интервьюер:** что вы не сваливаете четыре механизма в один.

**Провал:** «всё это отключает градиенты».
</details>

<details>
<summary><b>🎯 Вопрос.</b> `pred` имеет форму (32,), `target` — (32, 1). Что вернёт `pred - target` и чем это опасно?</summary>

**Короткий ответ.** Тензор $(32, 32)$: broadcasting выровнял формы справа и растянул обе оси.
Лосс посчитается по 1024 попарным разностям вместо 32 — молча и без ошибок.

**Развёрнуто.** Правило broadcasting: формы выравниваются с конца, размеры должны совпадать
либо быть равны 1. Здесь $(32,) \to (1, 32)$ и $(32,1)$ дают $(32,32)$. Обучение пойдёт,
градиент будет от другой функции, модель начнёт стягивать предсказания к среднему таргету.
Защита: ассерт `pred.shape == target.shape` в начале лосса; `target.squeeze(-1)` или
`pred.unsqueeze(-1)` явно. Встроенные лоссы PyTorch выдают `UserWarning`, но в логах обучения
он теряется.

**Чего ждёт интервьюер:** что вы знаете правило и, главное, что рефлекторно проверяете формы.
Это вопрос про инженерную дисциплину, а не про API.

**Провал:** «ошибку размерности».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Обучение медленное, GPU загружена на 25 %. Как искать причину?</summary>

**Короткий ответ.** Разделить «данные» и «вычисления»: прогнать N шагов на одном заранее
загруженном батче. Если стало быстро — узкое место в пайплайне данных; если нет — искать
синхронизации и мелкие ядра профайлером.

**Развёрнуто.** Дальше по веткам. Данные: увеличить `num_workers`, включить `pin_memory` +
`non_blocking`, вынести тяжёлый препроцессинг из `__getitem__` в офлайн, сменить формат
хранения (много мелких файлов — почти всегда проблема). Вычисления: `torch.profiler`
с сортировкой по `self_cuda_time_total`, поиск `aten::copy_` и `cudaStreamSynchronize` в топе,
просмотр трассы на предмет дыр между ядрами. Частые находки: `.item()` внутри батча,
печать метрик каждый шаг, ассерты на значениях тензоров, слишком маленький батч
(ядра не насыщают GPU). Дальше — mixed precision, `torch.compile`, увеличение батча
с корректировкой LR.

**Чего ждёт интервьюер:** протокола, а не списка советов. И упоминания
`torch.cuda.synchronize()` при замерах — без него все числа неверны.

**Провал:** сразу предлагать более мощную GPU.
</details>

<details>
<summary><b>🎯 Вопрос.</b> Что сохранять в чекпоинте, чтобы корректно продолжить обучение?</summary>

**Короткий ответ.** `state_dict` модели, состояние оптимизатора, состояние планировщика LR,
номер эпохи/шага, состояние `GradScaler` при mixed precision, конфиг и (для строгой
воспроизводимости) состояния генераторов случайных чисел.

**Развёрнуто.** Самая частая ошибка — сохранить только веса. Тогда при рестарте обнуляются
моменты Adam ($m$ и $v$), и первые сотни шагов модель фактически ломается: лосс подскакивает.
Вторая — не сохранить планировщик, из-за чего LR откатывается к начальному. Сохранять модель
целиком (`torch.save(model, ...)`) не стоит: pickle привязывает файл к структуре модулей
проекта, переименование ломает загрузку. При загрузке — `map_location="cpu"` и явный
`weights_only=True`; при `strict=False` обязательно проверять список пропущенных ключей.

**Чего ждёт интервьюер:** опыта реального возобновления обучения после сбоя. Для ролей,
связанных с большими моделями, это обязательный вопрос.

**Провал:** «`torch.save(model.state_dict())`» и всё.
</details>

<details>
<summary><b>🎯 Вопрос.</b> Вы положили слои в обычный питоновский список `self.layers = [...]`. Что сломается?</summary>

**Короткий ответ.** PyTorch не узнает об этих модулях: они не попадут в `model.parameters()`
(оптимизатор их не обновит), не попадут в `state_dict` (не сохранятся и не загрузятся)
и не переедут на GPU при `model.to(device)`. При этом forward отработает и обучение пойдёт —
просто часть сети навсегда останется со случайными весами.

**Развёрнуто.** `nn.Module` находит вложенные модули и параметры через перехват `__setattr__`:
регистрируются только объекты типов `nn.Parameter`, `nn.Module` и зарегистрированные буферы.
Обычный список — не модуль, его содержимое невидимо. Правильные контейнеры: `nn.ModuleList`,
`nn.ModuleDict`, `nn.Sequential`. Та же логика у тензоров: обучаемый тензор надо оборачивать
в `nn.Parameter`, а необучаемое состояние (маски, running-статистики, таблицы частот RoPE) —
регистрировать через `register_buffer`, иначе оно останется на CPU. Практическая защита —
ассерт на число параметров: расхождение с расчётом мгновенно вскрывает потерю.

**Чего ждёт интервьюер:** понимания, что баг **молчаливый** — ни ошибки, ни предупреждения,
только необъяснимо плохое качество. Такие вопросы задают, чтобы отличить писавших модели
от собиравших их из готовых кусков.

**Провал:** «будет ошибка» — её не будет, и в этом вся проблема.
</details>

<details>
<summary><b>🧠 Вопрос.</b> Как добиться воспроизводимости обучения и почему полной воспроизводимости не бывает?</summary>

**Короткий ответ.** Зафиксировать сиды (`random`, `numpy`, `torch`), генератор DataLoader
и `worker_init_fn`, включить `use_deterministic_algorithms(True)`, `cudnn.deterministic=True`,
`cudnn.benchmark=False`, выставить `CUBLAS_WORKSPACE_CONFIG`. Полной не бывает, потому что
арифметика с плавающей точкой неассоциативна, а порядок редукций зависит от железа,
версии библиотек и числа устройств.

**Развёрнуто.** Отдельно стоит отметить, что `torch.manual_seed` покрывает и CUDA, а вот
numpy и `random` в воркерах DataLoader **не пересеваются** — отсюда классический баг
с одинаковыми аугментациями во всех воркерах. `cudnn.benchmark=True` даёт ускорение
при фиксированных формах, но выбирает алгоритм эмпирически и ломает воспроизводимость.
`use_deterministic_algorithms(True)` не «включает детерминизм», а бросает исключение
на недетерминированной операции — это диагностический инструмент. Практический вывод:
гнаться надо не за битовой идентичностью, а за фиксацией сплита и инициализации плюс
за измерением межсидового разброса метрики — иначе невозможно отличить реальный прирост
от шума.

**Чего ждёт интервьюер:** зрелого ответа «полной воспроизводимости нет, и вот что делать
вместо этого».

**Провал:** «`torch.manual_seed(42)` — и всё воспроизводимо».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Память растёт от итерации к итерации, хотя батч не меняется. Что проверять?</summary>

**Короткий ответ.** Что-то с графом переживает итерацию: накопление `loss` без `.item()`,
сбор предсказаний без `detach()`, скрытое состояние RNN без `detach()`, тензор, положенный
в атрибут модуля или в словарь метрик.

**Развёрнуто.** Порядок диагностики: печатать `torch.cuda.memory_allocated()` в конце каждой
итерации — линейный рост подтверждает удержание. Дальше искать все места, где тензор покидает
тело цикла. Отдельно надо различать **утечку** и **фрагментацию**: если `memory_allocated`
стабилен, а `memory_reserved` велик и OOM всё равно случается — это фрагментация кэширующего
аллокатора, типичная при переменных длинах последовательностей; лечится бакетингом по длине
или `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`. `torch.cuda.empty_cache()` в цикле —
не лечение, а маскировка симптома, к тому же дорогая.

**Чего ждёт интервьюер:** различения утечки и фрагментации; второе почти никто не называет.

**Провал:** «вызываю `empty_cache()` каждые сто шагов».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Почему на валидации нужен shuffle=False, а на обучении shuffle=True?</summary>

**Короткий ответ.** На обучении перемешивание разрушает корреляцию внутри батча (данные часто
лежат отсортированными по классу или дате), без него градиенты батчей смещены и обучение идёт
рывками. На валидации порядок не влияет на среднюю метрику, но фиксированный порядок делает
логи и разбор примеров сопоставимыми между запусками, а с `drop_last=True` перемешивание
ещё и теряет часть данных.

**Развёрнуто.** Формально SGD предполагает, что батч — независимая выборка из обучающего
распределения; отсортированные данные это предположение нарушают грубо (батч из одного класса
даёт градиент, тянущий модель к этому классу). На валидации `drop_last` должен быть `False`,
иначе метрика считается не по всему набору, а перемешивание вредно ещё и тем, что при
неполном последнем батче взвешивание по батчам даёт слегка смещённую оценку — метрики надо
агрегировать по числу объектов, а не усреднять по батчам.

**Чего ждёт интервьюер:** понимания, что перемешивание нужно там, где считается градиент,
и что усреднение метрик по батчам — отдельная ловушка.

**Провал:** «shuffle всегда True, так безопаснее».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Обернули модель в torch.compile — ускорения нет. Ваши действия?</summary>

**Короткий ответ.** Сначала убедиться, что замер честный (прогрев, одинаковые формы, замер
со второй эпохи), потом посмотреть `TORCH_LOGS="graph_breaks,recompiles"` и
`torch._dynamo.explain`. Две самые частые причины — разрывы графа и перекомпиляции
на новых формах. Третья, законная, — время и так уходило в большие матмулы, где слипать нечего.

**Развёрнуто.** `torch.compile` даёт выигрыш из двух источников: слияние цепочек поэлементных
операций (меньше обращений к HBM) и снижение накладных расходов на запуск ядер, вплоть
до CUDA-графов в режиме `reduce-overhead`. Значит, ожидаемое ускорение примерно равно доле
времени, которая уходила на мелкие memory-bound ядра и на запуски; если профиль показывает,
что 80 % времени в GEMM, честный ответ — компиляция здесь почти ничего не даст. Разрывы графа
возникают на `print`, `.item()`, ветвлениях по значениям тензора, обращениях к внешним
объектам: `graph_count` больше двух — уже плохой знак. Динамические формы вызывают
перекомпиляцию на каждую новую длину; лечится паддингом к фиксированному набору длин
или `dynamic=True`. И отдельная ловушка замера: первая итерация — это сама компиляция,
20–120 секунд.

**Чего ждёт интервьюер:** что вы понимаете механизм (граф, слияние, запуски), а не относитесь
к компиляции как к волшебному декоратору.

**Провал:** «наверное, моя модель не поддерживается» без единой попытки посмотреть логи.
</details>

<details>
<summary><b>🎯 Вопрос.</b> В трассе профайлера видны дыры на дорожке GPU, а в таблице операций ничего тяжёлого нет. Где искать?</summary>

**Короткий ответ.** На стороне Python. `torch.profiler` видит только операции PyTorch; дыра
означает, что карта ждёт, пока хост что-то делает своими силами. Дальше — `py-spy record`
на живом процессе с флагом `--subprocesses`, чтобы захватить воркеров DataLoader.

**Развёрнуто.** Типичные находки: тяжёлый препроцессинг в `__getitem__` (декодирование
картинок, токенизация на чистом Python, `pd.DataFrame` на объект), медленный `collate_fn`,
чтение множества мелких файлов, синхронизации `.item()`/`.cpu()` в цикле логирования.
Быстрая проверка гипотезы вообще без профайлера — прогнать N шагов на одном заранее
загруженном батче: если время резко упало, виноват пайплайн данных. Полезно помнить и второе
применение `py-spy`: `py-spy dump` по каждому процессу — самый быстрый способ понять, где
завис распределённый запуск, когда ошибок нет, а прогресса тоже нет.

**Чего ждёт интервьюер:** понимания, что у профилирования две половины — операции и Python, —
и что для второй нужен отдельный инструмент.

**Провал:** «увеличу батч» — при голодающей карте больший батч только увеличит паузы.
</details>

падает сразу.
*Критерий: вы можете назвать, к чему сходится модель при таком баге в задаче регрессии,
и объяснить почему.*

**Задача 4. Профилирование (60 минут).**
Возьмите обучение с `num_workers=0` и тяжёлым препроцессингом в `__getitem__`. Замерьте время
эпохи, затем примените по шагам: `num_workers=8`, `pin_memory=True` + `non_blocking=True`,
вынос препроцессинга в офлайн.
*Критерий: у вас есть таблица «изменение → время эпохи → утилизация GPU» и вы можете объяснить,
почему очередной шаг дал (или не дал) выигрыш. Дополнительно: запустите `torch.profiler`,
найдите в отчёте `cudaStreamSynchronize` и объясните, откуда он.*

**Задача 5. Воспроизводимость (45 минут).**
Обучите одну и ту же модель пять раз с сидами 0–4 и запишите валидационную метрику.
*Критерий: вы знаете стандартное отклонение метрики между сидами для своей задачи. Дальше
проверьте: даёт ли ваша любимая «улучшайзинг»-техника прирост больше этого разброса?
Затем включите `set_seed` со всеми флагами детерминизма и убедитесь, что два запуска с одним
сидом дают идентичные лоссы на первых 10 шагах.*

**Задача 6. Утечка памяти (30 минут).**
Напишите цикл, который течёт (сохраняет `logits` в список без `detach`), и найдите утечку
по `torch.cuda.memory_allocated()`.
*Критерий: вы построили график памяти по итерациям, увидели линейный рост, локализовали строку
и подтвердили, что после `detach().cpu()` график стал плоским. Затем повторите ту же охоту
через Memory Snapshot из [§11](#11-профилирование-где-на-самом-деле-уходит-время): включите
`_record_memory_history`, снимите дамп и найдите удерживающий стек по картинке — на реальном
проекте это будет ваш основной инструмент.*

**Задача 7. Три замера одного и того же (40 минут).**
Возьмите один forward-проход и измерьте его тремя способами: `time.perf_counter()` без
синхронизации, `time.perf_counter()` с `torch.cuda.synchronize()` и через
`torch.cuda.Event`. Повторите для двух режимов: батч 1 и батч 256.
*Критерий: у вас есть таблица из шести чисел, и вы можете объяснить каждое расхождение.
В частности: при батче 1 время постановки в очередь сопоставимо со временем GPU (модель
launch-bound), при батче 256 — на порядки меньше. Дополнительно проверьте, что перенос
`synchronize()` внутрь цикла ухудшает результат, и объясните почему.*

**Задача 8. Охота на разрывы графа (60 минут).**
Возьмите свою модель, вставьте в `forward` `print(x.mean().item())` и скомпилируйте её.
Запустите с `TORCH_LOGS="graph_breaks,recompiles"` и посчитайте графы через
`torch._dynamo.explain`. Затем уберите строку и повторите. Отдельно прогоните модель
на входах пяти разных длин.
*Критерий: вы видите, как одна строка увеличивает число графов, и умеете прочитать причину
разрыва в логе; вы наблюдали перекомпиляцию на каждой новой форме и измерили её стоимость
в секундах; вы сравнили честное ускорение (с прогревом, на фиксированных формах) для
`mode="default"` и `mode="reduce-overhead"` и знаете, какой из них выигрывает на вашей модели.*

## 16. Что читать дальше

- [PyTorch: Autograd mechanics](https://pytorch.org/docs/stable/notes/autograd.html) —
  официальная заметка о том, как устроен граф, что такое leaf-тензоры и как работают
  in-place операции. Короткая и обязательная.
- [PyTorch: Broadcasting semantics](https://pytorch.org/docs/stable/notes/broadcasting.html) —
  формальные правила из [§3](#3-broadcasting-и-как-он-молча-ломает-лосс). Прочитать один раз внимательно дешевле, чем неделю искать баг.
- [PyTorch: CUDA semantics](https://pytorch.org/docs/stable/notes/cuda.html) —
  асинхронность, потоки, закреплённая память, кэширующий аллокатор. Это фундамент для [§8](#8-устройства-и-перемещение-данных) и [§11](#11-профилирование-где-на-самом-деле-уходит-время).
- [PyTorch: Reproducibility](https://pytorch.org/docs/stable/notes/randomness.html) —
  первоисточник для [§13](#13-воспроизводимость), включая полный список недетерминированных операций.
- [PyTorch: Performance Tuning Guide](https://pytorch.org/tutorials/recipes/recipes/tuning_guide.html) —
  чек-лист ускорения обучения: от `channels_last` до слияния операций. Прогоняйте по нему
  каждый новый проект.
- [PyTorch Profiler recipe](https://pytorch.org/tutorials/recipes/recipes/profiler_recipe.html) —
  практическое руководство по `torch.profiler` с разбором вывода.
- [PyTorch Blog: Understanding GPU Memory](https://pytorch.org/blog/understanding-gpu-memory-1/) —
  серия постов о Memory Snapshot и визуализаторе: как читать картинку аллокаций и как искать
  по ней утечки и фрагментацию. Основа для [§11](#11-профилирование-где-на-самом-деле-уходит-время).
- [Introduction to torch.compile](https://pytorch.org/tutorials/intermediate/torch_compile_tutorial.html)
  и [torch.compile Troubleshooting](https://pytorch.org/docs/stable/torch.compiler_troubleshooting.html) —
  первый объясняет, что происходит внутри, второй — как читать разрывы графа
  и перекомпиляции. Второй документ пригодится в первый же день работы с компиляцией.
- [Triton](https://triton-lang.org/) — документация языка, на котором Inductor генерирует ядра.
  Начинать стоит с туториала про векторное сложение и слитый softmax: два примера дают
  ощущение того, чем блочная модель отличается от CUDA.
- [py-spy](https://github.com/benfred/py-spy) — сэмплирующий профайлер для живого процесса.
  Осваивается за десять минут и закрывает ровно ту половину профилирования, которой
  `torch.profiler` не видит.
- [Karpathy A. «A Recipe for Training Neural Networks» (2019)](https://karpathy.github.io/2019/04/25/recipe/) —
  лучший текст о методологии отладки обучения: почему начинать надо с переобучения одного батча
  и почему нельзя менять пять вещей сразу. Читать целиком, желательно дважды.
- [Karpathy A. «nanoGPT»](https://github.com/karpathy/nanoGPT) —
  референсный обучающий цикл на 300 строк со всеми практиками из этой главы: AMP,
  gradient accumulation, DDP, компиляция. Отличный образец того, как выглядит
  production-grade учебный код.
- [PyTorch Examples](https://github.com/pytorch/examples) —
  официальные примеры (ImageNet, языковая модель, DDP). Полезны как эталон структуры проекта.
