## 1. Интуиция: почему данные ломаются чаще моделей

Модель после обучения — это замороженный файл. Он не меняется сам. Данные меняются постоянно,
и меняет их не ваша команда.

Посчитаем, сколько людей может сломать вход вашей модели. Типичный набор признаков собирается
из 5–8 источников: события фронтенда, транзакции из биллинга, каталог товаров, справочник
регионов, внешний обогатитель (гео, кредитная история), агрегаты из хранилища. У каждого
источника своя команда, свой релизный цикл и свои приоритеты, в которых ваша модель
не значится вообще. Если каждая из шести команд делает по одному релизу в неделю
с вероятностью 2% сломать контракт, то вероятность, что за квартал ваш вход останется цел:

$$
P = (1 - 0.02)^{6 \cdot 13} \approx 0.21
$$

где 0.02 — вероятность ломающего изменения в одном релизе, 6 — число источников,
13 — число недель в квартале. То есть с вероятностью около 80% за квартал что-нибудь
да сломается. Это не пессимизм, это арифметика.

Хуже того: **ломающее изменение почти никогда не выглядит как ошибка**. Никто не удаляет
колонку — колонку переименовывают, добавляют новую и постепенно мигрируют. Никто не портит
тип — просто в поле `price` теперь может прийти строка `"1 299,00"` из нового кассового
интерфейса. Никто не удаляет данные — просто джоба стала падать по понедельникам, и таблица
не обновляется, а вы читаете вчерашний снепшот, не зная об этом.

Отсюда позиция, из которой пишется вся эта глава: **входные данные — это внешний недоверенный
интерфейс, и относиться к нему надо как к пользовательскому вводу в веб-сервисе.** Вы
не доверяете телу HTTP-запроса — вы его валидируете. С таблицей признаков ровно так же.

> 💬 **На собеседовании.** Спросят: «Что чаще ломается в проде — модель или данные?»
> Хороший ответ: «Данные, с большим отрывом. Модель — замороженный артефакт, она не меняется
> без нашего деплоя. Данные меняются каждый день, и меняют их команды, которые про нашу модель
> не знают. При этом поломка данных обычно не даёт исключения: тип остаётся числом, схема
> формально валидна, сервис отвечает 200. Поэтому я строю валидацию входа как контракт:
> схема плюс семантика (единицы измерения, допустимые диапазоны, обязательность),
> плюс SLA на свежесть и объём, плюс политика изменений с окном депрекации. И ставлю проверки
> в четырёх местах пайплайна, потому что на входе, перед обучением и перед инференсом
> проверяется разное и цена остановки разная».
> Плохой ответ: «настроим алерты на метрики модели» — к моменту, когда просядет метрика,
> плохие данные уже месяц в проде.

## 2. Контракт данных

**Контракт данных** (data contract) — явное соглашение между поставщиком и потребителем
данных о том, что именно передаётся, с какими гарантиями и как это разрешено менять.
Ключевое слово — «явное»: контракт лежит в репозитории, версионируется и проверяется
автоматически, иначе это не контракт, а устная договорённость, которая живёт до увольнения
одного из участников.

Схема (список колонок и типов) — только первая треть контракта. Полный контракт содержит
четыре блока.

**Блок 1. Структура.** Колонки, типы, обязательность, первичный ключ, внешние ключи.

**Блок 2. Семантика.** То, чего нет в типе и что ломается тише всего: единицы измерения
(рубли или копейки, метры или километры), часовой пояс временных меток, кодировка категорий
(ISO-3166 alpha-2 или внутренний справочник), способ представления пропуска
(именно `NULL`, а не `-1` и не `0`), гранулярность строки (одна строка = один заказ
или один товар в заказе).

**Блок 3. Гарантии эксплуатации.** Свежесть (к какому времени данные за день готовы),
объём (ожидаемое число строк и допустимый разброс), полнота (максимальная доля пропусков
по каждой колонке), уникальность ключа, режим доставки (at-least-once или exactly-once —
от этого зависит, ждать ли дубли).

**Блок 4. Политика изменений.** Что считается ломающим изменением, за сколько дней
предупреждают, как долго живёт старая версия. Практичный дефолт: добавление необязательной
колонки — не ломающее, можно без предупреждения; удаление, переименование, смена типа,
смена единиц или семантики — ломающее, окно депрекации 30 дней, старая и новая версии
живут параллельно.

```yaml
# contracts/user_features_daily.yaml — контракт лежит в git рядом с кодом пайплайна
name: user_features_daily
version: 2.1.0            # major меняется только при ломающем изменении
owner: team-billing
consumers: [team-ml-risk, team-ml-recsys]

schema:
  - name: user_id
    type: string
    nullable: false
    primary_key: true
  - name: event_date
    type: date
    nullable: false
    semantics: "календарная дата в Europe/Moscow, партиция таблицы"
  - name: monthly_income
    type: decimal(12,2)
    nullable: true
    unit: RUB                       # <- ЕДИНИЦЫ ИЗМЕРЕНИЯ В КОНТРАКТЕ, ЭТО НЕ ФОРМАЛЬНОСТЬ
    range: [0, 10000000]
    null_means: "доход неизвестен; ЗАПРЕЩЕНО подставлять 0 или -1"
  - name: orders_30d
    type: int
    nullable: false
    range: [0, 5000]
    unit: count
  - name: country
    type: string
    nullable: false
    allowed_values_ref: "dim_country.iso_code"   # ссылочная целостность
  - name: last_login_at
    type: timestamp
    nullable: true
    semantics: "UTC, timezone-aware; naive-таймстемпы недопустимы"

sla:
  freshness: "данные за D готовы к 06:00 UTC дня D+1"
  volume:
    expected_rows_per_day: 12000000
    tolerance_pct: 25             # отклонение больше 25% — инцидент
  completeness:
    monthly_income: 0.35          # до 35% NULL нормально
    orders_30d: 0.0
  duplicates:
    primary_key_dup_rate_max: 0.0
  delivery: at_least_once         # значит дубли ВОЗМОЖНЫ, дедуп на нашей стороне

change_policy:
  non_breaking: ["добавление nullable-колонки"]
  breaking: ["удаление", "переименование", "смена типа", "смена unit", "смена null_means"]
  deprecation_window_days: 30
  notification_channel: "#data-contracts"
```

Главная ценность такого файла — не документация, а то, что из него **генерируются проверки**.
Схема, диапазоны, допустимая доля пропусков и SLA на свежесть — всё это машиночитаемо
и превращается в набор тестов автоматически. Контракт, который не превращается в проверки,
устаревает за два месяца.

> ⚠️ **Типичная ошибка.** Описать контракт только структурно: колонки и типы. Три самые
> дорогие поломки — смена единиц измерения, смена часового пояса и подмена `NULL` дефолтом —
> проходят структурную валидацию без единого замечания. Поле `unit`, `semantics`
> и `null_means` в контракте выглядят как бюрократия ровно до первого инцидента.

## 3. Шесть семейств проверок

Проверки полезно держать в голове как шесть семейств: они покрывают почти все реальные
поломки, и по ним удобно проходить чек-листом.

### 3.1. Полнота (completeness)

Доля пропусков по колонке:

$$
c_j = \frac{1}{n}\sum_{i=1}^{n} \mathbb{1}[x_{ij} = \text{NULL}]
$$

где $n$ — число строк в проверяемой партиции, $x_{ij}$ — значение признака $j$ в строке $i$,
$\mathbb{1}[\cdot]$ — индикатор.

Формулировки, которые надо писать в проверках:

- «`user_id` не содержит `NULL`» — порог 0, жёстко.
- «доля `NULL` в `monthly_income` не выше 35%» — порог из контракта, взятый как исторический
  максимум за 8 недель плюс запас.
- «доля `NULL` в `monthly_income` не выросла больше чем на 5 п.п. относительно среднего
  за прошлые 7 дней» — это важнее абсолютного порога: скачок с 2% до 20% при контрактном
  лимите 35% формально проходит, но означает, что источник наполовину отвалился.

Абсолютный порог ловит катастрофу, относительный — деградацию. Нужны оба.

### 3.2. Уникальность (uniqueness)

$$
d = 1 - \frac{|\{\text{уникальные ключи}\}|}{n}
$$

где $d$ — доля дублей, $n$ — число строк.

- «`user_id` уникален в партиции за день» — порог $d = 0$.
- «пара (`user_id`, `event_date`) уникальна» — для таблиц с историей.
- «доля дублей по бизнес-ключу события (`event_id`) не выше 0.1%» — если доставка
  at-least-once, полный ноль недостижим, и порог должен это отражать.

Отдельная проверка, которую забывают: **уникальность в справочнике перед джойном**.
Если `dim_product` содержит дубли по `product_id`, то `LEFT JOIN` размножит строки факта —
см. §8.2.

### 3.3. Диапазоны и допустимые значения (validity)

- «`orders_30d` лежит в `[0, 5000]`, доля нарушений 0%».
- «`monthly_income` лежит в `[0, 10 000 000]`, доля нарушений не выше 0.01%» — небольшой
  допуск нужен, потому что реальные выбросы существуют.
- «`age` лежит в `[14, 100]`» — обратите внимание, что 0 и 1900 — типичные значения-заглушки,
  и именно их эта проверка ловит.
- «`country` принимает значения только из справочника ISO-3166 alpha-2; доля новых
  категорий не выше 0.5%».

Как выбирать границы: **не по здравому смыслу, а по обучающей выборке**. Возьмите
1-й и 99-й перцентили обучающих данных, расширьте в 1.5–2 раза, зафиксируйте. Логика в том,
что модель видела именно этот диапазон; всё сильно за его пределами — территория,
где предсказание не имеет гарантий.

### 3.4. Распределения (distribution)

Это мостик к [следующей главе про дрифт](03-drift-detection.md), но часть проверок относится
именно к качеству, а не к дрифту, потому что ловит не изменение мира, а поломку.

- «среднее `monthly_income` отклонилось от среднего за прошлые 7 дней не более чем в 1.5 раза» —
  грубо, но ловит смену единиц измерения мгновенно (деление на 1000 даёт отклонение в 1000 раз).
- «доля нулей в `orders_30d` не выше 60%» — ловит подмену `NULL` нулём на стороне источника.
- «число уникальных значений `city` не изменилось более чем на 20%» — ловит смену кодировки
  справочника.
- «медиана и 95-й перцентиль в пределах ±30% от скользящего базлайна».

Практическое замечание: проверки распределений почти всегда должны быть **предупреждениями**,
а не стопами — они шумят на реальных сезонных изменениях. Исключение — проверка на смену
порядка величины (отклонение в 10+ раз), которая почти всегда означает поломку.

### 3.5. Ссылочная целостность (referential integrity)

Доля «сирот» — строк с ключом, отсутствующим в справочнике:

$$
o = \frac{|\{i: k_i \notin K_{\text{ref}}\}|}{n}
$$

где $k_i$ — значение внешнего ключа в строке $i$, $K_{\text{ref}}$ — множество ключей
в справочнике, $n$ — число строк.

- «все `product_id` из фактов присутствуют в `dim_product`; доля сирот не выше 0.1%».
- «все `country` присутствуют в `dim_country`».
- «после `LEFT JOIN` доля `NULL` в колонках справочника не выше 0.5%».

Последняя формулировка — самая полезная в ML-пайплайне: она ловит момент, когда справочник
не обновился, а факты уже приехали с новыми ключами, и половина признаков молча стала
пропусками.

### 3.6. Свежесть (freshness)

$$
L = t_{\text{сейчас}} - \max_i t_i
$$

где $t_i$ — временная метка события/строки, $L$ — лаг свежести.

- «максимальный `event_time` в таблице не старше 2 часов при часовом интервале обновления».
- «партиция за вчера существует и содержит больше 1 000 000 строк к 06:00 UTC».
- «время последнего успешного запуска DAG не старше 2× периода расписания».

Свежесть — единственная проверка, которую **обязательно** надо делать снаружи, по факту
отсутствия данных. Проверка внутри пайплайна не сработает, если пайплайн не запустился —
а именно это и есть самый частый способ, которым данные протухают. В Prometheus это выглядит
так (метрику выставляет сам пайплайн после успешного завершения):

```promql
# Алерт: таблица не обновлялась дольше двух интервалов
time() - max(feature_table_last_success_timestamp_seconds{table="user_features_daily"}) > 172800
```

## 4. Где ставить проверки и почему в разных местах разные

Соблазн — написать один большой набор проверок и прогонять его везде. Это не работает,
потому что в четырёх точках пайплайна различаются три вещи: **что вообще можно проверить**,
**сколько времени на это есть** и **сколько стоит остановка**.

```mermaid
flowchart LR
    S["Источники"] --> A["① Приём<br/>контракт с источником"]
    A --> T["Трансформации<br/>джойны, агрегаты"]
    T --> B["② После трансформаций<br/>инварианты преобразований"]
    B --> C["③ Перед обучением<br/>максимальная строгость"]
    B --> D["④ Перед инференсом<br/>дёшево и без стопа"]
    C --> M["Модель"]
    M --> D
```

| Точка | Что проверяем | Бюджет времени | Действие при провале |
|---|---|---|---|
| ① Приём (ingestion) | схема, типы, PK-уникальность, свежесть, объём, сырые диапазоны | минуты | жёсткий стоп: не пускаем мусор в хранилище |
| ② После трансформаций | fanout джойнов, дубли после джойна, сходимость сумм, доля сирот, доля новых `NULL` | минуты | жёсткий стоп: ошибка в нашем коде |
| ③ Перед обучением | всё вышеперечисленное + распределения, баланс классов, размер выборки, отсутствие утечек, point-in-time | десятки минут | жёсткий стоп: обучение дешевле переделать, чем выкатывать плохую модель |
| ④ Перед инференсом (онлайн) | только построчно: обязательные поля, типы, диапазоны | 0.5–2 мс на запрос | деградация и метрика, НЕ стоп |

Разберём логику каждой точки.

**① Приём.** Здесь вы разговариваете с чужой командой, и единственный способ удержать
контракт — не принимать данные, его нарушающие. Пропустив битую партицию, вы получите
её в трёх витринах и двух моделях, и разгребать это будет дороже, чем пересчитать
один источник. Здесь проверяется только то, что видно **до** любых преобразований:
структура, типы, ключи, объём, свежесть. Распределения признаков здесь проверять рано —
признаков ещё нет.

**② После трансформаций.** Здесь ловятся ошибки **вашего** кода, а не чужого. Главные
инварианты: число строк изменилось предсказуемо (`LEFT JOIN` не должен увеличивать
число строк — если увеличил, справочник содержит дубли), доля пропусков в присоединённых
колонках не выросла, суммы контрольных величин сходятся с источником. Эти проверки нельзя
поставить в точке ①, потому что там ещё нечего сравнивать.

**③ Перед обучением.** Точка максимальной строгости, потому что здесь стоп почти ничего
не стоит: обучение подождёт четыре часа, и никто не заметит. Именно здесь имеет смысл гонять
дорогие проверки: распределения по всем признакам, корреляция признака с таргетом
подозрительно близкая к 1 (признак утечки), доля позитивного класса, покрытие временного
диапазона, отсутствие строк из будущего относительно точки отсечки. Многие из этих проверок
физически невозможны в точке ④: чтобы посчитать распределение, нужен весь датасет,
а не одна строка.

**④ Перед инференсом.** Здесь всё наоборот: времени 1–2 миллисекунды, контекста — одна
строка, а стоп означает отказ обслуживать пользователя. Поэтому проверки максимально дешёвые
(pydantic-схема, обязательные поля, границы), а реакция — **не отказ, а деградация**: подставить
дефолт, пометить ответ `degraded=true`, инкрементировать счётчик. Агрегированные проверки
для онлайна делаются асинхронно: сервис логирует признаки, отдельная джоба раз в 5–15 минут
считает по логам распределения и сравнивает с обучающими.

```python
# Онлайн-валидация: pydantic-схема на входе сервиса. Дорогих проверок здесь быть не должно.
from pydantic import BaseModel, Field, field_validator

class ScoreRequest(BaseModel):
    model_config = {"extra": "forbid"}   # лишнее поле = нарушение контракта, а не «ну и ладно»

    user_id: str = Field(min_length=1, max_length=64)
    monthly_income: float | None = Field(default=None, ge=0, le=10_000_000)
    orders_30d: int = Field(ge=0, le=5000)
    country: str = Field(min_length=2, max_length=2)

    @field_validator("monthly_income")
    @classmethod
    def _reject_sentinel(cls, v: float | None) -> float | None:
        # Источники любят подменять NULL нулём или -1. Ноль дохода формально валиден,
        # но встречается на порядок реже, чем ошибка источника, поэтому трактуем как пропуск.
        if v is not None and v <= 0:
            return None
        return v
```

> 💬 **На собеседовании.** Спросят: «Где вы поставите проверки качества данных?»
> Хороший ответ: «В четырёх местах, и это разные проверки. На приёме — контракт с источником:
> схема, типы, уникальность ключа, свежесть, объём; действие — жёсткий стоп, потому что
> дешевле не пустить мусор, чем вычищать его из пяти витрин. После трансформаций — инварианты
> моего кода: fanout джойна, дубли, доля новых пропусков; тоже стоп. Перед обучением —
> максимальная строгость, включая распределения и проверки на утечку, потому что остановка
> обучения почти ничего не стоит. Перед онлайн-инференсом — только построчные проверки
> в пределах пары миллисекунд, и реакция не стоп, а деградация с флагом и счётчиком: отказ
> обслуживать пользователя обычно хуже, чем предсказание на дефолтных фичах. Агрегированные
> проверки для онлайна делаю асинхронно по логам признаков».
> Плохой ответ: «прогоним Great Expectations в конце пайплайна» — одна точка не покрывает
> ни ошибок источника, ни ошибок трансформаций, ни онлайн-трафика.

## 5. Своя проверялка на 40 строк

Прежде чем брать фреймворк, полезно увидеть, что внутри. Механика тривиальна: проверка —
это функция, возвращающая наблюдаемое значение, порог и уровень строгости.

```python
# checks.py — минимальный движок проверок. Запускается как есть.
from __future__ import annotations

from dataclasses import dataclass
from typing import Literal

import pandas as pd

Severity = Literal["block", "warn"]


@dataclass
class CheckResult:
    name: str
    passed: bool
    observed: float
    threshold: float
    severity: Severity

    def __str__(self) -> str:
        mark = "OK " if self.passed else ("FAIL" if self.severity == "block" else "WARN")
        return f"[{mark}] {self.name}: observed={self.observed:.6g} threshold={self.threshold:.6g}"


def not_null(df: pd.DataFrame, column: str, max_share: float = 0.0,
             severity: Severity = "block") -> CheckResult:
    observed = float(df[column].isna().mean())
    return CheckResult(f"not_null:{column}", observed <= max_share, observed, max_share, severity)


def unique_key(df: pd.DataFrame, columns: list[str], max_dup_share: float = 0.0,
               severity: Severity = "block") -> CheckResult:
    observed = float(df.duplicated(subset=columns).mean())
    return CheckResult(f"unique:{'+'.join(columns)}", observed <= max_dup_share,
                       observed, max_dup_share, severity)


def in_range(df: pd.DataFrame, column: str, lo: float, hi: float,
             max_violation_share: float = 0.0, severity: Severity = "block") -> CheckResult:
    s = df[column].dropna()
    # Пустая колонка не должна «проходить» проверку молча: это отдельная поломка.
    observed = 1.0 if len(s) == 0 else float(((s < lo) | (s > hi)).mean())
    return CheckResult(f"range:{column}[{lo},{hi}]", observed <= max_violation_share,
                       observed, max_violation_share, severity)


def referential(df: pd.DataFrame, column: str, allowed: set, max_orphan_share: float = 0.0,
                severity: Severity = "block") -> CheckResult:
    observed = float((~df[column].isin(allowed)).mean())
    return CheckResult(f"ref:{column}", observed <= max_orphan_share,
                       observed, max_orphan_share, severity)


def relative_mean_shift(df: pd.DataFrame, column: str, baseline_mean: float,
                        max_ratio: float = 1.5, severity: Severity = "warn") -> CheckResult:
    # Отношение, а не разность: ловит смену единиц измерения (×1000) независимо от масштаба.
    cur = float(df[column].mean())
    observed = max(cur / baseline_mean, baseline_mean / cur) if baseline_mean and cur else float("inf")
    return CheckResult(f"mean_shift:{column}", observed <= max_ratio, observed, max_ratio, severity)


def run(results: list[CheckResult]) -> None:
    for r in results:
        print(r)
    blocking = [r for r in results if not r.passed and r.severity == "block"]
    if blocking:
        raise ValueError(f"Проверки данных провалены: {[r.name for r in blocking]}")
```

Пример применения к дневной партиции:

```python
df = pd.read_parquet("user_features_daily/event_date=2026-07-25/")
countries = set(pd.read_parquet("dim_country/")["iso_code"])

run([
    not_null(df, "user_id"),
    not_null(df, "orders_30d"),
    not_null(df, "monthly_income", max_share=0.35),
    unique_key(df, ["user_id"]),
    in_range(df, "orders_30d", 0, 5000),
    in_range(df, "monthly_income", 0, 10_000_000, max_violation_share=1e-4),
    referential(df, "country", countries, max_orphan_share=1e-3),
    relative_mean_shift(df, "monthly_income", baseline_mean=68_400.0, max_ratio=1.5),
])
```

Этих сорока строк хватает небольшой команде надолго. Фреймворк нужен, когда появляются
требования, которые дороже писать самому: единый отчёт по всем таблицам, история результатов,
автогенерация ожиданий по данным, интеграция с каталогом данных, документация для смежников.

## 6. Great Expectations: рабочий пример

**Great Expectations** (GX) — самый распространённый инструмент валидации данных в питоновом
стеке. Его модель мира: *expectation* — одна проверка, *suite* — набор проверок, *validation
definition* — связка «данные + suite», *checkpoint* — то, что запускается и умеет выполнять
действия по результату.

Код ниже — под **great_expectations 1.x**; в ветке 0.18 API заметно отличается, поэтому
версию всегда фиксируйте в `requirements.txt`.

```python
# validate_daily.py — валидация дневной партиции витрины признаков.
# pip install "great_expectations>=1.0,<2.0"
import great_expectations as gx
import great_expectations.expectations as gxe
import pandas as pd

context = gx.get_context(mode="file")   # состояние и история валидаций лежат на диске

# 1. Источник и ассет. Для pandas-датафрейма батч передаётся в момент запуска.
source = context.data_sources.add_or_update_pandas(name="warehouse")
asset = source.add_dataframe_asset(name="user_features_daily")
batch_definition = asset.add_batch_definition_whole_dataframe("daily_partition")

# 2. Suite — набор ожиданий. Это и есть исполняемая версия контракта из §2.
suite = context.suites.add_or_update(gx.ExpectationSuite(name="user_features_daily"))

suite.add_expectation(gxe.ExpectTableColumnsToMatchSet(
    column_set=["user_id", "event_date", "monthly_income", "orders_30d", "country", "last_login_at"],
    exact_match=True,          # лишняя колонка — тоже нарушение контракта
))
suite.add_expectation(gxe.ExpectTableRowCountToBeBetween(min_value=9_000_000, max_value=15_000_000))
suite.add_expectation(gxe.ExpectColumnValuesToNotBeNull(column="user_id"))
suite.add_expectation(gxe.ExpectColumnValuesToBeUnique(column="user_id"))
suite.add_expectation(gxe.ExpectColumnValuesToNotBeNull(column="orders_30d"))
# mostly=0.65 означает «не более 35% пропусков» — ровно порог из контракта
suite.add_expectation(gxe.ExpectColumnValuesToNotBeNull(column="monthly_income", mostly=0.65))
suite.add_expectation(gxe.ExpectColumnValuesToBeBetween(
    column="monthly_income", min_value=0, max_value=10_000_000, mostly=0.9999,
))
suite.add_expectation(gxe.ExpectColumnValuesToBeBetween(column="orders_30d", min_value=0, max_value=5000))
suite.add_expectation(gxe.ExpectColumnValuesToBeInSet(
    column="country", value_set=["RU", "KZ", "BY", "AM", "UZ", "GE"], mostly=0.995,
))
# Ловит смену единиц измерения: базлайн — среднее за 8 предыдущих недель
suite.add_expectation(gxe.ExpectColumnMeanToBeBetween(
    column="monthly_income", min_value=45_000, max_value=95_000,
))

# 3. Validation definition + checkpoint.
validation = context.validation_definitions.add_or_update(
    gx.ValidationDefinition(name="daily", data=batch_definition, suite=suite)
)
checkpoint = context.checkpoints.add_or_update(
    gx.Checkpoint(name="daily_cp", validation_definitions=[validation])
)

df = pd.read_parquet("s3://warehouse/user_features_daily/event_date=2026-07-25/")
result = checkpoint.run(batch_parameters={"dataframe": df})

if not result.success:
    # Разделяем блокирующие и предупреждающие: имена ожиданий помечены в meta,
    # либо, проще, держим два отдельных suite — blocking и warning.
    raise RuntimeError("Валидация витрины провалена, обучение остановлено")
```

Практические замечания, которых нет в документации.

**Два suite вместо одного.** Держите `user_features_daily__blocking` и
`user_features_daily__warning` раздельно. Иначе весь набор проверок деградирует до одного
булева флага, и любая шумная проверка распределения начинает останавливать пайплайн —
после чего её просто удаляют вместе с полезными.

**Автогенерация ожиданий опасна.** GX умеет профилировать данные и предлагать ожидания
автоматически. Использовать это можно только как черновик: профайлер зафиксирует случайные
свойства конкретной партиции (например, что `city` принимает ровно 1043 значения),
и вы получите десятки ложных срабатываний на следующей же неделе. Каждое сгенерированное
ожидание надо просмотреть глазами и либо обосновать, либо выкинуть.

**Стоимость.** GX на pandas читает данные в память. Для партиции в 12 млн строк × 40 колонок
это десятки гигабайт. Варианты: валидировать на Spark-бэкенде, валидировать на выборке
(но тогда проверки уникальности и полноты теряют смысл — их надо считать SQL-запросом
по всей таблице), или считать агрегаты в SQL и проверять уже их.

**Альтернативы, которые стоит знать.** `pandera` — легковесная типизированная валидация
датафреймов, отлично ложится на код и тесты. Тесты `dbt` — если трансформации живут в dbt,
проверки уникальности, `not_null` и ссылочной целостности пишутся одной строкой в YAML
и выполняются в базе, что бесплатно по памяти. `Deequ`/`PyDeequ` — для больших объёмов
на Spark. Часто самое правильное решение — не фреймворк, а несколько SQL-запросов
в оркестраторе: их проще читать и они выполняются там, где лежат данные.

## 7. Что делать при провале: стоп или предупреждение

Это самое важное решение в главе, и оно принимается не по вкусу, а по экономике.

Пусть проверка сработала. Введём:

- $p$ — вероятность, что данные действительно испорчены, при условии, что проверка упала
  (то есть **точность проверки**, precision);
- $C_{\text{стоп}}$ — стоимость остановки пайплайна, когда данные на самом деле хорошие
  (устаревшие рекомендации, задержка отчёта, ручной разбор дежурным, недополученная выручка
  за время простоя);
- $C_{\text{плохо}}$ — стоимость пропуска испорченных данных дальше по пайплайну.

Ожидаемые потери двух решений:

$$
E[C_{\text{стоп}}] = (1-p)\, C_{\text{стоп}}, \qquad
E[C_{\text{пропуск}}] = p\, C_{\text{плохо}}
$$

Останавливать выгодно, когда $E[C_{\text{стоп}}] < E[C_{\text{пропуск}}]$, то есть когда

$$
p > \frac{C_{\text{стоп}}}{C_{\text{стоп}} + C_{\text{плохо}}}
$$

**Разбор на числах, случай первый: обучение.** Пайплайн переобучения запускается ночью.
Ложная остановка означает, что модель обновится на сутки позже — оценим в 50 тысяч рублей
недополученной выручки. Пропуск испорченных данных означает выкатку модели, обученной
на мусоре: до обнаружения через отложенные метрики пройдёт две недели, ущерб — порядка
5 миллионов. Порог:

$$
p > \frac{50}{50 + 5000} \approx 0.01
$$

То есть **достаточно, чтобы проверка была права один раз из ста**, и остановка уже оправдана.
Вот почему перед обучением ставят жёсткие стопы почти на всё: асимметрия цен огромна.

**Разбор на числах, случай второй: онлайн-инференс.** Ложная остановка означает, что сервис
отказывает пользователю: при 3000 RPS минута отказа — это 180 тысяч неотвеченных запросов
и прямая потеря конверсии, оценим в 300 тысяч рублей за 10 минут. Пропуск подозрительной
строки означает одно предсказание на дефолтных признаках — ущерб порядка рубля. Порог:

$$
p > \frac{300\,000}{300\,000 + 1} \approx 0.999997
$$

Практически недостижимо. Отсюда правило: **в онлайне почти никогда не останавливаемся;
деградируем и считаем метрику.**

Сведём в таблицу режимы реакции:

| Режим | Что делает | Когда применять |
|---|---|---|
| Жёсткий стоп (fail) | пайплайн падает, следующие шаги не запускаются, данные не публикуются | приём, трансформации, обучение; проверки схемы, ключей, свежести |
| Карантин (quarantine) | плохие строки откладываются в отдельную таблицу, хорошие идут дальше; метрика доли карантина | построчные поломки в батче, когда доля мала (< 1%) |
| Деградация (degrade) | подставляем дефолт, помечаем `degraded=true`, инкрементируем счётчик | онлайн-инференс |
| Предупреждение (warn) | пишем в отчёт и в метрику, пайплайн идёт дальше | распределения, мягкие пороги, новые проверки на испытательном сроке |

Три правила, которые стоит принять как командные:

1. **Новая проверка живёт две недели в режиме `warn`.** За это время видно её частоту
   срабатывания на реальных данных. Не сработала ни разу и не должна была — можно повышать
   до `block`. Сработала пять раз впустую — порог не готов.
2. **Стоп обязан оставлять след.** Упавший пайплайн без сохранённого отчёта (какая проверка,
   какое наблюдаемое значение, какая партиция, примеры нарушающих строк) — это гарантированные
   два часа расследования вместо десяти минут.
3. **У жёсткого стопа должен быть явный обход.** Кнопка «принять партицию вручную»
   с обязательным комментарием и записью в лог. Без неё в 3 часа ночи кто-то закомментирует
   проверку в коде, и она уже не вернётся.

```python
# Гейт в Airflow: проверка как отдельная задача, а не как побочный эффект внутри трансформации.
from airflow.decorators import task
from airflow.exceptions import AirflowFailException, AirflowSkipException

@task
def validate_partition(partition_date: str) -> dict:
    report = run_checks(partition_date)          # ваш движок из §5 или GX из §6
    blocking = [c for c in report if not c.passed and c.severity == "block"]
    warnings = [c for c in report if not c.passed and c.severity == "warn"]

    push_to_prometheus(report)                   # метрики уходят ВСЕГДА, даже при провале
    save_report_to_s3(report, partition_date)    # след для расследования — обязателен

    if blocking:
        # AirflowFailException, а не Skip: провал контракта должен быть виден как ошибка,
        # иначе DAG зелёный, а данных нет, и это худший из возможных исходов.
        raise AirflowFailException(f"blocking checks failed: {[c.name for c in blocking]}")
    return {"warnings": [c.name for c in warnings]}
```

> 💬 **На собеседовании.** Спросят: «Проверка данных упала. Останавливать пайплайн?»
> Хороший ответ: «Зависит от соотношения цены ложной остановки и цены плохих данных.
> Формально останавливать выгодно, когда точность проверки выше отношения
> $C_{\text{стоп}}/(C_{\text{стоп}}+C_{\text{плохо}})$. Перед обучением это отношение
> порядка процента: сутки задержки стоят дёшево, а модель на мусоре — дорого, поэтому там
> жёсткий стоп почти на всё. В онлайн-инференсе наоборот: остановка означает отказ
> пользователю, поэтому там деградация с флагом и счётчиком, а не отказ. Плюс промежуточный
> режим — карантин строк, когда доля нарушений меньше процента. И новую проверку я две недели
> держу в режиме предупреждения, чтобы измерить её частоту ложных срабатываний, прежде
> чем давать ей право ронять пайплайн».
> Плохой ответ: «всегда останавливать, данные важнее» или «никогда не останавливать,
> бизнес не поймёт» — оба варианта игнорируют, что это решение с ценой.

## 8. Пять типовых поломок из практики

### 8.1. Тихая смена формата

**Симптом.** Метрики сервиса в норме, ошибок нет, но доля положительных решений упала
в несколько раз за один день. Схема валидна.

**Причина.** Источник изменил представление значения, не изменив тип: рубли стали тысячами
рублей; дата `2026-07-25` стала `25.07.2026`; число `1299.00` стало строкой `"1 299,00"`
и после `pd.to_numeric(errors="coerce")` превратилось в `NaN`; код страны `RU` стал `RUS`.
Формально всё корректно, семантически всё сломано.

**Что делать.** Проверка на соотношение среднего к базлайну (`max(cur/base, base/cur) > 1.5`)
ловит смену единиц мгновенно и почти без ложных срабатываний, потому что реальные изменения
такого масштаба за сутки не происходят. Дополнительно: границы `[min, max]` из обучающей
выборки; доля значений, не приводящихся к нужному типу (после `coerce` — доля новых `NaN`,
порог 0.1%); доля новых категорий. Долгосрочно — блок `unit` и `semantics` в контракте
и версионирование источника.

### 8.2. Битые джойны

**Симптом.** Число строк после джойна выросло в 1.3 раза, метрики обучения улучшились
(лик), а в проде модель работает хуже офлайн-оценки. Или наоборот: половина признаков
внезапно `NULL`.

**Причина.** Три классических варианта. Первый — **fanout**: в правой таблице дубли
по ключу, `LEFT JOIN` размножает строки факта; часть объектов попадает в выборку несколько
раз и получает больший вес. Второй — **потеря**: справочник не обновился, новые ключи
не нашли пары, присоединённые колонки стали `NULL`, а модель обучалась на непропущенных.
Третий — **несовпадение типов**: `user_id` в одной таблице `int64`, в другой `string`
с ведущими нулями; джойн формально отрабатывает, совпадений почти нет.

**Что делать.** Обязательный инвариант после каждого `LEFT JOIN`:

$$
\text{fanout} = \frac{n_{\text{после}}}{n_{\text{до}}}
$$

и проверка `fanout == 1.0` с допуском 0. Плюс проверка уникальности ключа в правой таблице
**до** джойна, доля `NULL` в присоединённых колонках после джойна (порог 0.5%),
и явное приведение типов ключей с проверкой доли совпадений.

```sql
-- Проверка справочника ДО джойна: одна строка на ключ
SELECT count(*) - count(DISTINCT product_id) AS dup_keys FROM dim_product;
-- Ожидание: dup_keys = 0

-- Проверка результата ПОСЛЕ джойна
SELECT
    count(*)                                                       AS rows_after,
    count(*) FILTER (WHERE d.product_id IS NULL) * 1.0 / count(*)  AS orphan_share
FROM fact_orders f
LEFT JOIN dim_product d USING (product_id);
-- Ожидания: rows_after = rows_before; orphan_share <= 0.001
```

### 8.3. Дубли из-за ретраев

**Симптом.** Число событий за день выросло на 4%, агрегаты `orders_30d` завышены,
конверсия «улучшилась» без причины. При пересчёте вчерашней партиции получаются другие числа.

**Причина.** Три источника. Первый — доставка **at-least-once** в Kafka: при переподключении
консьюмера сообщения между последним коммитом оффсета и сбоем доставляются повторно.
Второй — **ретрай задачи в оркестраторе**: задача упала после записи половины партиции,
Airflow перезапустил её, и данные дописались поверх (режим `append` вместо `overwrite`).
Третий — **backfill поверх существующих данных**: пересчёт исторической партиции без
предварительной очистки.

**Что делать.** Три уровня защиты, и нужны все три.

1. **Идемпотентность записи.** Партиция пишется атомарно с полной перезаписью
   (`INSERT OVERWRITE PARTITION`, `mode="overwrite"` с `partitionOverwriteMode=dynamic`,
   в Delta/Iceberg — `replaceWhere` или `MERGE`). Задача, запущенная дважды, должна давать
   тот же результат.
2. **Дедупликация по бизнес-ключу.** Не по всей строке (строка может отличаться техническими
   полями вроде `ingested_at`), а по `event_id` или по (`user_id`, `event_type`, `event_time`),
   с выбором последней записи по времени приёма:

```sql
SELECT * FROM (
    SELECT *, row_number() OVER (
        PARTITION BY event_id ORDER BY ingested_at DESC
    ) AS rn
    FROM raw_events WHERE event_date = '2026-07-25'
) t WHERE rn = 1
```

3. **Проверка доли дублей как метрика.** Не «мы дедуплицируем, значит всё хорошо»,
   а именно измерение: если доля дублей до дедупликации внезапно выросла с 0.3% до 8%,
   это сигнал о проблеме доставки, который надо расследовать, даже если дедуп справился.

### 8.4. Часовые пояса

**Симптом.** Дневные агрегаты не сходятся с отчётом аналитиков на 3–8%. Часть событий
попадает в «завтра». Дважды в год (переход на летнее время в странах, где он есть) появляется
час с нулём событий или с двойным объёмом. Признак «заказов за последние 24 часа»
на обучении и в проде считается по разным границам.

**Причина.** Смешение naive-таймстемпов (без пояса) и aware; хранение локального времени
без указания зоны; партиционирование по локальной дате при событиях в UTC; клиентское время
вместо серверного (часы пользователя могут врать на часы и дни).

**Что делать.** Правила, которые надо принять один раз и соблюдать везде:

- **Хранить всё в UTC**, timezone-aware. Локальное время — только на уровне отображения.
- **Партиционировать по той же зоне, в которой считается бизнес-логика**, и записать это
  в контракт (`semantics: "календарная дата в Europe/Moscow"`). Расхождение партиции
  и логики — источник вечных несостыковок на границе суток.
- **Проверка «событий из будущего»**: доля строк с `event_time > now() + 5 минут` — порог 0.
  Это ловит и клиентское время, и перепутанные зоны.
- **Проверка почасового профиля**: число событий в каждом часе не отклоняется больше чем
  в 3 раза от медианы того же часа за прошлые 7 дней. Час с нулём событий — гарантированный
  сдвиг зоны.
- **Хранить рядом с событием и `event_time`, и `ingested_at`** — без второго невозможно
  ни дедуплицировать, ни отладить лаг доставки, ни корректно сделать point-in-time-выборку
  (см. [feature store](../07-mlops/03-data-and-feature-store.md)).

### 8.5. Подмена пропусков дефолтом на стороне источника

**Симптом.** Доля `NULL` в признаке упала до нуля — выглядит как улучшение качества данных.
Через месяц офлайн-метрика проседает. В распределении признака появляется аномальный пик
в одной точке.

**Причина.** Источник «улучшил» данные: `NULL` заменили на `0`, `-1`, `"unknown"`,
`1970-01-01` или на среднее по популяции. Для модели это катастрофа: она обучалась
на признаке с честными пропусками (а бустинг умеет обрабатывать `NULL` осмысленно,
направляя их в отдельную ветку — см. [решающие деревья](../02-classic-ml/05-decision-trees.md)),
а теперь получает конкретное значение, которое означает «неизвестно», но выглядит как
«ноль рублей дохода».

**Что делать.**

- Прописать в контракте `null_means` и явный запрет на замену пропуска дефолтом
  на стороне источника.
- **Проверка на аномальный пик**: доля самого частого значения в непрерывном признаке.
  Если для `monthly_income` доля одного значения превысила 5% — это почти наверняка
  значение-заглушка. Формально:

$$
m_j = \max_{v} \frac{|\{i: x_{ij} = v\}|}{n}
$$

  где $m_j$ — доля модального значения признака $j$. Порог 0.05 для непрерывных признаков.

- **Проверка на конкретные подозрительные значения**: доля `0`, `-1`, `-999`, `9999`,
  `1970-01-01`, `1900-01-01`, `"unknown"`, `"N/A"`, пустой строки. Каждое из них
  по отдельности, с порогом из истории.
- **Мониторить долю пропусков в обе стороны.** Резкое **падение** доли `NULL` — такой же
  сигнал, как и рост. Это контринтуитивно и потому регулярно пропускается.

> 💬 **На собеседовании.** Спросят: «Как поймать, что источник подменил пропуски дефолтом?»
> Хороший ответ: «Прямая проверка — доля модального значения непрерывного признака: если одно
> значение занимает больше 5%, это заглушка. Плюс алерт на резкое падение доли `NULL`:
> обычно смотрят только на рост, а падение — такой же симптом. Плюс явный список подозрительных
> значений: 0, −1, −999, 1970-01-01, "unknown". Важно понимать, почему это дорого: бустинг
> обрабатывает `NULL` отдельной веткой, и подмена пропуска нулём переводит объекты
> в совершенно другую часть дерева. Системное лечение — поле `null_means` в контракте
> и запрет источнику "улучшать" данные».
> Плохой ответ: «проверим на `NULL`» — их-то как раз и не будет.

## 9. Подводные камни

**Пайплайн зелёный, а данных за вчера нет.**
Симптом: DAG успешен, витрина пуста или содержит вчерашние данные.
Причина: проверки стоят внутри задачи, которая не запустилась (сенсор не дождался,
расписание сдвинулось, DAG на паузе). Проверка внутри не может обнаружить своё отсутствие.
Что делать: свежесть проверяется **снаружи**, по метрике «время последнего успешного
завершения», через Prometheus/Alertmanager, а не задачей внутри того же DAG.

**Проверки отключили через месяц после внедрения.**
Симптом: `if False:` перед блоком валидации или закомментированная задача в DAG.
Причина: набор проверок сразу поставили в блокирующий режим, он давал 3–5 ложных
срабатываний в неделю, дежурные устали.
Что делать: испытательный срок в две недели в режиме `warn`, пороги — из исторических
квантилей, разделение blocking/warning, явная кнопка ручного пропуска партиции с записью
в лог (см. §7).

**Проверка «доля пропусков ≤ 35%» проходит, а половина источника отвалилась.**
Симптом: доля `NULL` выросла с 2% до 30%, порог не пробит, никто не заметил.
Причина: только абсолютный порог, взятый с большим запасом.
Что делать: относительная проверка рядом с абсолютной — «не выросла больше чем
на 5 п.п. относительно среднего за 7 дней».

**Валидация датасета съедает больше памяти, чем обучение.**
Симптом: OOM на шаге валидации, при том что обучение проходит.
Причина: GX на pandas читает всю партицию в память, датафрейм 12 млн × 40 колонок
разворачивается в десятки гигабайт.
Что делать: считать агрегаты SQL-запросом в хранилище и валидировать уже их; либо
Spark-бэкенд; проверки распределений — на выборке, проверки уникальности и полноты —
только по полным данным (на выборке они бессмысленны).

**После внедрения дедупликации метрики модели упали.**
Симптом: офлайн-качество просело после «исправления» данных.
Причина: модель обучалась на данных с дублями, и дубли выполняли роль весов
(активные пользователи дублировались чаще). Убрали дубли — изменилось эффективное
распределение обучающей выборки.
Что делать: любое исправление данных — это изменение распределения, его надо катить
как изменение модели: переобучить, сравнить офлайн, выкатить через
[канареечную схему](../07-mlops/08-deployment-strategies.md), а не «просто починить».

**Проверки на обучении есть, на инференсе нет.**
Симптом: офлайн-метрики отличные, в проде хуже; расхождение не объясняется.
Причина: классический train/serve skew — в обучении данные проходят валидацию и очистку,
в онлайне приходят сырыми.
Что делать: одна и та же схема (один файл контракта) используется в обеих точках;
логировать признаки в момент предсказания и раз в неделю сравнивать их распределения
с обучающими — это единственный надёжный способ обнаружить skew
(см. [feature store](../07-mlops/03-data-and-feature-store.md)).

**Контракт есть, но никто не знает, что он нарушен.**
Симптом: файл контракта в репозитории, проверок из него не сгенерировано.
Причина: контракт написан как документ, а не как код.
Что делать: единственный источник правды — файл контракта; проверки генерируются из него;
CI падает, если контракт изменён без повышения версии и без уведомления потребителей.

## 10. Проверь себя

<details>
<summary><b>🎯 Вопрос.</b> Что такое контракт данных и что в нём должно быть, кроме схемы?</summary>

**Короткий ответ.** Явное версионируемое соглашение между поставщиком и потребителем.
Кроме структуры (колонки, типы, ключи) в нём должны быть семантика (единицы измерения,
часовой пояс, что означает пропуск, гранулярность строки), гарантии эксплуатации (свежесть,
объём, полнота, уникальность, режим доставки) и политика изменений с окном депрекации.

**Развёрнуто.** Ценность контракта в том, что он машиночитаем и из него генерируются проверки;
контракт-документ устаревает за два месяца. Самая недооценённая часть — семантика: три самые
дорогие поломки (смена единиц измерения, смена часового пояса, подмена `NULL` дефолтом)
проходят структурную валидацию без замечаний, потому что тип не меняется. Политика изменений
нужна, чтобы отличать добавление nullable-колонки (можно молча) от переименования или смены
типа (30 дней предупреждения, параллельные версии). И у контракта обязан быть владелец —
конкретная команда, а не «данные».

**Чего ждёт интервьюер:** что вы назовёте семантику и SLA, а не ограничитесь списком колонок.

**Провал:** «контракт данных — это схема таблицы».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Перечислите виды проверок качества данных.</summary>

**Короткий ответ.** Шесть семейств: полнота (доля пропусков), уникальность (дубли по ключу),
валидность (типы, диапазоны, допустимые значения), распределения (сдвиг среднего, доля
модального значения, число уникальных), ссылочная целостность (доля сирот после джойна),
свежесть (лаг данных и лаг запуска пайплайна).

**Развёрнуто.** Полезно к каждому семейству добавить, что порог бывает двух типов —
абсолютный и относительный, и нужны оба: абсолютный ловит катастрофу («не больше 35%
пропусков»), относительный — деградацию («доля пропусков не выросла больше чем на 5 п.п.
к среднему за неделю»). Отдельно надо назвать проверки, специфичные для ML-пайплайна:
fanout джойна (`rows_after / rows_before == 1` для `LEFT JOIN`), доля значений вне обучающего
диапазона, событий «из будущего», отсутствие утечки таргета. Свежесть — единственная проверка,
которая обязана выполняться снаружи пайплайна, потому что самый частый способ протухания
данных — пайплайн вообще не запустился.

**Чего ждёт интервьюер:** структурированного списка вместо потока примеров и понимания,
что часть проверок специфична для ML.

**Провал:** назвать только «проверить на `NULL` и на дубли».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Почему в разных точках пайплайна ставят разные проверки?</summary>

**Короткий ответ.** Потому что различаются три вещи: что технически можно проверить, сколько
есть времени и сколько стоит остановка. На приёме нет признаков — проверять распределения
нечего; в онлайне есть одна строка и 2 миллисекунды — распределение посчитать не из чего;
перед обучением есть весь датасет и часы времени, и остановка почти бесплатна.

**Развёрнуто.** Четыре точки. Приём: схема, типы, PK, свежесть, объём; жёсткий стоп, потому
что мусор дешевле не пустить, чем вычищать из пяти витрин. После трансформаций: инварианты
собственного кода — fanout, дубли, доля новых `NULL`, сходимость сумм; тоже стоп, это наш баг.
Перед обучением: максимальная строгость, включая распределения, баланс классов, проверки
на утечку и point-in-time; стоп стоит суток задержки, а плохая модель — недель ущерба.
Перед онлайн-инференсом: только построчные дешёвые проверки, реакция — деградация с флагом
и счётчиком, а не отказ; агрегированные проверки для онлайна делаются асинхронно по логам
признаков. Одна точка валидации не покрывает ни ошибок источника, ни ошибок трансформаций,
ни онлайн-трафика.

**Чего ждёт интервьюер:** что вы объясните различие через цену остановки и доступный контекст,
а не просто перечислите точки.

**Провал:** «поставим один Great Expectations в конце пайплайна».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Проверка упала. Останавливать пайплайн или пропускать с предупреждением?</summary>

**Короткий ответ.** Останавливать выгодно, когда точность проверки $p$ превышает
$C_{\text{стоп}}/(C_{\text{стоп}} + C_{\text{плохо}})$. Перед обучением это отношение
около процента — стоп почти всегда оправдан. В онлайне цена остановки — отказ пользователю,
поэтому там деградация, а не стоп.

**Развёрнуто.** Вывод простой: ожидаемая потеря при остановке $(1-p)C_{\text{стоп}}$,
при пропуске $p\,C_{\text{плохо}}$; приравниваем и получаем порог. Числа для обучения:
сутки задержки ≈ 50 тыс., модель на мусоре две недели ≈ 5 млн, порог $p > 0.01$ — достаточно,
чтобы проверка была права раз в сто. Числа для онлайна: минута отказа при 3000 RPS —
это 180 тысяч необслуженных запросов, а одно предсказание на дефолтах стоит копейки,
порог получается практически недостижимым. Между стопом и предупреждением есть два
промежуточных режима, которые надо назвать: карантин строк (плохие в отдельную таблицу,
хорошие дальше) и деградация с флагом. Плюс процессное правило: новая проверка две недели
живёт в режиме `warn`, чтобы измерить частоту ложных срабатываний.

**Чего ждёт интервьюер:** что решение будет обосновано ценой ошибки, а не догмой.

**Провал:** «всегда останавливаем, качество данных важнее».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Источник изменил единицы измерения признака: было в рублях, стало в тысячах. Какие проверки это поймают?</summary>

**Короткий ответ.** Проверка отношения текущего среднего к базлайну (порог 1.5×), проверка
границ из обучающей выборки и — быстрее всего в проде — сдвиг распределения предсказаний
и доли решений выше порога. Схема, типы и полнота не поймают ничего.

**Развёрнуто.** Ключевая мысль: тип не изменился, `NULL` не появились, строк столько же —
все структурные проверки зелёные. Отношение средних выбрано именно как отношение, а не разность,
потому что оно безразмерно и ловит смену порядка величины независимо от масштаба признака;
на реальных данных среднее за сутки редко меняется больше чем в полтора раза, так что порог
почти не даёт ложных срабатываний. Границы `[min, max]` из обучающей выборки — вторая линия:
доход 85 при обучающем диапазоне `[10 000, 5 000 000]` даёт долю нарушений близкую к 100%.
Системное лечение — поле `unit` в контракте, версионирование источника и окно депрекации:
такое изменение обязано быть major-версией с параллельной поддержкой старого формата.

**Чего ждёт интервьюер:** понимания, что валидация типов не защищает от семантических поломок.

**Провал:** «проверка схемы поймает».
</details>

<details>
<summary><b>🎯 Вопрос.</b> После джойна число строк выросло на 30%. Что произошло и как это предотвратить?</summary>

**Короткий ответ.** Fanout: в правой таблице дубли по ключу джойна, `LEFT JOIN` размножил
строки факта. Предотвращается проверкой уникальности ключа в справочнике до джойна
и инвариантом `rows_after / rows_before == 1` после.

**Развёрнуто.** Последствия серьёзнее, чем «лишние строки»: размноженные объекты получают
больший вес в обучении, а если дубли коррелируют с таргетом (активные пользователи
дублируются чаще), это смещает модель. Кроме fanout есть ещё два вида битого джойна:
потеря соответствий, когда справочник не обновился и присоединённые колонки стали `NULL`
(проверка: доля `NULL` в присоединённых колонках после джойна, порог 0.5%), и несовпадение
типов ключей — `int64` против строки с ведущими нулями, когда джойн формально работает,
а совпадений почти нет (проверка: доля сирот). Практика: после каждого `LEFT JOIN`
в пайплайне стоит явная проверка числа строк, это одна строка кода и десятки сэкономленных
часов.

**Чего ждёт интервьюер:** что вы назовёте не только симптом, но и последствие для обучения.

**Провал:** «поставим `DISTINCT`» — это маскирует проблему и может удалить легитимные строки.
</details>

<details>
<summary><b>🧠 Вопрос.</b> Откуда берутся дубли при ретраях и как от них защититься?</summary>

**Короткий ответ.** Три источника: доставка at-least-once в Kafka, повторный запуск задачи
оркестратора после частичной записи, backfill поверх существующей партиции. Защита в три
уровня: идемпотентная запись, дедупликация по бизнес-ключу, метрика доли дублей.

**Развёрнуто.** Идемпотентность — главное: партиция должна перезаписываться целиком
(`INSERT OVERWRITE`, `mode="overwrite"`, `MERGE` в Delta/Iceberg), тогда повторный запуск
даёт тот же результат. Дедупликация — по бизнес-ключу (`event_id` или тройка
пользователь/тип/время), а не по всей строке: строки различаются техническими полями вроде
`ingested_at`, и `DISTINCT *` дубли не уберёт. Третий уровень — измерение: даже если дедуп
работает, долю дублей до него надо мониторить, потому что скачок с 0.3% до 8% означает
проблему в доставке, которую надо чинить у источника. Отдельно стоит упомянуть, что exactly-once
в Kafka существует, но стоит производительности и требует транзакций на всём пути, поэтому
на практике чаще берут at-least-once плюс дедуп на стороне потребителя.

**Чего ждёт интервьюер:** что вы отделите гарантии доставки от идемпотентности обработки —
это разные вещи, и вторая под вашим контролем.

**Провал:** «включим exactly-once, и дублей не будет».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Какие проблемы создают часовые пояса и как их ловить?</summary>

**Короткий ответ.** Расхождение агрегатов на границе суток, события «из будущего», час
с нулём или двойным объёмом при переходе на летнее время, разные окна признаков на обучении
и в проде. Ловится проверкой на будущее время, проверкой почасового профиля и хранением
всего в UTC.

**Развёрнуто.** Корень проблемы — смешение naive и aware таймстемпов и использование
клиентского времени вместо серверного. Правила: хранить в UTC timezone-aware; локальное
время — только на отображение; партиционировать по той зоне, в которой считается
бизнес-логика, и записать это в контракт. Проверки: доля строк с `event_time > now() + 5 мин`
с порогом 0 (ловит и клиентские часы, и перепутанные зоны); почасовой профиль — число событий
в часе не отклоняется больше чем в 3 раза от медианы того же часа за неделю. Отдельно важно
для ML: рядом с `event_time` обязателен `ingested_at` — без него невозможна корректная
point-in-time-выборка, и вы получите утечку из будущего, потому что признак попадёт
в обучающую строку раньше, чем он реально был доступен в проде.

**Чего ждёт интервьюер:** связки «часовые пояса → point-in-time correctness → утечка».

**Провал:** «переведём всё в московское время» — naive-время без зоны воспроизводит проблему.
</details>

<details>
<summary><b>🧠 Вопрос.</b> Доля пропусков в признаке упала с 20% до 0. Это хорошо?</summary>

**Короткий ответ.** Почти наверняка плохо: источник заменил `NULL` дефолтным значением.
Для модели, обученной на честных пропусках, это меняет семантику признака и ломает предсказания.

**Развёрнуто.** Как обнаружить: доля модального значения непрерывного признака — если одно
значение занимает больше 5%, это заглушка (0, −1, −999, 1970-01-01, «unknown»). Плюс алерт
на **падение** доли `NULL`, а не только на рост — про это забывают почти все. Почему дорого:
бустинг обрабатывает пропуск отдельным направлением в узле, то есть у `NULL` есть собственный
маршрут по дереву; замена его нулём переводит объекты в совсем другую ветку и даёт
систематически смещённый скор. Если признак перед моделью импутируется, эффект похожий:
импутация обучалась на одном распределении пропусков, а получила другое. Лечение —
`null_means` в контракте и явный запрет источнику подставлять дефолт.

**Чего ждёт интервьюер:** что вы не примете «стало меньше пропусков» за улучшение и объясните
механику ущерба через устройство модели.

**Провал:** «отлично, качество данных выросло».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Зачем нужен Great Expectations, если проверки можно написать на pandas за час?</summary>

**Короткий ответ.** Ради того, что дороже писать самому: единый отчёт и история валидаций
по всем таблицам, документация для смежных команд, готовая библиотека ожиданий, интеграция
с оркестратором и каталогом. Для одной команды и пяти таблиц свой скрипт часто разумнее.

**Развёрнуто.** Полезно показать, что вы понимаете границы. Плюсы GX: декларативность
(проверка читается как предложение), Data Docs — HTML-отчёт, который можно показать
дата-инженерам и продакту, история результатов, несколько бэкендов (pandas, Spark, SQL).
Минусы: заметный порог входа, ломающие изменения API между 0.18 и 1.x, потребление памяти
на pandas-бэкенде (партиция 12 млн × 40 колонок не влезет), избыточность для простых случаев.
Альтернативы, которые стоит назвать: `pandera` для типизированной валидации в коде,
тесты `dbt` для проверок в базе (выполняются рядом с данными, бесплатны по памяти),
`Deequ`/`PyDeequ` для Spark. И честный вывод: если трансформации живут в SQL, проверки
тоже правильнее держать в SQL.

**Чего ждёт интервьюер:** инженерного суждения, а не рекламы инструмента.

**Провал:** «GX — стандарт, надо всегда его».
</details>

<details>
<summary><b>🌱 Вопрос.</b> Почему проверку свежести нельзя ставить внутрь пайплайна?</summary>

**Короткий ответ.** Потому что самый частый способ протухания данных — пайплайн вообще
не запустился, и проверка внутри него тоже не запустилась. Отсутствие данных должно
обнаруживаться снаружи, по факту отсутствия сигнала.

**Развёрнуто.** Механика: пайплайн после успешного завершения выставляет метрику
`feature_table_last_success_timestamp_seconds`. Внешний алерт проверяет
`time() - max(метрика) > 2 × период_расписания`. Такая схема ловит все варианты: DAG на паузе,
сенсор не дождался апстрима, расписание сдвинулось, кластер недоступен, задача висит.
Это частный случай общего принципа мониторинга: **отсутствие сигнала — тоже сигнал**,
и система, которая умеет говорить только «у меня всё плохо», но не умеет молчать заметно,
неполна. Тот же принцип применяется к heartbeat-метрикам сервисов и к watchdog в
[стеке наблюдаемости](05-observability-stack.md).

**Чего ждёт интервьюер:** понимания разницы между «данные плохие» и «данных нет».

**Провал:** «добавим задачу проверки в конец DAG».
</details>

## 11. Практика

**Задача 1. Написать контракт (45 минут).**
Возьмите любую таблицу, с которой работаете, и опишите контракт по шаблону из §2:
структура, семантика, SLA, политика изменений.
*Сделано правильно: для каждой числовой колонки указана единица измерения; для каждой
временной — часовой пояс; для каждой nullable — что означает пропуск; указан режим доставки
и ожидаемое число строк; вы можете назвать, какая проверка генерируется из каждой строки
контракта.*

**Задача 2. Реализовать движок проверок (60 минут).**
Возьмите код из §5, добавьте три проверки: доля модального значения, доля значений
из «чёрного списка» заглушек (`0, -1, -999, 1970-01-01`), доля событий из будущего.
*Сделано правильно: движок возвращает отчёт со всеми результатами (а не падает на первом
провале), различает `block` и `warn`, и при пустой колонке проверка не проходит молча.*

**Задача 3. Сломать данные и посмотреть, что сработает (90 минут).**
Возьмите датасет и внесите пять поломок: (а) числовой признак разделить на 1000;
(б) продублировать 5% строк; (в) заменить 25% `NULL` нулями; (г) сдвинуть все временные метки
на 3 часа; (д) в справочнике перед джойном продублировать 2% ключей.
Прогоните полный набор проверок и составьте матрицу «поломка × проверка».
*Сделано правильно: у вас есть матрица, где видно, что структурные проверки ловят только (б);
для каждой поломки названа минимум одна проверка, которая её ловит, и указан порог,
при котором она сработала бы.*

**Задача 4. Настроить Great Expectations (60 минут).**
Соберите suite из §6 на своих данных, разделив его на `blocking` и `warning`. Запустите
на трёх последовательных партициях.
*Сделано правильно: suite воспроизводимо запускается из скрипта; пороги взяты из истории,
а не из одной партиции; вы можете показать отчёт и объяснить, почему каждое ожидание попало
именно в blocking или в warning.*

**Задача 5. Посчитать порог остановки (30 минут).**
Для своего пайплайна оцените $C_{\text{стоп}}$ и $C_{\text{плохо}}$ в деньгах и посчитайте
порог точности проверки по формуле из §7. Сделайте это отдельно для обучения и для онлайна.
*Сделано правильно: получены два сильно разных числа; на их основе вы перераспределили
хотя бы две проверки между режимами `block`, `quarantine`, `warn` и можете обосновать
каждое решение.*

**Задача 6. Проверка свежести снаружи (40 минут).**
Настройте выставление метрики времени последнего успешного запуска (Prometheus Pushgateway
или запись в таблицу) и внешний алерт на её устаревание. Остановите пайплайн и убедитесь,
что алерт сработал.
*Сделано правильно: алерт срабатывает при остановке пайплайна, при DAG на паузе и при
зависшей задаче; порог выражен через период расписания, а не зашит константой.*

## 12. Что читать дальше

- [Great Expectations — документация](https://docs.greatexpectations.io/) — начните
  с Core concepts и списка встроенных ожиданий: он сам по себе хороший чек-лист того,
  что вообще стоит проверять. Обязательно смотрите на версию, API 0.18 и 1.x различаются.
- [pandera — документация](https://pandera.readthedocs.io/) — типизированные схемы
  датафреймов, которые естественно ложатся на pytest. Хороший выбор, когда фреймворк
  уровня GX избыточен.
- [dbt — тесты данных](https://docs.getdbt.com/docs/build/data-tests) — `unique`, `not_null`,
  `accepted_values`, `relationships` одной строкой YAML и выполнение в базе. Если
  трансформации в dbt, проверки должны быть там же.
- [PyDeequ / Deequ (AWS Labs)](https://github.com/awslabs/deequ) — проверки качества
  на Spark для больших объёмов, с профилированием и детекцией аномалий в метриках данных.
  Читать вместе со статьёй авторов «Automating Large-Scale Data Quality Verification» (VLDB 2018).
- [Google. «Rules of Machine Learning»](https://developers.google.com/machine-learning/guides/rules-of-ml) —
  правила про мониторинг свежести данных и про train/serve skew прямо относятся к этой главе;
  текст короткий и очень прикладной.
- **Google. «The ML Test Score: A Rubric for ML Production Readiness and Technical Debt
  Reduction» (2017)** — блок Data Tests из семи пунктов можно взять как готовый аудит
  своего пайплайна; ищется по названию.
- **Chip Huyen. «Designing Machine Learning Systems» (O'Reilly, 2022)** — главы Training Data
  и Data Distribution Shifts and Monitoring: систематизация проблем данных и их последствий
  для модели.
- Соседние главы: [что мониторить](01-what-to-monitor.md) — куда встраиваются метрики
  качества данных; [дрифт](03-drift-detection.md) — что делать, когда данные формально
  корректны, но изменились; [feature store](../07-mlops/03-data-and-feature-store.md) —
  point-in-time correctness и train/serve skew.
