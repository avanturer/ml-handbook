## 1. Что такое «упакованная модель»

Типичная сцена. Дата-сайентист присылает бэкендеру файл `model.pkl` в мессенджере и говорит:
«вот, загрузи через `pickle.load` и вызови `predict`». Через час бэкендер пишет, что не грузится.
Ещё через час выясняется, что у него `scikit-learn 1.5`, а модель обучена на `1.2`. К вечеру
находят, что на входе модель ждала колонки в конкретном порядке, а сервис отдаёт словарь.
На следующий день обнаруживается, что в проде она предсказывает не то — потому что в обучении
категориальная фича кодировалась `OrdinalEncoder`, который остался в ноутбуке.

Всё это — не случайности. Это следствие одного решения: считать, что артефакт модели — это
веса. **Артефакт модели — это то, что позволяет получить из сырого входа предсказание,
воспроизводимо и на чужой машине.** Минимальный полный комплект:

| Компонента | Что это | Почему без неё ломается |
|---|---|---|
| Веса / структура | `.onnx`, `.pkl`, `.safetensors` | собственно модель |
| Препроцессинг | энкодеры, скейлеры, импьютеры — с **обученными** статистиками | средние для импьюта и границы бинов подобраны на трейне; пересчитать на проде = утечка и skew |
| Контракт I/O | список признаков, их типы, порядок, допустимые диапазоны, формат ответа | молчаливые ошибки: перепутанный порядок колонок не падает, а тихо портит предсказания |
| Окружение | точные версии Python и библиотек (lock-файл) | pickle привязан к версиям; ONNX — к версии opset |
| Метаданные | версия, датасет, метрики, автор, дата, хеш кода | без них невозможен ни откат, ни разбор инцидента |
| Способ вызова | сигнатура: сырой вход → предсказание | «а нормализовать надо самому?» — вопрос, которого не должно быть |

> ⚠️ **Типичная ошибка.** Сериализовать только модель, а препроцессинг оставить в коде сервиса.
> Через три месяца кто-то поменяет заполнение пропусков в сервисе, обучающий пайплайн об этом
> не узнает, и вы получите классический train/serve skew — расхождение между тем, что видела
> модель на обучении, и тем, что видит в проде. Лечится тем, что препроцессинг едет **внутри
> артефакта**: `sklearn.pipeline.Pipeline`, граф ONNX с включёнными преобразованиями или
> явный `preprocess()` в одном модуле с моделью.

## 2. Pickle: как он работает и почему это оружие

`pickle` — штатный питоновский формат сериализации объектов. Он не сохраняет код класса.
Он сохраняет **инструкции виртуальной машине pickle**: «импортируй `sklearn.ensemble._forest`,
возьми оттуда `RandomForestClassifier`, создай экземпляр, положи в `__dict__` вот эти
атрибуты». Из этого вытекают обе его проблемы.

### 2.1. Произвольное выполнение кода

Одна из инструкций формата — `REDUCE`: «вызови вот этот callable вот с этими аргументами».
Какой именно callable, определяет сам файл. Это значит, что **загрузка pickle — это исполнение
кода**, а не чтение данных.

```python
import os
import pickle

class Payload:
    # __reduce__ говорит pickle: "при загрузке вызови os.system с этой строкой"
    # Никакой магии нет — это документированная точка расширения протокола.
    def __reduce__(self):
        return (os.system, ("echo ВЫПОЛНИЛСЯ_ЧУЖОЙ_КОД",))

blob = pickle.dumps(Payload())

# Достаточно ЗАГРУЗИТЬ файл. Ни одного вызова predict ещё не было.
pickle.loads(blob)   # -> печатает ВЫПОЛНИЛСЯ_ЧУЖОЙ_КОД
```

Вместо `echo` там может быть `curl`, отправляющий переменные окружения (а вместе с ними
токены S3 и пароли БД) на внешний хост. Файл при этом остаётся валидной моделью: `predict`
работает, метрики сходятся, вредоносная нагрузка отрабатывает при загрузке.

Практические следствия, которые надо выучить:

- Загружать pickle из недоверенного источника — то же самое, что запустить чужой скрипт
  с правами вашего сервиса. Публичный хаб моделей, чужой S3-бакет, артефакт из чужого CI —
  недоверенные источники.
- Внутри компании доверие обеспечивается процессом: артефакт кладётся только из CI, доступ
  на запись в бакет реестра — только у CI, у сервиса — только на чтение, у артефакта считается
  контрольная сумма (SHA-256) и сверяется при загрузке.
- `torch.load` до версии 2.6 по умолчанию тоже был полноценным pickle со всеми последствиями;
  начиная с 2.6 по умолчанию включён `weights_only=True`, который разрешает восстанавливать
  только тензоры и простые типы. Не выключайте его «чтобы заработало» — это ровно та ручка,
  которая защищает от описанного выше.

> 💬 **На собеседовании.** Спросят: «Чем опасен pickle?»
> Хороший ответ: при десериализации pickle исполняет инструкции из файла, включая
> `REDUCE` — вызов произвольного callable; поэтому загрузка чужого `.pkl` эквивалентна
> запуску чужого кода с правами процесса, и никакая проверка «а он predict-ится?» этого
> не ловит. Плюс вторая, менее громкая проблема: pickle хранит ссылки на классы по полному
> имени модуля, поэтому артефакт жёстко привязан к версиям библиотек. Лечится доверенным
> каналом поставки (только из CI, чек-сумма при загрузке) и переходом на форматы без
> исполнения кода — ONNX или safetensors, где хранятся только тензоры.
> Плохой ответ: «pickle небезопасный» — без объяснения механизма.

### 2.2. Привязка к версиям

Второй эффект того же дизайна: в файле лежит строка `sklearn.ensemble._forest` — путь к классу.
Если в новой версии библиотеки модуль переименовали, разложение падает с `ModuleNotFoundError`.
Так было при переходе `sklearn.ensemble.forest → sklearn.ensemble._forest` (0.21 → 0.22).
Аналогично `numpy` в версии 2.0 переехал с `numpy.core` на `numpy._core`: pickle, созданный
под numpy 2, не читается под numpy 1.x.

Хуже тихий вариант. Класс на месте, а набор атрибутов изменился: модель распаковывается,
`predict` вызывается, но внутренняя логика уже другая — и предсказания едут. Именно поэтому
`scikit-learn`, начиная с 1.3, при загрузке артефакта, сделанного другой версией, выдаёт
`InconsistentVersionWarning`. **Это предупреждение надо превращать в ошибку в проде:**

```python
import warnings
import joblib
from sklearn.exceptions import InconsistentVersionWarning

# В сервисе несовпадение версий должно валить старт, а не логироваться и забываться:
# лучше не подняться, чем подняться и молча предсказывать неправильно.
with warnings.catch_warnings():
    warnings.simplefilter("error", InconsistentVersionWarning)
    model = joblib.load("artifacts/model.joblib")
```

Отсюда железное правило: **артефакт pickle/joblib и окружение — это одна неделимая единица
поставки.** Их версионируют вместе, катят вместе, и образ сервиса собирается из того же
lock-файла, из которого обучали (см. [§8](#8-версии-зависимостей-и-lock-файлы)).

## 3. Joblib, cloudpickle и когда они уместны

`joblib.dump/load` — надстройка над pickle, оптимизированная под большие numpy-массивы.
Отличия по существу два.

**Раздельное хранение буферов.** Массивы пишутся как непрерывные блоки байт, а не через общий
поток pickle. Для типичного случайного леса на 500 деревьев глубины 12 (файл порядка
200–400 МБ, практически весь объём — массивы порогов и индексов) это ускоряет чтение
примерно вдвое относительно чистого `pickle`.

**Memory mapping.** `joblib.load(path, mmap_mode="r")` отображает массивы в память, не копируя их.
Два эффекта: старт быстрее (страницы читаются лениво) и, если сервис запускает несколько
процессов-воркеров на одной машине, страницы разделяются между ними ядром — вместо
8 × 350 МБ = 2.8 ГБ RSS вы платите примерно один раз. Это очень практичный приём для
многопроцессного FastAPI-сервиса.

**Сжатие — компромисс, а не улучшение.** `joblib.dump(model, path, compress=3)` уменьшает
файл в 5–8 раз (350 МБ → ~50 МБ), что заметно на скачивании артефакта в CI. Но декомпрессия
съедает время старта: было ~1.5 с, стало ~6–9 с. Если у вас Kubernetes с автоскейлингом
(см. [сервинг](05-serving-architectures.md)), время старта — это деньги и хвост латентности
при скачках нагрузки. Практическое правило: **сжимать в хранилище, распаковывать при сборке
образа, в рантайме грузить несжатое с `mmap_mode`.**

`cloudpickle` умеет сериализовать функции и лямбды **по значению** — включая байт-код тела
функции, а не ссылку на модуль. Его используют Spark, Ray и MLflow, чтобы отправить
пользовательскую функцию на воркеры. Для вас это значит: `cloudpickle` спасает от
`AttributeError: Can't pickle local object`, но привязка становится ещё жёстче — байт-код
Python несовместим между минорными версиями, поэтому артефакт, сделанный на Python 3.11,
не гарантированно читается на 3.12.

> 🌱 **База.** Если вы только начинаете: для scikit-learn/LightGBM/CatBoost используйте
> `joblib` и обязательно кладите рядом lock-файл окружения. Для нейросетей — `safetensors`
> для весов плюс код модели в репозитории. Для передачи модели в другой язык или другой
> рантайм — ONNX. Остальное — детали, к которым вы вернётесь, когда упрётесь.

## 4. ONNX: граф, opset и места, где конверсия ломается

Идея ONNX (Open Neural Network Exchange) — вынуть модель из фреймворка. Вместо «объект Python
класса `RandomForestClassifier`» получается **описание вычисления**, которое умеет исполнить
любой совместимый рантайм: ONNX Runtime на C++, TensorRT, браузер через WebAssembly, мобильный
телефон. Кода Python в файле нет вообще — значит, нет и проблемы [§2.1](#21-произвольное-выполнение-кода).

### 4.1. Что лежит внутри

Файл `.onnx` — это protobuf со структурой:

- **Граф** — список узлов (nodes). Узел = оператор (`MatMul`, `Gemm`, `Relu`, `TreeEnsembleRegressor`)
  плюс имена входных и выходных тензоров плюс атрибуты. Порядок узлов топологический:
  граф ациклический, циклы выражаются специальными операторами `Loop` и `Scan`.
- **Инициализаторы** (initializers) — константные тензоры, то есть обученные веса.
- **Входы и выходы** с типами и формами. Ось можно объявить динамической, назвав её строкой:
  `[batch, 100]` вместо `[32, 100]`.
- **opset_import** — версия набора операторов.

**opset** (operator set) — ключевое понятие, вокруг которого крутятся все проблемы совместимости.
Это версия «языка»: семантика операторов фиксируется в конкретной версии opset и потом не меняется,
а изменения приходят новой версией. Например, в opset 13 у `Squeeze` оси переехали из атрибута
во второй вход — то есть один и тот же по названию оператор в opset 12 и 13 устроен по-разному.
Рантайм заявляет, до какого opset он умеет. Отсюда правило: **экспортируйте в opset, который
поддерживает ваш прод-рантайм, а не самый свежий.** Экспорт в opset 21 при ONNX Runtime,
понимающем 17, даст ошибку загрузки — и хорошо, если на этапе CI, а не при выкатке.

### 4.2. Экспорт и обязательная проверка

```python
# Экспорт scikit-learn-пайплайна (вместе с препроцессингом!) в ONNX и проверка эквивалентности.
import numpy as np
import onnxruntime as ort
from skl2onnx import to_onnx

# pipeline уже обучен: StandardScaler -> LogisticRegression, X_val: np.ndarray (n, d) float32
onnx_model = to_onnx(
    pipeline,
    X_val[:1].astype(np.float32),   # по образцу определяются типы и формы входа
    target_opset=17,                # ФИКСИРУЕМ opset под версию рантайма в проде
    options={id(pipeline): {"zipmap": False}},  # иначе вероятности приедут списком словарей
)
with open("model.onnx", "wb") as f:
    f.write(onnx_model.SerializeToString())

sess = ort.InferenceSession("model.onnx", providers=["CPUExecutionProvider"])
input_name = sess.get_inputs()[0].name

p_native = pipeline.predict_proba(X_val)[:, 1]
p_onnx = sess.run(None, {input_name: X_val.astype(np.float32)})[1][:, 1]

# Численная проверка — обязательная часть конверсии, а не «на всякий случай».
max_abs = np.abs(p_native - p_onnx).max()
disagree = np.mean((p_native > 0.5) != (p_onnx > 0.5))
print(f"max|Δp| = {max_abs:.2e}, доля расхождений по классу = {disagree:.5f}")
assert max_abs < 1e-5, "конверсия изменила модель"
assert disagree < 1e-4, "расхождение по решениям слишком велико"
```

Почему проверка не формальность. Scikit-learn считает в `float64`, ONNX-операторы деревьев —
в `float32`. Разница в предсказании порядка $10^{-7}$ безобидна, пока значение не лежит вплотную
к порогу: тогда объект перескакивает через границу и класс меняется. На выборке в 10⁵ объектов
доля таких перескоков обычно $10^{-5}$–$10^{-4}$ — приемлемо для скоринга, но неприемлемо, если
вы обещали бизнесу побитовое совпадение с офлайн-расчётом. Проверять надо всегда на реальных
данных валидации, а не на случайном шуме: шум не попадает в узкие места распределения.

### 4.3. Где конверсия ломается

Все известные грабли сводятся к одному: **ONNX описывает статический граф, а Python — нет.**

| Что в коде | Что происходит при экспорте | Что делать |
|---|---|---|
| `if x.sum() > 0:` в `forward` | `torch.onnx.export` работает трассировкой: прогоняет один пример и записывает, какие операции реально выполнились. Ветка, не выполнившаяся на этом примере, в граф не попадёт — модель молча станет другой | переписать без ветвления, либо `torch.jit.script`, либо экспорт через `torch.onnx.export(..., dynamo=True)` |
| `for i in range(x.shape[0])` | цикл разворачивается на длину примера: граф зафиксирует ровно 32 итерации | векторизовать; в крайнем случае оператор `Loop` |
| `.item()`, `int(x)`, `x.tolist()` внутри `forward` | тензор превращается в питоновское число, связь с графом рвётся — значение зашивается константой | убрать из forward, вынести в постобработку |
| кастомный слой / незнакомый оператор | `Unsupported operator` при экспорте | выразить через стандартные операторы либо реализовать custom op в рантайме |
| динамический размер батча | без `dynamic_axes` в граф зашьётся batch=1 | `dynamic_axes={"input": {0: "batch"}, "output": {0: "batch"}}` |
| строки, словари, вложенные структуры на входе | не тип ONNX | токенизация/кодирование остаётся снаружи графа, вход — только тензоры |
| CatBoost с категориальными фичами | категории обрабатываются логикой, слабо выражаемой в графе | использовать нативный экспорт CatBoost или оставить нативный формат |

> 🧠 **Middle+.** Практический выигрыш от ONNX стоит называть числами, а не словом «быстрее».
> Типичная картина на CPU: небольшая полносвязная сеть или бустинг на сотне признаков —
> ускорение в 1.5–4× относительно вызова через Python-фреймворк, прежде всего за счёт
> исчезновения питоновского оверхеда на вызов и за счёт слияния операторов (fusion).
> Для BERT-подобного энкодера на CPU ONNX Runtime даёт порядка 2–3×, а с квантизацией
> в int8 — ещё 2–3× сверху при падении качества в пределах 1% (детали —
> в [NLP в продакшене](../04-nlp/06-nlp-in-production.md) и
> [оптимизации инференса](09-inference-optimization.md)). На GPU для крупных
> трансформеров выигрыш меньше: там всё упирается в те же ядра CUDA, и специализированные
> рантаймы вроде TensorRT дают больше.

## 5. TorchScript, torch.export и safetensors

**TorchScript** — способ вынуть модель из Python внутри экосистемы PyTorch: сериализуется
граф плюс веса, загрузить можно из C++ (`libtorch`) без интерпретатора Python. Два режима:

- `torch.jit.trace(model, example)` — трассировка, с ровно теми же ограничениями, что у экспорта
  ONNX: динамический control flow теряется;
- `torch.jit.script(model)` — компиляция подмножества Python: `if`/`for` сохраняются, но код
  должен быть типизирован и укладываться в поддерживаемое подмножество языка (никаких
  произвольных библиотек внутри `forward`).

TorchScript сейчас в режиме поддержки, а стратегическое направление — `torch.export`
и `torch.compile`. На собеседовании достаточно знать разницу trace/script и то, зачем это
вообще нужно (инференс без Python, отсутствие GIL, деплой на мобильные и в C++-сервисы).

Отдельный факт, который многие упускают: **`torch.save(model)` — это pickle.** И `state_dict`
тоже сохраняется через pickle, просто внутри лежат только тензоры и строки, поэтому
`torch.load(..., weights_only=True)` может проверять это безопасно.

**safetensors** решает ровно эту проблему. Формат простой до примитивности: 8 байт длины
заголовка, JSON-заголовок с описанием каждого тензора (`dtype`, `shape`, смещения в файле),
дальше подряд сырые байты тензоров. Что это даёт:

- **исполнения кода нет вообще** — парсер читает JSON и мапит байты, вызывать нечего;
- **zero-copy загрузка через mmap** — тензоры не копируются в память процесса при чтении.
  Для модели на 7 млрд параметров в fp16 (≈14 ГБ) это разница между десятками секунд
  и единицами секунд на NVMe, что напрямую бьёт по времени холодного старта пода;
- **можно прочитать один тензор**, не поднимая весь файл — удобно для шардированных чекпоинтов.

Чего safetensors не делает: он **не хранит архитектуру**. Это контейнер весов. Код модели
должен приехать отдельно — из репозитория, зафиксированный коммитом. На практике это скорее
плюс: код в git ревьюится и версионируется, в отличие от байт внутри pickle.

## 6. Сравнение форматов: что выбирать

| Формат | Исполняет код при загрузке | Переносимость | Хранит препроцессинг | Типичное применение |
|---|---|---|---|---|
| `pickle` | да | только тот же Python + те же версии библиотек | да, если это `Pipeline` | быстрый обмен внутри одной команды, никогда — из недоверенного источника |
| `joblib` | да (тот же протокол) | то же | да | прод для sklearn/LGBM/CatBoost при жёстком lock-файле |
| нативный формат бустинга (`.txt` LightGBM, `.cbm` CatBoost, `.json` XGBoost) | нет | между версиями библиотеки и языками (C++/Java/Go) | нет | прод для бустингов; сильно недооценённый вариант |
| `ONNX` | нет | любой ONNX-рантайм, любой язык | да, если препроцессинг вошёл в граф | кросс-языковой инференс, ускорение на CPU, edge |
| `TorchScript` | нет (граф) | PyTorch/libtorch, C++ | частично | инференс PyTorch без Python |
| `safetensors` | нет | любой, кто умеет читать формат | нет (только тензоры) | веса нейросетей, LLM, публичные хабы |

Практическая рекомендация по типам моделей:

- **Бустинг (LightGBM/XGBoost/CatBoost)** — нативный формат библиотеки, а не pickle:
  он стабилен между версиями и читается из других языков. Препроцессинг тогда отдельно,
  но явно и с тестом.
- **scikit-learn пайплайн** — joblib с жёстким lock-файлом либо ONNX, если сервис не на Python
  или нужна скорость.
- **Нейросеть на PyTorch** — safetensors для весов + код модели из git; ONNX или TensorRT,
  если инференс требует оптимизации.
- **LLM** — safetensors, вариантов практически нет.

## 7. Контракт входа и выхода

Контракт — это ответ на вопрос «что именно можно прислать модели и что она обещает вернуть».
Он должен существовать в виде **исполняемого кода**, а не в виде абзаца в Confluence, иначе
он протухнет за два спринта.

Главная опасность здесь — молчаливые ошибки. Если вы передадите массив с переставленными
местами колонками `age` и `income`, модель не упадёт: формы совпадают, типы совпадают.
Она просто начнёт предсказывать чушь, и вы узнаете об этом через неделю по бизнес-метрике.

```python
# schema.py — контракт живёт рядом с моделью и версионируется вместе с ней.
from typing import Literal
from pydantic import BaseModel, Field, ConfigDict, field_validator

FEATURE_ORDER: tuple[str, ...] = ("age", "income", "n_orders_30d", "days_since_last_order")

class ScoreRequest(BaseModel):
    # extra="forbid" ловит опечатки в именах полей: лучше 422, чем тихо проигнорированное поле.
    model_config = ConfigDict(extra="forbid")

    user_id: str = Field(min_length=1, max_length=64)
    age: int = Field(ge=14, le=100)                  # границы — из статистики трейна, не с потолка
    income: float = Field(ge=0, le=1e8)
    n_orders_30d: int = Field(ge=0, le=1000)
    days_since_last_order: float | None = Field(default=None, ge=0, le=3650)
    channel: Literal["web", "ios", "android"]

    @field_validator("income")
    @classmethod
    def clip_income(cls, v: float) -> float:
        # На обучении доход клипался 99-м перцентилем. Если этого не сделать в сервисе,
        # выброс уедет за пределы виденного моделью диапазона -> непредсказуемое предсказание.
        return min(v, 5_000_000.0)

class ScoreResponse(BaseModel):
    user_id: str
    score: float = Field(ge=0.0, le=1.0)
    model_version: str          # какая версия ответила — попадает в логи и в разбор инцидентов
    contract_version: str = "1.2.0"
    degraded: bool = False      # True, если часть фич подставлена дефолтами
```

Три решения, заложенные в этот код, стоит проговорить.

**Границы значений берутся из обучающей выборки.** `age: ge=14, le=100` — не «здравый смысл»,
а перцентили 0.1% и 99.9% трейна. Значение вне них означает, что мы вышли из области,
где модель что-то видела, и лучше явно вернуть 422 или пометить ответ `degraded`, чем
экстраполировать вслепую.

**`extra="forbid"`.** Клиент прислал `n_orders_30` вместо `n_orders_30d` — с разрешёнными
extra-полями вы получите пропуск и молча испорченное предсказание. С `forbid` — немедленную
ошибку валидации на этапе интеграции.

**Порядок признаков фиксирован в одном месте** (`FEATURE_ORDER`) и используется и при обучении,
и в сервисе. Строить матрицу нужно по именам, а не полагаться на порядок ключей словаря:

```python
import numpy as np

def to_matrix(reqs: list[ScoreRequest]) -> np.ndarray:
    rows = [[getattr(r, name) if getattr(r, name) is not None else -1.0
             for name in FEATURE_ORDER] for r in reqs]
    # -1.0 как маркер пропуска — то же значение, что использовалось при обучении.
    # Любое другое значение здесь = train/serve skew.
    return np.asarray(rows, dtype=np.float32)
```

> 💬 **На собеседовании.** Спросят: «Как вы гарантируете, что сервис подаёт модели признаки
> в том же виде, что и при обучении?»
> Хороший ответ: три уровня. Первый — препроцессинг едет внутри артефакта (Pipeline или граф),
> а не дублируется в коде сервиса. Второй — схема входа описана исполняемым контрактом
> (pydantic), порядок признаков берётся из одной константы, общей для обучения и сервинга,
> дефолты для пропусков зафиксированы там же. Третий — тест на эквивалентность: берём
> N реальных запросов из лога, прогоняем через офлайн-пайплайн и через сервис, сравниваем
> предсказания с допуском; этот тест стоит в CI и в smoke-тесте после выката. Плюс мониторинг
> распределений фич на входе сервиса против трейна.
> Плохой ответ: «мы аккуратно пишем код» или «делаем ревью».

## 8. Версии зависимостей и lock-файлы

`requirements.txt` со строками вида `scikit-learn>=1.2` — это мина замедленного действия.
Образ, собранный сегодня и месяц назад, содержит разные библиотеки; воспроизвести старый прод
невозможно; артефакт pickle, обученный в июне, перестаёт грузиться в июле.

Нужны **два файла**: список прямых зависимостей и полный lock со всеми транзитивными
зависимостями и хешами.

```text
# requirements.in — то, что мы объявляем сами, читаемо человеком
scikit-learn==1.5.2
lightgbm==4.5.0
numpy==2.1.3
fastapi==0.115.5
uvicorn[standard]==0.32.1
pydantic==2.10.2
```

```bash
# Компиляция полного дерева с хешами: uv (быстрее) или pip-tools.
uv pip compile requirements.in -o requirements.txt --generate-hashes

# Установка строго по локу: --require-hashes падает, если пакет подменили в зеркале.
uv pip install --require-hashes -r requirements.txt
```

Что даёт `--generate-hashes`: установка проверяет SHA-256 каждого колеса. Это защита
от компрометации зеркала PyPI и от «тот же номер версии, другое содержимое».

Два правила поверх этого:

1. **Обучение и сервинг собираются из одного и того же lock-файла.** Практический способ —
   базовый образ с зависимостями, от которого наследуются и образ тренировки, и образ сервиса.
   Тогда «у меня локально другой numpy» перестаёт быть возможным состоянием.
2. **Lock-файл — часть артефакта модели.** Он кладётся в реестр рядом с весами. При откате
   на модель трёхмесячной давности вам нужен её lock, а не текущий.

> ⚠️ **Типичная ошибка.** Закрепить версии Python-пакетов и забыть про версию самого Python
> и про системные библиотеки. Артефакт cloudpickle, сделанный на 3.11, ломается на 3.12;
> модель на GPU требует совпадения ветки CUDA и драйвера. Поэтому фиксируется именно
> **образ целиком** (см. [Docker и k8s](06-docker-and-k8s.md)), и в метаданных модели
> хранится digest образа, в котором она обучалась.

## 9. Версионирование модели

Модель — не библиотека, но семантическое версионирование (`MAJOR.MINOR.PATCH`) к ней
приспосабливается хорошо, если договориться, что означает каждое число. Рабочая схема:

| Разряд | Когда увеличиваем | Что должен сделать потребитель |
|---|---|---|
| **MAJOR** | сломан контракт: изменился набор или семантика входов, изменился формат ответа, поменялся смысл score (было «вероятность клика», стало «ожидаемая выручка») | обязательно менять код клиента; выкатывается через новый эндпоинт или новую версию API |
| **MINOR** | контракт тот же, изменилась модель: другая архитектура, другие гиперпараметры, добавлены признаки, вычисляемые внутри артефакта | ничего не менять, но обязателен A/B или канареечная выкатка: качество может измениться в любую сторону |
| **PATCH** | тот же код, то же множество признаков, переобучение на свежих данных | ничего; выкатывается автоматически после прохождения гейт-метрик |

Ключевой момент, который отличает версионирование модели от версионирования кода:
**одной версии кода соответствует много версий модели.** Поэтому в метаданных обязаны быть
все три координаты — версия модели, коммит кода обучающего пайплайна и версия/срез данных:

```
model: churn-scoring 2.3.7
  code: git 9f2ac41 (pipeline/train_churn.py)
  data: snapshot 2026-07-19, окно обучения 2025-07-20..2026-07-19
  env:  image registry.internal/ml-base:py3.11-sklearn1.5.2@sha256:1a2b...
```

Восстановить модель по такой записи можно даже через год. Без любой из трёх строк —
уже нет.

> 🧠 **Middle+.** Отдельная тонкость — версия признаков. Если фича `avg_check_30d` считается
> в feature store и её формулу поменяли (например, стали исключать возвраты), модель формально
> не изменилась, а её поведение изменилось. Это самый неприятный класс инцидентов, потому что
> git-историю модели он не задевает. Отсюда требование к feature store: определение фичи
> версионируется, а модель фиксирует **версии фич**, на которых обучалась. Подробнее —
> в главе про [данные и feature store](03-data-and-feature-store.md).

## 10. Метаданные и model card

Метаданные отвечают на вопросы, которые задают в двух ситуациях: при разборе инцидента
(«кто это выкатил, на чём обучено, какие метрики были?») и при аудите («на каких данных,
на каких сегментах проверяли, какие ограничения?»). Идея **model card** — карточки модели,
предложенная в работе Mitchell et al., 2019 — как раз в том, чтобы это был обязательный
документ, а не устная традиция.

Машиночитаемая часть, которая должна лежать рядом с весами:

```json
{
  "name": "churn-scoring",
  "version": "2.3.7",
  "task": "binary_classification",
  "created_at": "2026-07-20T03:14:07Z",
  "created_by": "ci/train-churn#4821",
  "framework": {"lightgbm": "4.5.0", "python": "3.11.9"},
  "artifact": {
    "format": "lightgbm_txt",
    "path": "s3://ml-registry/churn/2.3.7/model.txt",
    "sha256": "c1d9...f30a",
    "size_bytes": 18734211
  },
  "contract_version": "1.2.0",
  "features": ["age", "income", "n_orders_30d", "days_since_last_order"],
  "feature_store_view": "user_profile_v4",
  "training": {
    "data_snapshot": "2026-07-19",
    "window": ["2025-07-20", "2026-07-19"],
    "rows": 41238907,
    "positive_rate": 0.0731,
    "code_commit": "9f2ac41",
    "base_image": "registry.internal/ml-base:py3.11-lgbm4.5.0@sha256:1a2b"
  },
  "metrics": {
    "roc_auc": 0.8412, "pr_auc": 0.3106, "brier": 0.0598,
    "roc_auc_by_segment": {"ios": 0.8501, "android": 0.8377, "web": 0.8290},
    "eval_window": ["2026-06-20", "2026-07-19"]
  },
  "latency_ms": {"p50_batch_1000": 38.4, "p99_batch_1000": 61.2},
  "limitations": [
    "не валидирована на пользователях младше 18 (доля в трейне < 0.1%)",
    "качество падает на пользователях с историей короче 7 дней (ROC-AUC 0.71)"
  ],
  "fallback_model": "churn-scoring 2.3.6"
}
```

Три поля здесь стоят особняком, потому что их обычно забывают.

`sha256` артефакта: сервис при загрузке пересчитывает хеш и сверяет. Это ловит и порчу файла
при выкачке, и подмену — прямая контрмера к [§2.1](#21-произвольное-выполнение-кода).

`roc_auc_by_segment`: агрегированная метрика скрывает деградацию на важном сегменте.
Разбивка обязана быть в карточке, а не в чьём-то ноутбуке.

`limitations` и `fallback_model`: первое — единственное место, где честно написано, где модель
врёт; второе — на что переключаться при откате. Эти два поля превращают карточку из отчётности
в рабочий инструмент дежурного.

## 11. Реестр моделей, стадии и откат

**Реестр моделей** (model registry) — сервис, который отвечает на вопрос «какой артефакт сейчас
считается продовым для задачи X» и хранит историю ответов. Без него эту роль играет чей-то
скрипт с захардкоженным путём к S3, и откат превращается в раскопки.

Классическая схема стадий: `None → Staging → Production → Archived`. Модель регистрируется,
проходит проверки, продвигается в Staging (там на неё смотрят shadow-трафиком), затем
в Production, а вытесненная версия уходит в Archived. Важно: MLflow, начиная с версии 2.9,
объявил стадии устаревшими в пользу **алиасов и тегов** — потому что стадий всегда оказывалось
мало (нужны ещё `champion`, `challenger`, версия для конкретного региона). Алиас — это
именованный указатель на конкретную версию:

```python
import mlflow
from mlflow import MlflowClient

client = MlflowClient()

# 1. Регистрация версии из завершённого рана обучения
mv = mlflow.register_model(
    model_uri=f"runs:/{run_id}/model",
    name="churn-scoring",
)

# 2. Метаданные и гейт-метрики в тегах — по ним потом принимается решение о продвижении
client.set_model_version_tag("churn-scoring", mv.version, "roc_auc", "0.8412")
client.set_model_version_tag("churn-scoring", mv.version, "data_snapshot", "2026-07-19")
client.set_model_version_tag("churn-scoring", mv.version, "code_commit", "9f2ac41")

# 3. Продвижение = переброс алиаса. Это атомарная операция и единственная точка правды.
client.set_registered_model_alias("churn-scoring", alias="challenger", version=mv.version)
# ... канареечная выкатка, сравнение метрик ...
client.set_registered_model_alias("churn-scoring", alias="champion", version=mv.version)

# 4. Сервис всегда грузит по алиасу, а не по номеру версии — тогда откат не требует деплоя.
model = mlflow.pyfunc.load_model("models:/churn-scoring@champion")
```

### Откат

Откат — это то, что вы будете делать в три часа ночи, и его дизайн важнее, чем дизайн выкатки.
Требование одно: **откат должен быть переключением указателя, а не пересборкой чего-либо.**

Правильная схема: сервис при старте (и по сигналу) читает из реестра, какая версия сейчас
`champion`, скачивает артефакт, проверяет хеш, поднимает рядом со старой и переключает трафик.
Тогда откат = вернуть алиас на предыдущую версию, время — секунды-минуты.

Антипаттерн: версия модели вшита в Docker-образ. Тогда откат = пересобрать образ и выкатить
деплой; это 10–30 минут в лучшем случае и невозможно, если сборка сломана. У вшивания есть
и плюс — полная воспроизводимость и отсутствие сетевой зависимости при старте, — поэтому
компромисс такой: **артефакт вшит в образ, но версия образа переключается одной командой,
а предыдущий образ гарантированно лежит в реестре и не вычищается ретенцией.**
`kubectl rollout undo deployment/scoring` в этом случае и есть откат.

Чек-лист готовности к откату, который стоит проговорить на собеседовании:

- предыдущая версия артефакта не удалена (ретенция минимум N последних версий и все,
  что были в проде за 90 дней);
- сохранён её lock-файл и образ окружения;
- контракт совместим (иначе откат модели требует и отката клиента — это MAJOR-версия);
- фичи, которых требует старая модель, всё ещё считаются в feature store (типичная ловушка:
  выкатили новую модель, выключили расчёт «ненужных» старых фич, откатиться уже нельзя);
- процедура отката прогоняется учебно раз в квартал, иначе на боевом инциденте выяснится,
  что она не работает.

> 💬 **На собеседовании.** Спросят: «Модель в проде начала выдавать заниженные скоры,
> бизнес-метрика падает. Ваши действия?»
> Хороший ответ: сначала останавливаем ущерб, потом разбираемся. Откат на предыдущую версию
> через переключение алиаса/образа — минуты; параллельно смотрим, что изменилось: новая версия
> модели, новая версия фич, изменение входных данных. Ключевой инструмент — логи предсказаний
> с версией модели и версией контракта в каждой записи: они позволяют сравнить распределения
> скоров до и после и локализовать момент. Разбор — постмортем, а не в момент инцидента.
> Плохой ответ: «начну искать причину в коде модели» — вы оставили проблему в проде
> на время расследования.

## 12. Подводные камни

**`ModuleNotFoundError: No module named 'sklearn.ensemble.forest'` при загрузке артефакта.**
Симптом: старая модель не грузится в новом образе.
Причина: pickle хранит полный путь к классу, библиотека переименовала модуль.
Что делать: грузить в окружении, зафиксированном lock-файлом модели (он должен быть в реестре);
на будущее — уйти с pickle на нативный формат бустинга/ONNX либо жёстко связать артефакт
и образ одним digest.

**Предсказания сервиса и офлайн-расчёта расходятся на 2–5%.**
Симптом: одна и та же модель, одни и те же входы, разные ответы.
Причина: почти всегда препроцессинг живёт в двух местах и разошёлся — разное заполнение
пропусков, разный порядок колонок, разный клип выбросов, разные `dtype` (`float64` против
`float32`).
Что делать: перенести препроцессинг внутрь артефакта; поставить в CI тест эквивалентности
на N сохранённых реальных запросах; логировать в проде сам вектор фич, а не только вход.

**Сервис поднимается 4 минуты и не проходит probe.**
Симптом: под перезапускается по кругу, деплой не завершается.
Причина: `joblib.load` со сжатием + скачивание 400 МБ артефакта из S3 при старте.
Что делать: хранить несжатый артефакт (или распаковывать при сборке образа), грузить
с `mmap_mode="r"`, вшивать веса в образ либо использовать init-контейнер и общий том;
в Kubernetes обязательно настроить `startupProbe` (см. [Docker и k8s](06-docker-and-k8s.md)).

**Память процесса × число воркеров.**
Симптом: под с 4 ГБ лимита получает OOMKilled после включения `--workers 8`.
Причина: каждый воркер загружает свою копию модели: 8 × 400 МБ = 3.2 ГБ только на веса.
Что делать: считать память как «модель × воркеры + рантайм»; использовать
`joblib.load(mmap_mode="r")` для разделения страниц; либо один процесс с внутренним
батчингом вместо восьми (см. [сервинг, раздел про GIL](05-serving-architectures.md)).

**Модель обучена на 300 признаках, а в сервисе их 299.**
Симптом: тихая деградация качества, ошибок нет.
Причина: фича выведена из строя в feature store, а сервис подставил дефолт.
Что делать: контракт должен требовать явного присутствия всех признаков; факт подстановки
дефолта — считаемая метрика (`degraded_features_total`) с алертом; в ответе флаг `degraded`.

**После обновления библиотеки метрики упали на 1.5 пункта.**
Симптом: артефакт грузится, warning проигнорирован, качество просело.
Причина: изменилась реализация внутри библиотеки — обработка пропусков, порядок обхода,
поведение при равных порогах.
Что делать: превращать `InconsistentVersionWarning` в ошибку; при плановом обновлении
библиотек — переобучать модель и прогонять полную офлайн-оценку, а не просто загружать
старый артефакт.

**Артефакт весит 2.3 ГБ и хранится в git.**
Симптом: `git clone` занимает 15 минут, CI тормозит.
Причина: бинарники попали в историю git.
Что делать: артефакты — в объектном хранилище/реестре моделей, в git — только ссылка и хеш
(DVC, MLflow, LFS как крайний вариант). Уже попавшее в историю чистится отдельно и болезненно.

## 13. Проверь себя

<details>
<summary><b>🎯 Вопрос.</b> Почему нельзя просто отдать в прод файл model.pkl?</summary>

**Короткий ответ.** Потому что pickle исполняет код при загрузке и жёстко привязан к версиям
библиотек, а сам по себе он не содержит ни препроцессинга, ни контракта входа, ни метаданных —
то есть не является полным артефактом.

**Развёрнуто.** Три независимые проблемы. Безопасность: протокол pickle содержит инструкцию
`REDUCE`, вызывающую произвольный callable, поэтому загрузка недоверенного файла эквивалентна
запуску чужого кода. Совместимость: в файле лежат полные имена классов
(`sklearn.ensemble._forest.RandomForestClassifier`), при переименовании модуля загрузка падает,
а при изменении набора атрибутов — работает, но неправильно. Полнота: без препроцессинга,
порядка признаков, дефолтов для пропусков и версии модель невозможно ни корректно вызвать,
ни откатить. Правильная упаковка — артефакт (лучше в формате без исполнения кода) + lock-файл
окружения + исполняемый контракт I/O + метаданные + запись в реестре.

**Чего ждёт интервьюер:** что вы знаете механизм, а не лозунг «pickle небезопасен», и что
понимаете: артефакт — это больше, чем веса.

**Провал:** «pickle плохой, надо использовать ONNX» без объяснения, почему именно.
</details>

<details>
<summary><b>🎯 Вопрос.</b> Что такое opset в ONNX и зачем он вам?</summary>

**Короткий ответ.** Версия набора операторов: она фиксирует семантику каждого оператора.
Экспортировать нужно в тот opset, который поддерживает прод-рантайм, иначе модель не загрузится.

**Развёрнуто.** ONNX-файл содержит граф из узлов-операторов и объявляет `opset_import`.
Семантика оператора в конкретной версии opset неизменна, а изменения выходят новой версией:
например, у `Squeeze` в opset 13 оси переехали из атрибута во вход. Рантайм (ONNX Runtime,
TensorRT, WebAssembly-сборка) заявляет максимальный поддерживаемый opset. Отсюда практика:
target_opset задаётся явно и попадает в метаданные модели, а обновление рантайма в проде
и повышение opset — отдельные, независимо проверяемые изменения.

**Чего ждёт интервьюер:** понимания, что ONNX — это не «универсальный формат, который везде
работает», а контракт с версионированием, у которого есть совместимость.

**Провал:** «opset — это версия ONNX» без понимания, что это версия операторов и что она
ограничена рантаймом.
</details>

<details>
<summary><b>🧠 Вопрос.</b> В каких случаях конверсия PyTorch-модели в ONNX даст неправильный результат, а не ошибку?</summary>

**Короткий ответ.** Когда `forward` содержит зависящий от данных control flow, а экспорт идёт
трассировкой: выполнится одна ветка, и именно она зашьётся в граф. Ошибки не будет — будет
другая модель.

**Развёрнуто.** `torch.onnx.export` в классическом режиме прогоняет пример и записывает
фактически выполненные операции. Опасные конструкции: `if` по значению тензора, `for` по
`x.shape[0]` (развернётся в фиксированное число итераций), `.item()`/`int()` внутри `forward`
(значение станет константой), отсутствие `dynamic_axes` (batch зафиксируется). Проверка одна
и обязательная: прогнать валидационную выборку через нативную модель и через рантайм и сравнить
не только максимум модуля разности, но и долю расхождений по итоговому решению, на реальных
данных с разными длинами и размерами батча. Обход: `torch.jit.script`, экспорт через dynamo,
либо переписывание ветвлений в векторизованном виде.

**Чего ждёт интервьюер:** понимания разницы между трассировкой и компиляцией графа
и рефлекса «после конверсии — численный тест».

**Провал:** «если экспорт прошёл без ошибок, значит всё в порядке».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Чем safetensors лучше pickle и что он не умеет?</summary>

**Короткий ответ.** Не исполняет код (структура: JSON-заголовок + сырые байты, вызывать нечего)
и грузится zero-copy через mmap. Не хранит архитектуру модели — только тензоры.

**Развёрнуто.** Формат состоит из длины заголовка, JSON с описанием тензоров (dtype, shape,
смещения) и непрерывного блока данных. Отсюда два свойства: безопасность парсинга и загрузка
без копирования, что для модели на 14 ГБ означает секунды вместо десятков секунд — критично
для холодного старта пода при автоскейлинге. Плата: код модели должен приехать отдельно,
из git с фиксированным коммитом. На практике это не недостаток, а разделение ответственности:
код ревьюится и версионируется в git, веса лежат в объектном хранилище.

**Чего ждёт интервьюер:** понимания, что безопасность формата следует из его устройства,
и что «контейнер весов» — не то же самое, что «сериализованная модель».

**Провал:** «safetensors — это быстрый pickle».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Как вы версионируете модели? Что означает мажорная версия?</summary>

**Короткий ответ.** SemVer с явной семантикой: MAJOR — сломан контракт входа/выхода или изменился
смысл предсказания; MINOR — изменилась модель при том же контракте; PATCH — переобучение на свежих
данных тем же кодом. Плюс в метаданных фиксируются коммит кода и снимок данных.

**Развёрнуто.** Смысл разделения в том, что от разряда зависит процедура выката. PATCH может
катиться автоматически после гейт-метрик. MINOR требует канарейки или A/B, потому что качество
могло измениться в любую сторону. MAJOR требует согласованного изменения клиента и обычно
живёт как отдельная версия эндпоинта. Важно, что одной версии кода соответствует много версий
модели, поэтому версия модели самостоятельна, а воспроизводимость обеспечивается тройкой
«версия модели + коммит кода + снимок данных» плюс digest образа окружения. Отдельная тонкость —
версия определения фич: изменение формулы фичи меняет поведение модели, не меняя её артефакт.

**Чего ждёт интервьюер:** связи между разрядом версии и процедурой выкатки, а не пересказа
semver.org.

**Провал:** «увеличиваем номер при каждом переобучении» без различения случаев.
</details>

<details>
<summary><b>🧠 Вопрос.</b> Как устроен откат модели и что чаще всего мешает откатиться?</summary>

**Короткий ответ.** Откат — переключение указателя (алиас в реестре или предыдущий образ),
секунды-минуты. Мешает обычно то, что предыдущую версию нельзя воспроизвести: удалён артефакт,
не сохранён lock, выключен расчёт фич, которых она требует, или несовместим контракт.

**Развёрнуто.** Требование к дизайну: сервис грузит модель по алиасу (`models:/name@champion`)
или деплой откатывается через `kubectl rollout undo` — в обоих случаях без пересборки.
Мешают четыре вещи, и все они предотвращаются заранее: ретенция артефактов (хранить все версии,
что были в проде, минимум 90 дней) вместе с их lock-файлами и образами; запрет на удаление
фич из feature store, пока их использует хоть одна не-архивная версия; совместимость контракта
(несовместимость = MAJOR и требует отката клиента); и учебный прогон отката раз в квартал,
без которого процедура гарантированно окажется нерабочей в момент инцидента. Отдельно нужны
логи предсказаний с версией модели — иначе после отката нельзя доказать, что стало лучше.

**Чего ждёт интервьюер:** что вы проектируете откат заранее, а не импровизируете, и знаете
конкретные причины его отказа.

**Провал:** «откатим предыдущий коммит и пересоберём» — это десятки минут и зависимость
от работоспособности сборки.
</details>

<details>
<summary><b>🌱 Вопрос.</b> Чем joblib отличается от pickle и когда какой брать?</summary>

**Короткий ответ.** joblib — тот же протокол pickle, но numpy-массивы пишутся отдельными
сырыми блоками; отсюда быстрее чтение больших моделей и возможность `mmap_mode="r"`.
Безопасность та же, то есть никакая.

**Развёрнуто.** Для модели с большим числом массивов (случайный лес, большой бустинг) joblib
читается примерно вдвое быстрее и умеет отображать массивы в память, что важно при нескольких
процессах-воркерах: страницы разделяются ядром, и вместо восьми копий модели в RSS вы платите
примерно за одну. Сжатие `compress=3` уменьшает файл в 5–8 раз, но увеличивает время загрузки
в несколько раз — поэтому сжимают для хранения и передачи, а в рантайме держат несжатый файл.
Выбор между ними вторичен: обе опции небезопасны для недоверенных источников, и для бустингов
лучше нативный формат библиотеки, а для нейросетей — safetensors.

**Чего ждёт интервьюер:** знания про mmap и понимания, что joblib не решает проблему
безопасности.

**Провал:** «joblib безопаснее pickle».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Что должно лежать в реестре моделей помимо файла с весами?</summary>

**Короткий ответ.** Контракт I/O, lock-файл окружения (и digest образа), метаданные обучения
(снимок данных, окно, коммит кода), метрики целиком и по сегментам, замеры латентности,
ограничения применимости, хеш артефакта и ссылка на fallback-версию.

**Развёрнуто.** Реестр — это не хранилище файлов, а ответ на вопрос «что сейчас в проде
и как это воспроизвести». Практический тест полноты: сможет ли новый человек через полгода,
имея только запись в реестре, (а) поднять сервис с этой моделью, (б) воспроизвести обучение,
(в) объяснить регулятору, на каких данных она обучена и где не работает. Отсюда обязательные
поля: тройка «модель + код + данные», окружение с точностью до digest, метрики по сегментам
(агрегат прячет деградацию), latency (иначе выкатите модель, не влезающую в SLA), sha256 для
проверки целостности и явный список ограничений.

**Чего ждёт интервьюер:** понимания реестра как контракта между обучением и эксплуатацией.

**Провал:** «модель и метрика ROC-AUC».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Порядок колонок в матрице признаков перепутан. Как вы это обнаружите?</summary>

**Короткий ответ.** Никак, если полагаться на исключения: формы и типы совпадут, сервис
не упадёт. Обнаруживается только тестом эквивалентности офлайн↔онлайн и мониторингом
распределений признаков.

**Развёрнуто.** Это канонический пример молчаливой ошибки и главный аргумент за то, чтобы
матрица собиралась по именам из одной константы (`FEATURE_ORDER`), общей для обучения
и сервинга, а препроцессинг ехал внутри артефакта. Три уровня защиты: (1) артефакт хранит
имена признаков и проверяет их при вызове — LightGBM и XGBoost умеют, sklearn-пайплайн
с `ColumnTransformer` по именам тоже; (2) в CI прогоняется набор сохранённых реальных запросов
и сравниваются предсказания с офлайн-расчётом; (3) в проде мониторятся распределения каждой
фичи на входе модели против трейна — перестановка двух признаков с разными масштабами
немедленно видна по PSI.

**Чего ждёт интервьюер:** осознания класса «ошибок без исключений» и наличия против них
процедуры.

**Провал:** «поймаем на код-ревью».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Зачем нужен контракт входа, если модель всё равно принимает numpy-массив?</summary>

**Короткий ответ.** Затем, что массив не содержит ни имён, ни допустимых диапазонов,
ни правил обработки пропусков — а расхождение по любому из этих пунктов не вызывает ошибки,
только неправильные предсказания.

**Развёрнуто.** Контракт делает четыре вещи. Фиксирует имена и порядок — защита от перестановки.
Фиксирует границы значений, взятые из перцентилей трейна: вход вне диапазона означает
экстраполяцию, и лучше явно вернуть ошибку или пометить ответ как degraded. Фиксирует политику
пропусков (какое значение подставляем — то же, что при обучении). Фиксирует формат ответа,
включая версию модели, чтобы каждая запись лога была атрибутируема. Реализуется исполняемым
кодом (pydantic-схема, версионируемая вместе с моделью), а не документом: документ расходится
с реальностью за пару спринтов.

**Чего ждёт интервьюер:** понимания, что контракт — инструмент против train/serve skew,
а не бюрократия.

**Провал:** «валидацию делает фронтенд».
</details>

## 14. Практика

**Задача 1. Демонстрация опасности pickle (20 минут).**
Соберите класс с `__reduce__`, который при загрузке создаёт файл `/tmp/pwned`. Сериализуйте,
загрузите, убедитесь, что файл появился. Затем оберните загрузку: посчитайте SHA-256 файла
и сверьте с ожидаемым перед `pickle.loads`.
*Сделано правильно: вы можете за 30 секунд объяснить коллеге механизм и показать, что
проверка хеша — необходимое, но не достаточное условие (она защищает от подмены, а не
от изначально вредоносного артефакта).*

**Задача 2. Конверсия в ONNX с проверкой (60 минут).**
Обучите `Pipeline(StandardScaler, LogisticRegression)` на любом табличном датасете.
Экспортируйте в ONNX с `target_opset=17` и `zipmap=False`. Напишите тест: max|Δp| < 1e-5,
доля расхождений по классу < 1e-4 на всей валидации. Замерьте латентность обоих вариантов
на батчах 1, 32, 1000 (по 200 повторов, берите медиану).
*Сделано правильно: тест проходит; у вас есть таблица «батч → мс» для нативного вызова
и для ONNX Runtime; вы можете назвать, на каком размере батча выигрыш максимален и почему
(на маленьких батчах доминирует питоновский оверхед).*

**Задача 3. Сломать конверсию намеренно (30 минут).**
Напишите `nn.Module`, в `forward` которого есть `if x.mean() > 0`. Экспортируйте трассировкой,
подайте вход, попадающий в другую ветку, сравните с нативной моделью. Затем почините
через `torch.jit.script`.
*Сделано правильно: вы получили численно разные ответы без единой ошибки при экспорте
и понимаете, почему в реальном проекте это обнаружилось бы только по бизнес-метрике.*

**Задача 4. Полный артефакт (90 минут).**
Соберите директорию `artifacts/churn-2.3.7/`: модель в нативном формате, `schema.py`
с pydantic-контрактом, `requirements.txt` с хешами, `model_card.json` по образцу из [§10](#10-метаданные-и-model-card),
`load.py` с функцией `load_model(path)`, которая сверяет sha256 и валидирует версию библиотеки.
*Сделано правильно: коллега, у которого есть только эта директория и Docker, поднимает
предсказание на тестовом запросе за 10 минут без единого вопроса к вам. Это и есть критерий
упакованности.*

**Задача 5. Учебный откат (45 минут).**
Зарегистрируйте в локальном MLflow две версии модели, назначьте алиас `champion` второй,
поднимите сервис, который грузит по алиасу. Переключите алиас на первую версию и убедитесь,
что сервис подхватил её без перезапуска (или с перезапуском — но измерьте, за сколько).
*Сделано правильно: время отката измерено в секундах и записано; вы знаете, какая часть
процедуры самая медленная — обычно скачивание артефакта, и знаете, чем её ускорить.*

## 15. Что читать дальше

- [Документация модуля `pickle` (python.org)](https://docs.python.org/3/library/pickle.html) —
  раздел про безопасность и описание протокола. Читать, чтобы увидеть предупреждение
  в первоисточнике и понять механизм `__reduce__`.
- [ONNX: документация по версионированию и операторам (репозиторий onnx/onnx, папка docs)](https://github.com/onnx/onnx/blob/main/docs/Versioning.md) —
  как устроены IR version и opset, что означает совместимость. Обязательно перед первой
  конверсией в прод.
- [ONNX Runtime — официальный сайт и документация](https://onnxruntime.ai/) —
  провайдеры исполнения, квантизация, оптимизации графа. Смотреть, когда конверсия уже
  работает и надо ускоряться.
- [safetensors (документация Hugging Face)](https://huggingface.co/docs/safetensors/index) —
  описание формата на одной странице. Полезно прочитать целиком: формат простой, и понимание
  его устройства снимает вопросы о том, откуда берётся zero-copy.
- [TorchScript (документация PyTorch)](https://pytorch.org/docs/stable/jit.html) —
  разница `trace` и `script`, ограничения поддерживаемого подмножества Python.
- [Mitchell et al. «Model Cards for Model Reporting» (2019)](https://arxiv.org/abs/1810.03993) —
  откуда взялась идея карточки модели и что в ней должно быть. Полезно для аргументации,
  зачем нужны поля limitations и разбивка метрик по сегментам.
- [MLflow — официальная документация](https://mlflow.org/docs/latest/) — разделы Model Registry
  и Models. Обратите внимание на переход от стадий к алиасам и на формат `MLmodel`
  как на готовый пример метаданных артефакта.
- **Chip Huyen. «Designing Machine Learning Systems» (O'Reilly, 2022)** — глава про деплой
  и про model store: хорошая систематизация того, что должно храниться рядом с моделью.
- [Sculley et al. «Hidden Technical Debt in Machine Learning Systems» (NeurIPS 2015)](https://papers.nips.cc/paper/2015/hash/86df7dcfd896fcaf2674f757a2463eba-Abstract.html) —
  раздел про configuration debt и entanglement объясняет, почему артефакт без метаданных
  превращается в невоспроизводимый чёрный ящик.
