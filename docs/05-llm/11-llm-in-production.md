## 1. Проблема: прототип работает, продукт не сходится

Типичная история. Команда за две недели собрала ассистента: промпт, RAG, вызов API самой сильной
модели. На демо всё прекрасно. Дальше происходит следующее.

**Считают экономику.** 200 тысяч запросов в день, в каждом 4000 токенов контекста (системный промпт
+ пять документов из базы) и 400 токенов ответа. При цене топовой модели порядка \$5 за миллион входных и \$25 за миллион выходных токенов один запрос стоит

$$
c = \frac{4000 \cdot 5 + 400 \cdot 25}{10^6} = \frac{20\,000 + 10\,000}{10^6} = 0.03\ \text{доллара}
$$

то есть 6 000 долларов в день, около 180 тысяч в месяц. При среднем чеке продукта в несколько
долларов юнит-экономика не сходится ни при каком раскладе.

**Меряют латентность.** Пользователь ждёт 9 секунд до первого символа: сначала эмбеддинг запроса,
потом поиск, потом реранкер, потом модель обрабатывает 4000 токенов контекста. Половина
пользователей уходит, не дождавшись.

**Ловят первый инцидент.** В час пик провайдер отдаёт 429, сервис отвечает пятисотками, ретраи
без джиттера превращают всплеск в лавину.

**Обнаруживают, что качество поехало.** Провайдер обновил модель, ответы стали длиннее и мягче,
доля эскалаций на оператора выросла на 15%, а заметили это через три недели по жалобам, потому
что разметки в проде нет и качество никто не мерил.

Каждая из этих четырёх проблем решается известными приёмами. Эта глава — про них.

> 🌱 **База.** Если запомнить из главы одну вещь: **стоимость и латентность LLM-сервиса определяются
> не выбором модели, а архитектурой вокруг неё.** Кэширование, роутинг, сокращение контекста и
> дистилляция дают выигрыш в разы; смена модели на соседнюю по цене — десятки процентов.

## 2. Анатомия стоимости запроса

### 2.1 Формула

$$
c = \frac{T_{\text{in}}\, p_{\text{in}} + T_{\text{out}}\, p_{\text{out}}}{10^6}
$$

где $c$ — стоимость одного запроса в долларах, $T_{\text{in}}$ — число входных токенов,
$T_{\text{out}}$ — число выходных, $p_{\text{in}}$ и $p_{\text{out}}$ — цены за миллион токенов.

> 📐 **Разбор формулы.** Тривиальная арифметика, но из неё сразу следует главное: **выходные токены
> обычно в 4–5 раз дороже входных**, потому что генерация memory-bound и на каждый токен требует
> полного прохода по весам (подробный разбор — в [главе про инференс](05-inference-and-serving.md)).
> При этом в типичном RAG-сценарии $T_{\text{in}} \gg T_{\text{out}}$: 4000 против 400. Отсюда
> неочевидный вывод: в RAG-продуктах **вход обычно доминирует в счёте** несмотря на более низкую
> цену за токен — и первым рычагом становится сокращение контекста, а не сокращение ответа.

Проверим на числах примера из [§1](#1-проблема-прототип-работает-продукт-не-сходится): вход даёт $20\,000/10^6 = 0.02$, выход — $0.01$. Две трети счёта
приходятся на контекст. Убрав два документа из пяти, вы экономите больше, чем сократив ответ вдвое.

### 2.2 Что ещё входит в счёт, кроме токенов основной модели

| Статья | Типичная доля | Комментарий |
|---|---|---|
| Токены основной модели | 50–80% | то, о чём все думают |
| Эмбеддинги при индексации и поиске | 3–10% | индексация — разово, поиск — на каждый запрос |
| Реранкер (cross-encoder) | 5–15% | считает $k$ пар «запрос–документ» на каждый запрос |
| Классификаторы фильтров и роутера | 2–8% | дешёвые, но на каждом запросе |
| LLM-судья для мониторинга | 1–5% | зависит от доли сэмплирования |
| Ретраи и перегенерации | 5–20% | самая недооценённая статья |
| Хранение и трафик (векторная БД, логи) | 2–5% | растёт со временем, а не с нагрузкой |

**Ретраи заслуживают отдельного внимания.** Если 10% запросов ретраятся из-за таймаута или
невалидного JSON, вы платите за них дважды. Если агент делает в среднем 4 шага вместо
запланированных 2 — счёт удваивается. Считайте стоимость не «за вызов модели», а **за успешно
завершённую пользовательскую задачу**: это единственная метрика, которую можно сопоставить с
выручкой.

```python
from dataclasses import dataclass, field


@dataclass
class Price:
    """Цены за миллион токенов. Значения — иллюстративные, порядок величин
    середины 2026 года; подставляйте актуальные для своего провайдера."""
    input_per_mtok: float
    output_per_mtok: float
    cached_input_multiplier: float = 0.1    # чтение из кэша обычно ~0.1x базовой цены входа
    cache_write_multiplier: float = 1.25    # запись в кэш с коротким TTL дороже обычного входа


CATALOG = {
    "large":  Price(5.0, 25.0),
    "medium": Price(3.0, 15.0),
    "small":  Price(1.0, 5.0),
}


@dataclass
class RequestCost:
    tokens_in: int
    tokens_out: int
    tokens_cached_read: int = 0      # часть входа, прочитанная из кэша
    tokens_cached_write: int = 0     # часть входа, записанная в кэш на этом запросе
    retries: int = 0                 # сколько РАЗ пришлось повторить (0 = с первого раза)
    extra_usd: float = 0.0           # эмбеддинги, реранкер, классификаторы

    def total(self, price: Price) -> float:
        fresh_in = self.tokens_in - self.tokens_cached_read - self.tokens_cached_write
        cost_in = (
            fresh_in * price.input_per_mtok
            + self.tokens_cached_read * price.input_per_mtok * price.cached_input_multiplier
            + self.tokens_cached_write * price.input_per_mtok * price.cache_write_multiplier
        ) / 1e6
        cost_out = self.tokens_out * price.output_per_mtok / 1e6
        # ретрай оплачивается целиком: провайдер посчитал токены, даже если ответ мы выбросили
        return (cost_in + cost_out) * (1 + self.retries) + self.extra_usd


# Сценарий из §1, без кэша
naive = RequestCost(tokens_in=4000, tokens_out=400, extra_usd=0.0015)
print(f"без кэша:   ${naive.total(CATALOG['large']):.5f}")

# Тот же сценарий: системный промпт и документы (3600 токенов) читаются из кэша
cached = RequestCost(
    tokens_in=4000, tokens_out=400,
    tokens_cached_read=3600, extra_usd=0.0015,
)
print(f"с кэшем:    ${cached.total(CATALOG['large']):.5f}")

# И на модели классом ниже
print(f"small+кэш:  ${cached.total(CATALOG['small']):.5f}")
```

Прогнав этот код, вы увидите характерную картину: префиксный кэш срезает больше половины стоимости
входа, а переход на модель классом ниже — ещё в несколько раз. Дальше вся глава про то, как
получить это, не потеряв качество.

### 2.3 Семь рычагов снижения стоимости

По убыванию типичного эффекта:

1. **Сокращение контекста.** Меньше документов в RAG (4 вместо 10 после хорошего реранкера),
   более короткий системный промпт, обрезка истории диалога, суммаризация вместо полной истории.
   Эффект: до 2–3×. Риск: падение recall — обязательно замерять.
2. **Роутинг на модель меньшего класса** для простых запросов. Эффект: 2–5× на тех запросах,
   что ушли вниз. Риск: ошибка роутера.
3. **Префиксное кэширование.** Эффект: до 60–80% стоимости входа при стабильном префиксе.
   Риск: почти нулевой, если не ломать префикс.
4. **Точный кэш ответов.** Эффект: пропорционален доле повторов; в саппорте это 10–30%.
5. **Дистилляция в свою маленькую модель** для узкой массовой задачи. Эффект: 5–20×.
   Цена: недели работы и своя инфраструктура.
6. **Батч-режим** для всего, что не требует немедленного ответа (пакетная классификация, ночная
   обработка). Провайдеры дают за это скидку порядка 50%.
7. **Сокращение вывода**: явное ограничение длины, структурный вывод вместо прозы,
   `max_tokens` по факту нужного.

## 3. Своя модель против API: точка безубыточности

Это самый частый вопрос продуктовой секции собеседования, и на него нужно уметь отвечать формулой,
а не мнением.

### 3.1 Постановка

Сравниваем два варианта на горизонте месяца при потоке $n$ запросов.

**Вариант API.** Стоимость линейна по объёму, фиксированных затрат нет:

$$
C_{\text{api}}(n) = n \cdot \frac{T_{\text{in}} p_{\text{in}} + T_{\text{out}} p_{\text{out}}}{10^6}
$$

**Вариант «своя модель».** Стоимость складывается из аренды ускорителей и фиксированных расходов:

$$
C_{\text{own}}(n) = \underbrace{\frac{n \cdot T_{\text{out}}}{3600 \cdot s \cdot u} \cdot c_{\text{gpu}}}_{\text{переменная часть}} \;+\; \underbrace{C_{\text{fix}}}_{\text{постоянная часть}}
$$

где $s$ — эффективная пропускная способность одного ускорителя в выходных токенах в секунду
(измеренная **на вашем** профиле нагрузки, с учётом prefill), $u$ — средняя утилизация
(отношение фактической нагрузки к пиковой ёмкости; при неравномерном трафике реалистично 0.3–0.5),
$c_{\text{gpu}}$ — стоимость часа ускорителя, $3600$ — секунд в часе,
$C_{\text{fix}}$ — фиксированные затраты в месяц.

**Что входит в $C_{\text{fix}}$** — и здесь чаще всего ошибаются, занижая:

- доля времени инженеров на поддержку инференс-стека (обновления, инциденты, дежурство);
- резервная ёмкость на пик и на отказ зоны;
- мониторинг, логирование, хранение;
- разовые, амортизированные: подбор и квантизация модели, нагрузочное тестирование, дообучение.

Реалистичная нижняя оценка для небольшой команды — эквивалент 0.5–1 FTE инженера плюс инфраструктура,
то есть порядка 8–15 тысяч долларов в месяц. Занизив эту цифру, вы получите красивую презентацию и
неприятную реальность.

### 3.2 Вывод точки безубыточности

Приравниваем и выражаем $n$. Обозначим стоимость одного запроса в каждом варианте:

$$
c_{\text{api}} = \frac{T_{\text{in}} p_{\text{in}} + T_{\text{out}} p_{\text{out}}}{10^6},
\qquad
c_{\text{own}} = \frac{T_{\text{out}} \cdot c_{\text{gpu}}}{3600 \cdot s \cdot u}
$$

Тогда $C_{\text{api}}(n) = C_{\text{own}}(n)$ даёт $n\,c_{\text{api}} = n\,c_{\text{own}} + C_{\text{fix}}$, откуда

$$
\boxed{\;n^{*} = \frac{C_{\text{fix}}}{c_{\text{api}} - c_{\text{own}}}\;}
$$

при условии $c_{\text{api}} > c_{\text{own}}$ (иначе своя модель не окупается никогда — такое бывает
при сравнении с дешёвой моделью провайдера).

> 📐 **Разбор формулы.** Читается как классическая точка безубыточности: фиксированные затраты
> делим на экономию с одного запроса. Два следствия, которые надо проговаривать вслух.
> **Первое:** если $c_{\text{own}}$ близко к $c_{\text{api}}$ (вы сравниваете свою модель с дешёвой
> моделью провайдера), знаменатель мал и $n^*$ улетает в космос — своя модель не нужна.
> **Второе:** $n^*$ обратно пропорционально утилизации через $c_{\text{own}}$: при $u = 0.2$ вместо
> $0.5$ переменная стоимость своей модели вырастает в 2.5 раза, и порог сдвигается вверх.
> Неравномерный трафик — главный убийца экономики собственного хостинга.

### 3.3 Численный пример

```python
def breakeven(tokens_in, tokens_out, price_in, price_out,
              gpu_hourly, throughput_out_tps, utilization, fixed_monthly):
    """Точка безубыточности «своя модель vs API» в запросах в месяц.

    throughput_out_tps — ЭФФЕКТИВНАЯ пропускная способность в выходных токенах/с
    на один ускоритель, измеренная под вашим профилем (длина контекста, батчинг).
    Брать её из маркетинговых материалов бессмысленно: она падает в разы
    при длинном контексте и при малом батче.
    """
    c_api = (tokens_in * price_in + tokens_out * price_out) / 1e6
    c_own_var = tokens_out * gpu_hourly / (3600 * throughput_out_tps * utilization)
    if c_api <= c_own_var:
        return None, c_api, c_own_var          # своя модель не окупается никогда
    n_star = fixed_monthly / (c_api - c_own_var)
    return n_star, c_api, c_own_var


# Сценарий A: сравниваем свою 8B-модель с API модели СОПОСТАВИМОГО класса (дешёвой)
n_star, c_api, c_own = breakeven(
    tokens_in=4000, tokens_out=400,
    price_in=1.0, price_out=5.0,               # дешёвая модель провайдера
    gpu_hourly=2.5, throughput_out_tps=2500, utilization=0.4,
    fixed_monthly=10_000,
)
print(f"A: c_api=${c_api:.5f}, c_own_var=${c_own:.6f}, "
      f"безубыточность ≈ {n_star/1e6:.2f} млн запросов/мес "
      f"({n_star/30/86400:.2f} RPS в среднем)")

# Сценарий B: сравниваем ту же свою модель с API ТОПОВОЙ модели.
# Формально порог падает в разы — но это сравнение НЕЧЕСТНОЕ: качество разное.
n_star_b, c_api_b, _ = breakeven(
    tokens_in=4000, tokens_out=400,
    price_in=5.0, price_out=25.0,
    gpu_hourly=2.5, throughput_out_tps=2500, utilization=0.4,
    fixed_monthly=10_000,
)
print(f"B: c_api=${c_api_b:.5f}, безубыточность ≈ {n_star_b/1e6:.2f} млн запросов/мес")
```

Прогон даёт порядок величин: **при сравнении с дешёвой моделью провайдера безубыточность
наступает в районе нескольких миллионов запросов в месяц** — то есть примерно от одного-двух RPS
в среднем и заметно больше в пике.

> ⚠️ **Типичная ошибка.** Сравнивать стоимость своей 8B-модели с ценой топовой API-модели.
> Это сценарий B, и он некорректен: вы сравниваете два разных уровня качества. Честное сравнение
> требует сначала **зафиксировать качество** — прогнать обе модели на своём эвал-наборе
> (см. [оценку LLM](09-llm-evaluation.md)) и убедиться, что они в одном классе на **вашей** задаче.
> Часто оказывается, что своя дообученная 8B-модель на узкой задаче не хуже большой универсальной —
> и тогда сравнение честное. Но это надо показать, а не предположить.

### 3.4 Что не входит в формулу, но решает

| Фактор | В пользу API | В пользу своей модели |
|---|---|---|
| Скорость запуска | недели → дни | месяцы |
| Требования к данным | данные уходят наружу | всё внутри периметра; часто это решающий аргумент |
| Пиковая нагрузка | эластичность из коробки | нужен запас железа или автоскейл на дорогих ускорителях |
| Контроль версий | провайдер может обновить модель | вы фиксируете веса навсегда |
| Латентность | сетевой хоп + очередь провайдера | контроль над очередью, возможен хостинг рядом |
| Дообучение под домен | ограничено тем, что даёт провайдер | полная свобода (LoRA, полный fine-tune) |
| Кадры | не нужны специалисты по инференсу | нужны, и это дефицит |
| Риск | зависимость от вендора, изменение цен | вся операционная нагрузка на вас |

**Гибридная схема — самый частый ответ на практике.** Массовый узкий поток (классификация,
извлечение полей, короткие типовые ответы) — на своей маленькой модели; сложный хвост — через API
сильной модели. Ниже мы разберём, как этот хвост отделять.

> 💬 **На собеседовании.** Спросят: «Своя модель или API?» Худший ответ — категоричный в любую
> сторону. Хороший начинается с уточняющих вопросов: какой объём и профиль нагрузки, есть ли
> требования к локализации данных, какое качество нужно и померено ли оно, есть ли команда с
> компетенцией в инференсе, насколько неравномерен трафик. Дальше — формула
> $n^* = C_{\text{fix}}/(c_{\text{api}} - c_{\text{own}})$ с явным перечислением, что входит в
> $C_{\text{fix}}$, и оговорка, что сравнивать надо **при равном качестве на своей задаче**.
> И финал: на практике чаще всего выигрывает гибрид — своя маленькая модель на массовом потоке
> плюс API на сложном хвосте.

## 4. Кэширование

Три принципиально разных механизма, которые постоянно смешивают. У каждого своя область применения
и своя экономия.

### 4.1 Точный кэш (exact cache)

Ключ — хеш от всего, что влияет на ответ: нормализованный запрос, версия промпта, версия модели,
параметры декодинга, идентификаторы документов контекста. Попадание — отдаём сохранённый ответ,
модель не вызывается вообще.

Экономия при доле попаданий $h$: ровно $h$ от стоимости и от латентности. Никаких компромиссов по
качеству — ответ бит в бит тот же.

Где работает: FAQ, поддержка, справочные боты, любые потоки с повторяющимися формулировками.
Реальные hit rate — 10–30%, в узких доменах выше.

**Обязательные детали, которые ломают наивную реализацию:**

- **Персонализация.** Если ответ зависит от пользователя, ключ обязан включать то, от чего он
  зависит, иначе вы отдадите одному пользователю данные другого. Это не оптимизация, а инцидент
  безопасности (см. [предыдущую главу](10-llm-safety-and-guardrails.md)).
- **Версии в ключе.** Сменили промпт — кэш обязан инвалидироваться. Иначе после выката вы
  продолжите отдавать старые ответы и будете долго удивляться, почему метрика не сдвинулась.
- **TTL по свежести данных.** Ответ про статус заказа нельзя кэшировать на сутки.
- **Не кэшировать неудачи.** Ответ, забракованный фильтром или пользователем, в кэш не пишется.

### 4.2 Префиксное кэширование (prefix / prompt caching)

Механизм другой: кэшируется не ответ, а **KV-кэш вычисленного префикса промпта**. Если следующий
запрос начинается с тех же токенов, prefill по ним не повторяется.

Это то, что реализовано и внутри серверов инференса (radix-дерево префиксов в SGLang, автоматическое
префиксное кэширование в vLLM), и как оплачиваемая функция у провайдеров API.

**Экономика.** У провайдеров чтение из кэша стоит порядка $0.1\times$ обычной цены входа, а запись —
порядка $1.25\times$ (для короткого TTL). Пусть $f$ — доля входных токенов, попадающих в
кэшируемый префикс, $h$ — доля запросов, на которых префикс уже в кэше. Эффективный множитель к
стоимости входа:

$$
m = (1 - f) + f\big[h \cdot 0.1 + (1 - h)\cdot 1.25\big]
$$

где $(1-f)$ — некэшируемый хвост промпта (он оплачивается по полной), а в скобках — ожидаемая
стоимость кэшируемой части: с вероятностью $h$ читаем, иначе пишем.

> 📐 **Разбор формулы.** Подставим типичный RAG-случай: системный промпт и стабильные документы —
> 90% входа ($f = 0.9$), hit rate 90% ($h = 0.9$).
> $m = 0.1 + 0.9(0.09 + 0.125) = 0.1 + 0.194 = 0.294$ — то есть **экономия около 70% стоимости
> входа**. Теперь тот же расчёт при $h = 0.3$: $m = 0.1 + 0.9(0.03 + 0.875) = 0.915$ — экономии
> практически нет, а при низком $h$ и большом $f$ можно даже уйти **в минус** относительно варианта
> без кэша. Точка безубыточности по числу обращений к одному префиксу выводится из
> $1.25 + (k-1)\cdot 0.1 < k$: уже при $k = 2$ кэширование выгодно ($1.35 < 2$). Значит, критично
> не «сколько кэшируем», а **попадаем ли**.

**Главное правило префиксного кэша: кэш — это совпадение по префиксу, и любое изменение байта в
начале инвалидирует всё после него.** Отсюда — архитектурное требование к сборке промпта:

```
[стабильное] → [полустабильное] → [волатильное]
 инструменты    системный промпт   документы    история   текущий запрос
```

Что ломает кэш чаще всего (и обнаруживается не сразу, потому что ошибок нет — просто нет экономии):

- текущая дата или время в системном промпте;
- идентификатор запроса, случайный UUID, имя пользователя в начале промпта;
- недетерминированная сериализация: `json.dumps` без `sort_keys=True`, итерация по множеству;
- динамический набор инструментов, различающийся между пользователями;
- смена модели — кэш привязан к модели.

**Диагностика простая:** провайдеры возвращают в ответе счётчики прочитанных и записанных из кэша
токенов. Если по повторяющимся запросам чтение стабильно нулевое — ищите «тихий инвалидатор» в
начале промпта. Это первое, что надо проверить, когда экономия от кэша не материализовалась.

```python
import hashlib
import json
import time


def build_prompt(system_core: str, tools: list[dict], docs: list[dict],
                 history: list[dict], query: str) -> list[dict]:
    """Сборка промпта в порядке убывания стабильности.

    Порядок здесь — не стилистика, а прямой рычаг экономии: всё, что стоит
    ПОСЛЕ первого изменившегося байта, пересчитывается заново.
    """
    blocks = []
    # 1. Абсолютно стабильное: инструменты в детерминированном порядке
    blocks.append({
        "role": "system",
        "content": json.dumps(sorted(tools, key=lambda t: t["name"]),
                              ensure_ascii=False, sort_keys=True),
    })
    # 2. Стабильное: ядро системного промпта БЕЗ дат, имён и идентификаторов
    blocks.append({"role": "system", "content": system_core})
    # 3. Полустабильное: документы, отсортированные по id (не по скору!) —
    #    иначе перестановка при том же наборе сломает префикс
    for d in sorted(docs, key=lambda d: d["id"]):
        blocks.append({"role": "user", "content": f"[{d['id']}]\n{d['text']}"})
    # 4. Волатильное: история и текущий запрос — в самом конце
    blocks.extend(history)
    blocks.append({"role": "user", "content": query})
    return blocks


def cache_key(query: str, doc_ids: list[str], *, prompt_version: str,
              model_id: str, decoding: dict, tenant: str) -> str:
    """Ключ ТОЧНОГО кэша. Всё, что влияет на ответ, обязано быть в ключе.

    tenant в ключе — не оптимизация, а защита: без него один клиент получит
    ответ, построенный на документах другого.
    """
    payload = {
        "q": " ".join(query.lower().split()),        # мягкая нормализация
        "docs": sorted(doc_ids),
        "prompt": prompt_version,
        "model": model_id,
        "decoding": {k: decoding[k] for k in sorted(decoding)},
        "tenant": tenant,
    }
    raw = json.dumps(payload, ensure_ascii=False, sort_keys=True)
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()
```

### 4.3 Семантический кэш

Идея: считать эмбеддинг запроса, искать ближайший в кэше и при косинусной близости выше порога
$\tau$ отдавать сохранённый ответ. Ловит перефразировки, которые точный кэш пропускает.

**И здесь начинаются проблемы**, поэтому применять его надо осознанно.

Семантическая близость **не равна** эквивалентности запроса. Классические провалы:

- «как отменить подписку» и «как **не** отменить подписку» — косинус высокий, смысл противоположный;
- «статус заказа 12345» и «статус заказа 12346» — почти идентичные эмбеддинги, разные ответы;
- «сколько стоит тариф Про» и «сколько стоит тариф Про для юрлиц» — уточнение теряется.

Иначе говоря, семантический кэш **вносит ошибки**, а точный — нет. Значит, он требует того же
режима, что и любой классификатор: измерения FP/FN и подбора порога по цене ошибки.

Что делать, чтобы это работало:

1. **Никогда не применять там, где в запросе есть идентификаторы, числа или отрицания.**
   Детектор простой: если запрос содержит цифры или маркеры отрицания — идём мимо кэша.
2. **Разделять пространства кэша по типу запроса** (интенту): сравнение внутри одного интента
   намного безопаснее, чем по всему потоку.
3. **Подбирать порог по размеченной выборке пар**, а не «на глаз». Метрика — доля неверных
   попаданий среди попаданий.
4. **Логировать попадания и сэмплировать их на проверку** судьёй или человеком.

```python
import re
import numpy as np


NEGATION = re.compile(r"\b(не|нет|без|кроме|отмен|нельзя)\w*", re.IGNORECASE)
HAS_DIGITS = re.compile(r"\d")


class SemanticCache:
    """Семантический кэш с защитными предохранителями.

    Ключевое отличие от наивной реализации: часть запросов сознательно
    НЕ обслуживается кэшем, потому что для них семантическая близость
    не гарантирует эквивалентности.
    """

    def __init__(self, embed, threshold: float = 0.93, max_items: int = 50_000):
        self.embed = embed                       # embed(str) -> np.ndarray (нормированный)
        self.threshold = threshold
        self.max_items = max_items
        self._vecs: dict[str, np.ndarray] = {}   # intent -> матрица (m, d)
        self._meta: dict[str, list[tuple[str, str, float]]] = {}   # intent -> [(q, answer, ts)]

    @staticmethod
    def is_cacheable(query: str) -> bool:
        # Отрицания меняют смысл при высокой близости; цифры почти всегда
        # означают конкретную сущность (номер заказа, сумму, дату).
        return not (NEGATION.search(query) or HAS_DIGITS.search(query))

    def get(self, query: str, intent: str) -> str | None:
        if not self.is_cacheable(query) or intent not in self._vecs:
            return None
        v = self.embed(query)
        sims = self._vecs[intent] @ v            # векторы нормированы -> скалярное = косинус
        best = int(np.argmax(sims))
        if float(sims[best]) < self.threshold:
            return None
        return self._meta[intent][best][1]

    def put(self, query: str, intent: str, answer: str) -> None:
        if not self.is_cacheable(query):
            return
        v = self.embed(query).reshape(1, -1)
        if intent not in self._vecs:
            self._vecs[intent] = v
            self._meta[intent] = []
        else:
            self._vecs[intent] = np.vstack([self._vecs[intent], v])
        self._meta[intent].append((query, answer, float(np.datetime64("now").astype(int))))
        # простейшее вытеснение: FIFO по интенту
        if len(self._meta[intent]) > self.max_items:
            self._vecs[intent] = self._vecs[intent][1:]
            self._meta[intent] = self._meta[intent][1:]
```

### 4.4 Сводка

| Тип кэша | Что экономит | Типичный эффект | Риск качества | Когда применять |
|---|---|---|---|---|
| Точный | весь вызов | $h$ × стоимости, $h$ = 10–30% | нет | всегда, если есть повторы |
| Префиксный | prefill входа | до 60–80% стоимости входа | нет | всегда при стабильном префиксе |
| Семантический | весь вызов | +5–15 п.п. к hit rate | **есть** | узкий домен, после замера FP |

Механизмы **складываются**: точный кэш проверяется первым, семантический — вторым, префиксный
работает на всём, что дошло до модели.

## 5. Роутинг моделей

Идея простая: не все запросы одинаково сложны. Если 70% потока — «где мой заказ» и «как сменить
пароль», нет смысла отправлять их в самую дорогую модель.

### 5.1 Схема 1: каскад

Сначала дешёвая модель; если результат не проходит проверку — переспрашиваем дорогую.

$$
\mathbb{E}[c] = c_{\text{small}} + p_{\text{esc}} \cdot c_{\text{large}}
$$

где $c_{\text{small}}$ и $c_{\text{large}}$ — стоимость запроса к дешёвой и дорогой модели,
$p_{\text{esc}}$ — доля эскалаций.

> 📐 **Разбор формулы.** Каскад выгоден, когда $c_{\text{small}} + p_{\text{esc}} c_{\text{large}} < c_{\text{large}}$,
> то есть при $p_{\text{esc}} < 1 - c_{\text{small}}/c_{\text{large}}$. При отношении цен 1:5
> порог — $p_{\text{esc}} < 0.8$: каскад окупается, даже если эскалируется большинство запросов.
> Но у него есть скрытая цена, которой нет в формуле: **латентность эскалированных запросов
> удваивается**. Если ваш SLA по p95 жёсткий, каскад может его сломать, даже будучи выгодным по
> деньгам.

Ключевой элемент каскада — **верификатор**: чем решаем, что ответ дешёвой модели достаточен?
По надёжности:

1. **Детерминированная проверка** — лучший вариант, когда применим: JSON валиден по схеме, все
   обязательные поля заполнены, тесты для кода проходят, число в ответе совпадает с числом в
   источнике.
2. **Уверенность модели** — средняя логарифмическая вероятность выданных токенов, если провайдер
   её отдаёт. Работает на задачах с коротким ответом (классификация, извлечение), плохо — на
   свободной генерации.
3. **Самопроверка** — попросить дешёвую модель оценить свой ответ. Работает хуже, чем кажется:
   модели плохо калиброваны и склонны к самоуверенности.
4. **Отдельный маленький классификатор-верификатор** — дороже в разработке, но надёжнее.

### 5.2 Схема 2: априорный роутер

Классификатор смотрит на запрос **до** генерации и выбирает модель. Экономит латентность (нет
двойного прохода), но требует, чтобы сложность запроса была предсказуема по нему самому.

Признаки, которые работают на практике:

- длина запроса и число сущностей в нём;
- интент (уже есть в большинстве продуктов);
- требуется ли рассуждение в несколько шагов (наличие «почему», «сравни», «посчитай»);
- число и разнородность извлечённых документов;
- есть ли инструменты в сценарии;
- язык и наличие кода.

Обучающая разметка получается почти бесплатно: прогоните исторический поток через обе модели,
разметьте судьёй или детерминированной проверкой, где дешёвая справилась, и обучите бинарный
классификатор «хватит ли дешёвой».

```python
import numpy as np
from dataclasses import dataclass


@dataclass
class RouterConfig:
    cost_small: float
    cost_large: float
    quality_penalty: float     # цена одного неверно роутнутого «вниз» запроса, в тех же деньгах


def choose_threshold(probs_small_enough: np.ndarray, small_was_enough: np.ndarray,
                     cfg: RouterConfig) -> tuple[float, dict]:
    """Подбор порога роутера минимизацией ожидаемых потерь.

    probs_small_enough — предсказанная вероятность, что дешёвой модели хватит;
    small_was_enough  — факт (0/1) по исторической разметке.

    Смысл: порог — не «0.5», а решение экономической задачи. Ошибка «отправил
    вниз, а не хватило» стоит quality_penalty; ошибка «отправил вверх зря»
    стоит разницы в цене.
    """
    best = (None, np.inf, None)
    for thr in np.linspace(0.05, 0.95, 91):
        route_small = probs_small_enough >= thr
        # отправили вниз и не хватило — платим дешёвую модель + штраф за качество
        bad_down = route_small & (small_was_enough == 0)
        # отправили вниз и хватило — экономия
        good_down = route_small & (small_was_enough == 1)
        # отправили вверх — платим дорогую независимо от того, хватило бы дешёвой
        up = ~route_small

        cost = (
            good_down.sum() * cfg.cost_small
            + bad_down.sum() * (cfg.cost_small + cfg.quality_penalty)
            + up.sum() * cfg.cost_large
        )
        if cost < best[1]:
            stats = {
                "threshold": float(thr),
                "share_small": float(route_small.mean()),
                "error_rate_among_small": float(bad_down.sum() / max(route_small.sum(), 1)),
                "cost_per_request": float(cost / len(probs_small_enough)),
                "cost_all_large": float(cfg.cost_large),
            }
            best = (thr, cost, stats)
    return best[0], best[2]


# Демонстрация: 60% запросов реально простые
rng = np.random.default_rng(0)
n = 20_000
simple = rng.random(n) < 0.6
# роутер несовершенен: вероятности пересекаются
probs = np.clip(np.where(simple, rng.normal(0.75, 0.15, n), rng.normal(0.35, 0.18, n)), 0, 1)

cfg = RouterConfig(cost_small=0.0035, cost_large=0.0300, quality_penalty=0.05)
thr, stats = choose_threshold(probs, simple.astype(int), cfg)
for k, v in stats.items():
    print(f"{k}: {v:.4f}")
```

Обратите внимание на параметр `quality_penalty`: он превращает подбор порога из «максимизируем долю
дешёвых» в честную задачу. Если плохой ответ стоит вам эскалации на оператора за 5 долларов, роутер
будет консервативным; если максимум неудобства — пользователь переспросит, роутер станет
агрессивнее. **Порог роутера — это бизнес-решение, выраженное числом**, а не гиперпараметр по
умолчанию.

### 5.3 Что ещё роутят

Роутинг — это не только «дорогая/дешёвая». В продакшене роутят:

- **по домену**: код — в модель, сильную в коде; русский текст — в модель с хорошей поддержкой языка;
- **по длине контекста**: короткое — в модель с меньшим окном и меньшей ценой;
- **по SLA**: интерактивный запрос — в быструю модель, фоновая задача — в батч-режим со скидкой;
- **как фолбэк**: провайдер отдал 429 или 5xx — уходим на резервного (см. [§9](#9-rate-limits-ретраи-и-деградация)).

**Всегда держите фолбэк-путь.** Схема с единственным провайдером означает, что его сбой — это ваш сбой.

## 6. Дистилляция в маленькую модель

Когда роутинг и кэш выжаты, а объём большой, следующий шаг — обучить свою маленькую модель на
выходах большой. Это классическая **дистилляция знаний (knowledge distillation)**, адаптированная
к LLM: вместо мягких вероятностных распределений учителя чаще используют просто его тексты
(sequence-level distillation), потому что логиты закрытых моделей недоступны.

### 6.1 Когда это окупается

Все четыре условия должны выполняться одновременно:

1. **Задача узкая и стабильная.** Классификация обращений, извлечение полей, генерация коротких
   типовых ответов, нормализация текста. Если завтра продукт попросит «а ещё пусть отвечает на
   произвольные вопросы» — дистилляция обесценится.
2. **Объём большой.** Иначе не окупятся недели работы и своя инфраструктура — см. $n^*$ из [§3](#3-своя-модель-против-api-точка-безубыточности).
3. **Есть данные.** 10–50 тысяч примеров с выходами учителя, отфильтрованных по качеству.
4. **Качество измеримо.** Без эвал-набора вы не сможете доказать, что студент не хуже.

### 6.2 Процедура

```
1. Собрать входы из реального потока (стратифицированно по типам запросов!)
2. Прогнать через сильную модель-учителя → сырые ответы
3. ОТФИЛЬТРОВАТЬ: детерминированные проверки + судья.
   Учить на ошибках учителя — верный способ закрепить их навсегда.
4. Дообучить маленькую модель (обычно LoRA, см. главу про PEFT)
5. Померить на эвал-наборе против учителя ПО СРЕЗАМ
6. Выкатывать через shadow → канарейку → долю трафика
7. Оставить эскалацию на учителя для случаев, где студент не уверен
```

Шаг 3 — тот, который чаще всего пропускают, и именно он определяет результат. Сырые выходы учителя
содержат его галлюцинации, его отказы не по делу, его многословие. Студент выучит всё это как
норму. Фильтрация обычно отсеивает 15–30% примеров, и это нормально.

Шаг 5 обязательно **по срезам**: типичная картина — студент не хуже учителя на 90% массовых
запросов и заметно хуже на редких сложных. Это не провал, а ровно то, ради чего строится гибрид:
массовое — студенту, хвост — учителю.

### 6.3 Экономика

Стоимость дистилляции:

$$
C_{\text{dist}} = \underbrace{N_{\text{train}} \cdot c_{\text{teacher}}}_{\text{сбор данных}} + \underbrace{C_{\text{train}}}_{\text{обучение}} + \underbrace{C_{\text{eval}}}_{\text{разметка и проверка}}
$$

где $N_{\text{train}}$ — число собранных примеров, $c_{\text{teacher}}$ — стоимость одного вызова
учителя, $C_{\text{train}}$ — стоимость обучения (для LoRA на 8B-модели это часы одного ускорителя,
то есть десятки долларов), $C_{\text{eval}}$ — стоимость разметки эвал-набора и проверок.

Доминирует обычно не обучение, а **сбор данных и разметка эвала**. 30 тысяч вызовов учителя по
\$0.03 — это 900 долларов; человеко-недели на эвал-набор и валидацию — существенно больше.
Считайте честно: дистилляция окупается объёмом, а не дешевизной обучения.

> 💬 **На собеседовании.** Спросят: «Как удешевить LLM-фичу в 10 раз?» Хороший ответ идёт по
> рычагам с оценкой эффекта каждого: (1) померить, где деньги — вход или выход, вызовы модели или
> ретраи; (2) сократить контекст — обычно самый быстрый выигрыш в RAG, где вход доминирует;
> (3) префиксное кэширование стабильной части промпта — до 70% стоимости входа при высоком hit rate;
> (4) точный кэш на повторах; (5) роутинг простых запросов на модель классом ниже с порогом,
> подобранным по цене ошибки; (6) батч-режим для всего, что не интерактивно; (7) если после этого
> объём всё ещё большой — дистилляция в свою модель на узкой задаче. И обязательная оговорка:
> каждый шаг проверяется на эвал-наборе, потому что удешевление без контроля качества — это не
> оптимизация, а деградация.

## 7. Латентность и стриминг

### 7.1 Из чего складывается ожидание

Пользовательская латентность разбивается на слагаемые (метрики TTFT и TPOT подробно разобраны в
[главе про инференс](05-inference-and-serving.md)):

$$
L_{\text{total}} = \underbrace{L_{\text{pre}}}_{\text{до модели}} + \underbrace{\text{TTFT}}_{\text{prefill}} + \underbrace{T_{\text{out}} \cdot \text{TPOT}}_{\text{генерация}} + \underbrace{L_{\text{post}}}_{\text{после}}
$$

где $L_{\text{pre}}$ — эмбеддинг запроса, поиск, реранкинг, фильтры входа; TTFT (time to first token) —
время до первого токена, определяется в основном длиной контекста; TPOT (time per output token) —
время на токен генерации; $L_{\text{post}}$ — валидация вывода, санитизация, фильтры выхода.

Типичный бюджет для RAG-ассистента (ориентировочно, p50):

| Этап | Время | Комментарий |
|---|---|---|
| Фильтры входа | 20–50 мс | классификатор на CPU/маленькой модели |
| Эмбеддинг запроса | 10–30 мс | |
| ANN-поиск | 10–40 мс | зависит от индекса |
| Реранкер | 100–400 мс | cross-encoder на $k$ кандидатах — часто главный вклад в $L_{\text{pre}}$ |
| TTFT модели | 300–1500 мс | растёт с длиной контекста |
| Генерация | 400 × 15 мс ≈ 6 с | доминирует, но скрывается стримингом |
| Фильтры выхода | 50–200 мс | **не скрываются стримингом**, см. ниже |

### 7.2 Стриминг: что он меняет и чего не меняет

Стриминг **не сокращает** $L_{\text{total}}$. Он меняет то, что воспринимает пользователь:
вместо «9 секунд пустого экрана» — «1.5 секунды, потом текст поехал». Воспринимаемая задержка
падает в разы при неизменной фактической.

Практические следствия:

- **Оптимизировать надо TTFT, а не общее время.** Всё, что стоит до первого токена, пользователь
  видит как «тормозит». Всё, что после, — как «печатает».
- **Реранкер — первый кандидат на оптимизацию** $L_{\text{pre}}$: сократить число кандидатов,
  взять модель поменьше, вынести на GPU, кэшировать по паре (запрос, документ).
- **Фильтры выхода конфликтуют со стримингом.** Если надо проверить весь ответ целиком, стримить
  нечего. Компромиссы: стримить с задержкой в несколько токенов; проверять инкрементально по
  предложениям; стримить и уметь **отозвать** уже показанное (интерфейс должен это поддерживать);
  для высокорисковых путей — отказаться от стриминга сознательно.
- **Первый токен — не обязательно от модели.** Можно немедленно отдать статусное сообщение
  («ищу в документах…»), пока идёт retrieval. Психологически это работает как снижение TTFT.

### 7.3 Хвосты, а не среднее

Оптимизировать надо p95/p99, а не среднее. Причины длинных хвостов в LLM-сервисах:

- **Очередь у провайдера в пик.** Нет контроля — только таймаут и фолбэк.
- **Длинные ответы.** Распределение $T_{\text{out}}$ имеет тяжёлый правый хвост; один запрос с
  ответом на 3000 токенов даёт минутную латентность. Лечение: жёсткий `max_tokens` и явная
  инструкция по длине.
- **Ретраи.** Каждый ретрай складывает латентности. При таймауте 30 с и двух ретраях худший случай —
  90 секунд, а пользователь ушёл на двадцатой.
- **Агенты.** Число шагов — случайная величина, и её хвост определяет p99. Обязателен лимит шагов.

**Правило таймаутов:** таймаут одного вызова должен быть **меньше**, чем бюджет всего запроса,
делённый на максимальное число попыток. Иначе ретраи гарантированно выйдут за SLA, и вы будете
платить за вычисления, результат которых уже никому не нужен.

## 8. Экономика рассуждающих моделей: когда длина ответа — случайная величина

Формула стоимости из [§2.1](#21-формула) молча предполагает, что $T_{\text{out}}$ вам известно.
Для обычной генерации это почти правда: вы ставите `max_tokens`, просите «ответь одним абзацем»,
и разброс невелик. Для модели с режимом рассуждения это неправда полностью.

У такой модели выходные токены распадаются на две части:

$$
T_{\text{out}} \;=\; T_{\text{reason}} + T_{\text{answer}}
$$

где $T_{\text{answer}}$ — токены ответа, который увидит пользователь, а $T_{\text{reason}}$ —
токены размышления, которых он не увидит. Вторая часть тарифицируется по цене **выходных**
токенов, при этом её содержимое провайдер часто не возвращает вовсе — только количество.
И главное: $T_{\text{reason}}$ — это выход модели, а не ваш параметр. Модель сама решает,
что задача трудная, и уходит думать на десять тысяч токенов.

Стоимость запроса перестаёт быть числом и становится случайной величиной. Дальше — как её считать
и что она делает с латентностью, ёмкостью и SLA. Механика самого рассуждения и способы им
управлять разобраны в главе про
[промптинг](06-prompting-and-structured-output.md#6-test-time-compute-качество-которое-покупают-на-инференсе);
здесь только деньги и железо.

### 8.1 Модель длины и расчёт

Эмпирически распределение $T_{\text{reason}}$ хорошо описывается **логнормальным**. Интуиция,
почему именно оно: длина складывается мультипликативно — «сколько шагов рассуждения» умножить
на «какой длины шаг», плюс вероятность добавить ещё один заход на самопроверку. Логарифм длины
получается суммой многих слагаемых, и центральная предельная теорема делает своё дело. Это
аппроксимация, а не закон: проверяйте на своих логах, прежде чем строить на ней бюджет.

Удобство логнормали в том, что её два параметра восстанавливаются по двум числам, которые видны
прямо в дашборде: медиане и 99-му перцентилю.

> 📐 **Разбор формулы.** Пусть $\ln T_{\text{reason}} \sim \mathcal{N}(\mu, \sigma^2)$. Медиана
> логнормали — это $e^{\mu}$, потому что медиана нормали равна $\mu$, а экспонента монотонна.
> Отсюда $\mu = \ln(\text{median})$. Квантиль уровня $\alpha$ равен $\exp(\mu + \sigma z_\alpha)$,
> где $z_\alpha$ — квантиль стандартной нормали ($z_{0.99} \approx 2.326$). Приравняв его
> к наблюдаемому $p_{99}$, получаем
>
> $$
> \sigma = \frac{\ln\big(p_{99} / \text{median}\big)}{z_{0.99}}
> $$
>
> А математическое ожидание логнормали — **не** медиана, а $\exp(\mu + \sigma^2/2)$. Множитель
> $e^{\sigma^2/2}$ и есть та наценка, которую вы не увидите, если планируете бюджет по медиане.
> При медиане 800 токенов и $p_{99}$ в 12 000 получается $\sigma = 1.164$, множитель
> $e^{0.677} = 1.97$ — среднее ровно вдвое больше медианы.

Теперь посчитаем на конкретном профиле: контекст 1500 токенов, содержательный ответ 300 токенов,
цены 3 и 15 условных единиц за миллион входных и выходных токенов, 200 тысяч запросов в сутки.

```python
import numpy as np
from scipy.stats import norm

# Профиль запроса: контекст 1500 токенов, содержательный ответ 300 токенов.
# Цены условные, за миллион токенов; берите свои — важна структура расчёта.
T_IN, T_ANSWER = 1500, 300
P_IN, P_OUT = 3.0, 15.0
TPOT = 0.015          # секунд на один выходной токен
N_DAY = 200_000       # запросов в сутки

# Длину рассуждения задаём логнормальным распределением по двум точкам,
# которые видно прямо в логах: медиане и 99-му перцентилю.
MEDIAN, P99 = 800.0, 12_000.0
mu = np.log(MEDIAN)
sigma = np.log(P99 / MEDIAN) / norm.ppf(0.99)
mean_len = np.exp(mu + sigma ** 2 / 2)

def spaced(x, digits=0):
    """Разряды через пробел — иначе числа не читаются глазами."""
    return f"{x:,.{digits}f}".replace(",", " ")

print(f"логнормаль по (медиана {MEDIAN:.0f}, p99 {P99:.0f}): mu = {mu:.3f}, sigma = {sigma:.3f}")
print(f"матожидание длины рассуждения = exp(mu + sigma^2/2) = {mean_len:.0f} токенов "
      f"— вдвое больше медианы\n")

rng = np.random.default_rng(0)
reason = rng.lognormal(mu, sigma, size=2_000_000)

def cost(t_out):
    return (T_IN * P_IN + t_out * P_OUT) / 1e6

base = cost(T_ANSWER)
print(f"без рассуждения: {base * 1000:.2f} за 1000 запросов, "
      f"{spaced(base * N_DAY)} в сутки\n")
header = (f"{'потолок':>8} {'обрезано':>9} {'средняя':>9} {'p50':>8} {'p95':>8} "
          f"{'p99':>8} {'в сутки':>9} {'p99 латентность':>16}")
print(header)
for cap in (None, 8192, 4096, 2048, 1024):
    r = reason if cap is None else np.minimum(reason, cap)
    t_out = r + T_ANSWER
    c = cost(t_out) * 1000           # цена за 1000 запросов
    lat = t_out * TPOT
    label = "нет" if cap is None else str(cap)
    trunc = 0.0 if cap is None else float((reason > cap).mean())
    print(f"{label:>8} {trunc:>8.1%} {c.mean():>9.2f} {np.percentile(c, 50):>8.2f} "
          f"{np.percentile(c, 95):>8.2f} {np.percentile(c, 99):>8.2f} "
          f"{spaced(c.mean() * N_DAY / 1000):>9} {np.percentile(lat, 99):>14.0f} с")

print(f"\nсредняя цена относительно режима без рассуждения: "
      f"{cost(mean_len + T_ANSWER) / base:.1f}x без потолка, "
      f"{cost(np.minimum(reason, 4096).mean() + T_ANSWER) / base:.1f}x с потолком 4096")

# насколько счёт сконцентрирован в хвосте — это решает, что оптимизировать
ordered = np.sort(cost(reason + T_ANSWER))
print(f"верхний 1% запросов даёт {ordered[int(0.99 * len(ordered)):].sum() / ordered.sum():.1%} "
      f"счёта, верхние 5% — {ordered[int(0.95 * len(ordered)):].sum() / ordered.sum():.1%}")
```

```

матожидание длины рассуждения = exp(mu + sigma^2/2) = 1575 токенов — вдвое больше медианы

без рассуждения: 9.00 за 1000 запросов, 1 800 в сутки

 потолок  обрезано   средняя      p50      p95      p99   в сутки  p99 латентность
     нет     0.0%     32.65    21.01    90.57   189.75     6 531            185 с
    8192     2.3%     30.67    21.01    90.57   131.88     6 135            127 с
    4096     8.0%     27.99    21.01    70.44    70.44     5 597             66 с
    2048    21.0%     23.97    21.01    39.72    39.72     4 795             35 с

```

Из этой таблицы вытаскиваются четыре вывода, и все четыре обычно оказываются новостью.

**Первый: средний запрос дороже медианного в полтора раза.** Медиана — 21 условная единица
за тысячу запросов, среднее — 32.65. Если вы оценивали бюджет по «типичному запросу, который
посмотрели глазами», вы недосчитали в полтора раза. Платите вы по среднему.

**Второй: счёт сконцентрирован в хвосте.** p99 стоит в девять раз дороже медианы (189.75 против
21.01), верхний процент трафика даёт 9.2% счёта, верхние пять процентов — почти четверть.
Это тот случай, когда осмысленно поставить отдельный лимит на самые дорогие запросы, а не
размазывать экономию по всем.

**Третий: потолок бюджета режет хвост несопоставимо эффективнее, чем среднее.** Потолок
в 4096 токенов обрезает 8% запросов, снижает среднюю цену всего на 14% — с 32.65 до 27.99, —
но роняет p99 c 189.75 до 70.44, то есть в 2.7 раза. И вместе с ним падает p99 латентности:
185 секунд превращаются в 66. Потолок — это инструмент управления **хвостом**, а не средним;
за среднее отвечает маршрутизация.

**Четвёртый: медиана не двигается вообще.** Во всех строках она равна 21.01, потому что медианное
рассуждение (800 токенов) короче любого из потолков. Отсюда практическое правило: если ваш
дашборд показывает только p50, вы не увидите ни эффекта от введения потолка, ни момента,
когда рассуждения поехали вверх.

### 8.2 Что это делает с ёмкостью

Деньги — только половина проблемы, и обычно не худшая. Хуже то, что происходит с железом,
если вы обслуживаете модель сами.

Длинная генерация занимает слот в батче всё время, пока идёт. По формуле Литтла среднее число
одновременно обрабатываемых запросов равно $\bar{N} = \lambda W$, где $\lambda$ — интенсивность
потока (запросов в секунду), $W$ — среднее время запроса в системе. Рассуждение увеличивает $W$
в разы, значит во столько же раз растёт число одновременно живых запросов при той же нагрузке.

Второй удар приходит с другой стороны: KV-кэш каждого запроса растёт с длиной последовательности.
Посчитаем для типичной 8B-модели с GQA — 32 слоя, 8 KV-голов, размерность головы 128, fp16:

$$
\text{байт на токен} = 2 \cdot 32 \cdot 8 \cdot 128 \cdot 2 = 131\,072 \approx 128\ \text{КиБ}
$$

где первая двойка — на ключи и значения, 32 — число слоёв, 8 — число KV-голов, 128 — размерность
головы, последняя двойка — байт на число в fp16 (вывод формулы — в главе про
[инференс](05-inference-and-serving.md)).

Теперь два сценария на карте с 80 ГиБ, из которых под KV-кэш остаётся около 40 ГиБ:

- запрос без рассуждения, 1500 входных плюс 300 выходных токенов: $1800 \cdot 128$ КиБ $= 0.22$ ГиБ,
  помещается около **180** одновременных запросов;
- запрос с рассуждением в хвосте, 1500 плюс 12 300: $13\,800 \cdot 128$ КиБ $= 1.68$ ГиБ,
  помещается около **24**.

Ёмкость по числу одновременных запросов падает примерно в семь раз — и это при том, что каждый
из них ещё и живёт дольше. Оба множителя перемножаются.

> ⚠️ **Типичная ошибка.** Включить режим рассуждения на 10% трафика и удивиться, что просел
> **весь** сервис, включая простые запросы. Механика: длинные генерации держат слоты KV-кэша
> и не отпускают их минутами; свободной памяти под новые запросы не остаётся, батч мельчает,
> continuous batching деградирует, и короткие запросы встают в очередь за длинными — классическая
> блокировка головы очереди. Правильно: развести ветки по разным пулам (или хотя бы по разным
> очередям с приоритетом), поставить жёсткий лимит на число одновременных длинных генераций
> и следить за долей вытесненных запросов (preemption rate) как за отдельным SLI.

### 8.3 Как это закладывать в SLA

Главное следствие всего предыдущего: **один SLA на смешанный трафик бессмысленен**. Если 10%
запросов имеют p99 в 185 секунд, а 90% — в 8 секунд, общий p99 зависит не от системы,
а от пропорции. Роутер поехал, доля думающих запросов выросла с 10% до 25% — и вы нарушили SLA,
не изменив ни строчки кода.

Отсюда четыре требования к формулировке.

**Разделять SLO по веткам.** Отдельная цель для быстрой ветки, отдельная — для думающей.
Формулировка вида «p95 не выше 4 секунд при доле думающих запросов не выше 12%» честнее,
чем единый порог: она явно называет условие, при котором обещание держится.

**Доля думающих запросов — это SLI, а не деталь реализации.** На неё ставится алерт, её изменение
разбирается как инцидент. Побочная польза: это самый ранний индикатор того, что распределение
входящего трафика изменилось.

**Жёсткий потолок бюджета обязателен.** Не потому, что он экономит деньги (мы видели: 14%),
а потому, что он делает худший случай **детерминированным**. Без потолка у вас нет верхней
границы ни по латентности, ни по времени удержания слота, а значит нет и SLA — есть пожелание.

**Таймаут считается иначе.** Правило из [§7.3](#73-хвосты-а-не-среднее) — «таймаут вызова меньше
бюджета запроса, делённого на число попыток» — при рассуждении даёт ловушку: таймаут в 30 секунд
обрывает все запросы с рассуждением длиннее примерно двух тысяч токенов, вы платите за эти токены
провайдеру и не получаете ничего. Порядок правильный: сначала ставится потолок бюджета
рассуждения, затем таймаут выбирается с запасом над величиной
$(\text{потолок} + T_{\text{answer}}) \cdot \text{TPOT}$, и только потом считается
число допустимых ретраев.

И одна вещь, которую ломает рассуждение и которую жалко: **стриминг перестаёт спасать**.
В [§7.2](#72-стриминг-что-он-меняет-и-чего-не-меняет) мы говорили, что генерация скрывается
за стримингом. Токены рассуждения пользователю обычно не показывают, поэтому воспринимаемый TTFT
равен полному времени размышления — те самые десятки секунд пустого экрана, от которых стриминг
и должен был избавить. Полумеры, которые действительно работают: показывать краткое резюме шагов
(«проверяю цены», «сверяю с договором») вместо самого рассуждения; отдавать промежуточный статус
из ветки роутинга до вызова модели; на быстрой ветке не включать рассуждение вовсе.

> 💬 **На собеседовании.** Спросят: «Сколько стоит запрос к thinking-модели?»
> Хороший ответ начинается с того, что это не число, а распределение. Выходные токены —
> это $T_{\text{reason}} + T_{\text{answer}}$, причём токены рассуждения тарифицируются
> по цене выходных, а в ответе их нет; считать надо по полю `usage`, а не по длине текста.
> Длина рассуждения приближённо логнормальна, поэтому среднее заметно больше медианы:
> при медиане 800 и $p_{99}$ в 12 000 токенов $\sigma = 1.164$ и среднее вдвое выше медианы.
> Дальше называю три числа, которые нужны для бюджета: среднее (по нему платите), p99
> (по нему считаете ёмкость и SLA) и долю трафика, попадающую в думающую ветку. На моём примере
> получается около 3.6× к стоимости запроса без рассуждения, и это на всём трафике —
> поэтому первый рычаг маршрутизация, а второй потолок бюджета. Плохой ответ: назвать цену
> за миллион токенов и умножить на среднюю длину видимого ответа.

> 💬 **На собеседовании.** Спросят: «Вы включили рассуждение, p99 латентности вырос в двадцать
> раз. Что делаете?»
> Хороший ответ по шагам. (1) Разделяю метрики по веткам: смешанный p99 не диагностируется,
> потому что в нём перемешаны два разных распределения. (2) Ставлю потолок бюджета рассуждения
> и смотрю таблицу «потолок → обрезано / средняя цена / p99»: потолок режет хвост в разы,
> а среднее почти не трогает, поэтому это самый дешёвый первый шаг. (3) Проверяю, не деградировала
> ли быстрая ветка: длинные генерации держат KV-кэш, батч мельчает, короткие запросы встают
> за длинными — если да, развожу ветки по пулам или очередям с приоритетом. (4) Пересчитываю
> таймауты от потолка, а не наоборот, иначе буду платить за оборванные генерации. (5) Пересматриваю
> роутер: доля думающих запросов — это SLI, и, скорее всего, проблема началась с её роста.
> Плохой ответ: «увеличу таймаут».

## 9. Rate limits, ретраи и деградация

### 9.1 Как устроены ограничения

Провайдеры ограничивают два ресурса одновременно: **запросы в минуту** (RPM) и **токены в минуту**
(TPM, часто раздельно по входу и выходу). Упереться можно в любой: 100 запросов с контекстом по
100 тысяч токенов выбьют TPM, не приблизившись к RPM.

При превышении — HTTP 429 с заголовком, указывающим, сколько ждать. Отдельно бывают 529/503 при
перегрузке провайдера — это другое: не ваш лимит, а его состояние.

### 9.2 Ретраи: экспоненциальная задержка с джиттером

Наивный ретрай сразу — худшее, что можно сделать: он усиливает перегрузку. Нужна экспоненциальная
задержка **с джиттером**, иначе все клиенты, получившие 429 одновременно, повторят тоже
одновременно (эффект «громового стада»).

$$
d_k = \min\big(d_{\max},\; d_0 \cdot 2^{k}\big) \cdot U(0, 1)
$$

где $d_k$ — задержка перед попыткой $k$ (нумерация с нуля), $d_0$ — базовая задержка,
$d_{\max}$ — потолок, $U(0,1)$ — равномерная случайная величина, дающая **полный джиттер**.

> 📐 **Разбор формулы.** Экспонента $2^k$ быстро разводит попытки во времени, потолок $d_{\max}$ не
> даёт задержке уйти в минуты, а множитель $U(0,1)$ размазывает попытки клиентов по интервалу.
> Полный джиттер (умножение на равномерную величину, а не добавление небольшого шума) — вариант,
> который на практике даёт наименьшую конкуренцию за ресурс. Если провайдер прислал заголовок
> `retry-after`, он приоритетнее любой формулы: это точное знание против эвристики.

Что **нельзя** ретраить: ошибки валидации (400), аутентификации (401/403), «не найдено» (404).
Повтор не изменит результат, но потратит бюджет и время.

```python
import random
import time


RETRYABLE_STATUS = {408, 409, 429, 500, 502, 503, 504, 529}


class BudgetExceeded(Exception):
    pass


def call_with_retry(fn, *, max_attempts=4, base_delay=0.5, max_delay=20.0,
                    total_budget_s=25.0, on_retry=None):
    """Ретрай с экспоненциальной задержкой и полным джиттером.

    Два принципиальных момента:
    1) Общий бюджет времени — жёсткая граница. Без него ретраи легко выходят
       за SLA, и вы платите за ответ, который уже никому не нужен.
    2) Заголовок retry-after от провайдера приоритетнее нашей формулы.
    """
    started = time.monotonic()
    last_exc = None

    for attempt in range(max_attempts):
        remaining = total_budget_s - (time.monotonic() - started)
        if remaining <= 0:
            raise BudgetExceeded(f"бюджет {total_budget_s}s исчерпан на попытке {attempt}")

        try:
            return fn(timeout=min(remaining, total_budget_s / max_attempts))
        except Exception as exc:                       # noqa: BLE001 — классифицируем ниже
            status = getattr(exc, "status_code", None)
            if status is not None and status not in RETRYABLE_STATUS:
                raise                                  # 400/401/404 ретраить бессмысленно
            last_exc = exc

            server_hint = getattr(exc, "retry_after", None)
            if server_hint is not None:
                delay = float(server_hint)
            else:
                delay = min(max_delay, base_delay * (2 ** attempt)) * random.random()

            if (time.monotonic() - started) + delay >= total_budget_s:
                raise BudgetExceeded("следующая попытка не укладывается в бюджет") from exc

            if on_retry:
                on_retry(attempt, delay, exc)
            time.sleep(delay)

    raise last_exc
```

### 9.3 Что делать, когда ретраи не помогают

Ретрай лечит кратковременный всплеск. Устойчивую перегрузку он только усугубляет. Поэтому нужен
**план деградации** — заранее описанная лестница, по которой сервис спускается вместо того, чтобы
падать:

| Ступень | Действие | Что теряем |
|---|---|---|
| 0 | нормальная работа | — |
| 1 | фолбэк на резервного провайдера / регион | немного качества или цены |
| 2 | роутинг всего трафика на модель классом ниже | качество на сложных запросах |
| 3 | отдавать ответы только из кэша, остальное — в очередь | свежесть и полноту |
| 4 | шаблонные ответы + предложение оператора | всё, кроме доступности |
| 5 | честное «сервис временно недоступен» с сохранением запроса | всё |

Переключение между ступенями должно быть **автоматическим** по метрикам (доля 429, p95 латентности,
доля ошибок) и **обратимым**. Плюс — размыкатель цепи (circuit breaker): после серии ошибок
перестаём стучаться в провайдера на фиксированное время, а не долбим его.

**Приоритизация трафика.** Не все запросы равны. Если ёмкость ограничена, интерактивный запрос
платящего пользователя важнее фоновой переиндексации. Практически это — отдельные очереди с
приоритетами и разными лимитами по арендаторам, чтобы один клиент не съел квоту всех.

## 10. Версионирование

**Что версионируется.** Ответ на вопрос «что именно изменилось» должен получаться из логов
однозначно. Значит, в каждой записи должны быть:

- идентификатор модели **с точной версией** (не алиас, который провайдер переназначает);
- версия промпта (хеш содержимого + человекочитаемый тег);
- параметры декодинга;
- версия схемы инструментов;
- версия конфигурации retrieval (модель эмбеддингов, схема чанкинга, версия индекса, $k$);
- версия набора фильтров.

Эта комбинация — и есть «версия системы». Изменение любого элемента может изменить поведение, и
если вы не логируете все, вы не сможете сопоставить метрику с причиной.

**Промпты — это код.** Практика, которая окупается с первого инцидента:

- промпты живут в репозитории, а не в конфиге админки и не в базе;
- изменение проходит ревью и прогон регрессионного эвала
  (см. [оценку LLM](09-llm-evaluation.md));
- есть тег версии, который пишется в каждый лог;
- откат — это откат коммита, а не ручное редактирование;
- шаблоны параметризованы, а не собираются конкатенацией строк по месту.

**Алиасы моделей опасны.** Если провайдер даёт алиас, указывающий на «последнюю версию», ваша
система может измениться без вашего участия — в момент, который вы не выбирали. Правильная
практика: **пин на точную версию**, а обновление — как отдельная выкатка со своим эвалом и
канарейкой. Это ровно та ситуация, где «ничего не меняли, а качество упало».

**Выкатка изменений** — по обычной лестнице
(подробно — в [стратегиях выкатки](../07-mlops/08-deployment-strategies.md)):

```mermaid
flowchart LR
    A["Регрессионный<br/>эвал"] --> B["Shadow:<br/>обе версии, показываем старую"]
    B --> C["Канарейка<br/>1-5% трафика"]
    C --> D["Ramp-up<br/>25% → 50% → 100%"]
    D --> E["Старая версия<br/>в резерве N дней"]
```

**Shadow-режим для LLM особенно полезен**: вы получаете пары ответов старой и новой версии на
реальном трафике и можете прогнать по ним парного судью — то есть провести полноценное сравнение
ещё до того, как хоть один пользователь увидел новую версию. Цена — двойные токены на время
эксперимента, поэтому сэмплируйте (5–10% трафика достаточно).

## 11. Мониторинг качества генерации в проде

### 11.1 Главная трудность

В классическом ML метрику качества в проде считают, дождавшись целевой переменной. В LLM-продукте
целевой переменной нет вообще: никто не скажет, был ли ответ хорош. Значит, мониторинг строится из
**прокси-сигналов** и **сэмплированной оценки**.

### 11.2 Четыре слоя мониторинга

**Слой 1: техника.** Латентность по этапам (p50/p95/p99), доля ошибок по кодам, доля ретраев, RPS,
стоимость на запрос и на успешную задачу, hit rate кэшей, доля попаданий в лимиты провайдера.
Это база, она обязана быть.

**Слой 2: распределение входа.** Дрифт запросов ловится дешёвыми признаками: длина, язык,
распределение по интентам, доля запросов с неизвестными терминами, среднее расстояние эмбеддинга
запроса до ближайшего кластера исторических запросов. Смещение здесь предупреждает о падении
качества **до** того, как оно проявится в жалобах (общая теория — в
[главе про дрифт](../09-monitoring/03-drift-detection.md)).

**Слой 3: свойства выхода.** Считаются на каждом ответе, стоят копейки и очень информативны:

| Сигнал | О чём говорит рост |
|---|---|
| Средняя длина ответа | сменилась версия модели; промпт стал многословнее; растёт стоимость |
| Доля отказов («не знаю») | сломался retrieval; изменилось поведение модели |
| Доля невалидного JSON / нарушений схемы | регресс структурного вывода — часто первый признак смены версии модели |
| Доля срабатываний фильтров выхода | либо атака, либо регресс поведения |
| Доля ответов без цитат (в RAG) | падение обоснованности |
| Число шагов агента, доля упирания в лимит | деградация планирования |

**Слой 4: качество на сэмпле.** Небольшую долю трафика (0.5–2%) прогоняем через LLM-судью с
рубрикой; ещё меньшую — через человека. Это даёт непрерывный ряд оценки качества с доверительным
интервалом. Обязательное условие: **судья провалидирован и его версия зафиксирована** — иначе вы
будете видеть изменения судьи, а не системы (см. [оценку LLM](09-llm-evaluation.md)).

### 11.3 Канареечный набор в проде

Отдельный приём, который стоит дёшево и ловит много: держите набор из 50–200 фиксированных запросов
и **прогоняйте его по расписанию** (например, ежечасно) через продовый путь целиком — с retrieval,
фильтрами и реальной моделью.

Что это даёт:

- сравнимый во времени ряд качества на неизменных входах — любое изменение вызвано системой,
  а не составом трафика;
- немедленное обнаружение молчаливого обновления модели у провайдера;
- проверку, что весь путь жив (это заодно и smoke-тест);
- контроль латентности и стоимости на стабильном профиле.

```python
import numpy as np
from dataclasses import dataclass, field


@dataclass
class GenerationMonitor:
    """Онлайн-мониторинг свойств генерации со скользящим окном и сравнением
    с эталонным периодом.

    Смысл: у нас нет разметки, поэтому мы следим не за качеством напрямую,
    а за СВОЙСТВАМИ распределения ответов. Их сдвиг — ранний сигнал.
    """
    window: int = 2000
    lengths: list[int] = field(default_factory=list)
    refusals: list[int] = field(default_factory=list)
    schema_fail: list[int] = field(default_factory=list)
    no_citation: list[int] = field(default_factory=list)
    baseline: dict[str, float] = field(default_factory=dict)

    REFUSAL_MARKERS = ("не могу", "не знаю", "нет информации", "недостаточно данных")

    def observe(self, answer: str, *, schema_ok: bool, has_citation: bool) -> None:
        low = answer.lower()
        self.lengths.append(len(answer))
        self.refusals.append(int(any(m in low for m in self.REFUSAL_MARKERS)))
        self.schema_fail.append(int(not schema_ok))
        self.no_citation.append(int(not has_citation))
        for arr in (self.lengths, self.refusals, self.schema_fail, self.no_citation):
            if len(arr) > self.window:
                del arr[0]

    def snapshot(self) -> dict[str, float]:
        return {
            "mean_length": float(np.mean(self.lengths)) if self.lengths else 0.0,
            "refusal_rate": float(np.mean(self.refusals)) if self.refusals else 0.0,
            "schema_fail_rate": float(np.mean(self.schema_fail)) if self.schema_fail else 0.0,
            "no_citation_rate": float(np.mean(self.no_citation)) if self.no_citation else 0.0,
        }

    def freeze_baseline(self) -> None:
        """Зафиксировать эталон — делается после стабилизации новой версии."""
        self.baseline = self.snapshot()

    def alerts(self, rel_tol: float = 0.25, abs_tol: float = 0.03) -> list[str]:
        """Двойной критерий: относительное И абсолютное отклонение.

        Только относительный порог даёт ложные тревоги на редких событиях
        (рост доли отказов с 0.2% до 0.3% — это +50%, но не новость).
        """
        if not self.baseline:
            return []
        out = []
        for k, now in self.snapshot().items():
            base = self.baseline[k]
            if base == 0:
                continue
            rel = abs(now - base) / base
            if rel > rel_tol and abs(now - base) > abs_tol * max(1.0, base):
                out.append(f"{k}: {base:.4f} -> {now:.4f} ({rel:+.0%})")
        return out
```

Двойной критерий в `alerts` — не мелочь. Мониторинг, который кричит на каждое относительное
отклонение редкого события, отключают через неделю, и он перестаёт защищать.

> 💬 **На собеседовании.** Спросят: «Как мониторить качество LLM в проде, если разметки нет?»
> Хороший ответ — по слоям: (1) техника — латентность, ошибки, стоимость, ретраи; (2) дрифт входа —
> длина, язык, распределение интентов, расстояние эмбеддингов до исторических кластеров;
> (3) свойства выхода — длина ответа, доля отказов, доля нарушений схемы, доля ответов без цитат,
> срабатывания фильтров; (4) сэмплированная оценка судьёй на 0.5–2% трафика плюс маленькая
> человеческая выборка. И отдельно — канареечный набор фиксированных запросов, прогоняемый по
> расписанию: он даёт сравнимый во времени ряд и ловит молчаливое обновление модели у провайдера.
> Плюс прокси-сигналы поведения: регенерации, эскалации, правки ответа перед отправкой.
> Плохой ответ: «будем смотреть на лайки» — их ставят 1–3% пользователей, и очень смещённо.

## 12. Компромиссы: как выбирать

Свести всю главу к одной таблице решений не получится, но три опорных выбора можно зафиксировать.

**Где живёт модель.**

| Условие | Решение |
|---|---|
| Объём ниже точки безубыточности, данные можно отдавать наружу | API |
| Требование не выпускать данные из периметра | своя, независимо от экономики |
| Большой стабильный объём на узкой задаче | своя (дистиллированная) + API на хвосте |
| Нужен максимум качества на редких сложных запросах | API топовой модели, роутинг только туда |
| Резкие пики нагрузки, низкая средняя утилизация | API (эластичность) или гибрид |

**Сколько тратить на снижение стоимости.** Порядок работ по отношению «эффект / трудозатраты»:
префиксное кэширование → сокращение контекста → точный кэш → роутинг → батч-режим →
семантический кэш → дистилляция. Первые три обычно дают в сумме 2–4× за дни работы. Дистилляция
даёт больше, но стоит недели — беритесь за неё, только пройдя предыдущие.

**Латентность против качества.** Каждый элемент, повышающий качество (реранкер, больше документов,
самопроверка, рассуждение в несколько шагов, каскад), увеличивает латентность. Решение принимается
не «в среднем», а **по маршрутам**: интерактивный чат — быстрый путь; отчёт по расписанию — полный
путь с проверками. Один и тот же продукт может иметь оба.

**Сколько вычислений тратить на запрос.** Отдельная ось, появившаяся в 2024–2026: качество можно
купить не только моделью, но и бюджетом рассуждения. Правило простое и вытекает из [§8](#8-экономика-рассуждающих-моделей-когда-длина-ответа--случайная-величина):
средним расходом управляет маршрутизация (какая доля трафика вообще думает), хвостом — потолок
бюджета на запрос. Оптимизировать среднее потолком бесполезно, а хвост маршрутизацией — поздно.

## 13. Подводные камни

**Кэш не даёт экономии, а метрики говорят, что он включён.**
Симптом: доля токенов, прочитанных из кэша, стабильно околонулевая.
Причина: тихий инвалидатор в начале промпта — дата, идентификатор запроса, недетерминированная
сериализация JSON, динамический порядок документов или инструментов.
Что делать: логировать счётчики кэша с первого дня; при нуле — побайтово сравнить два
последовательных промпта и найти первое расхождение.

**Стоимость считается за вызов, а не за задачу.**
Симптом: план по стоимости сходился, факт вдвое выше.
Причина: ретраи, перегенерации, шаги агента и вызовы вспомогательных моделей не учтены.
Что делать: единица учёта — успешно завершённая пользовательская задача; в неё входят все вызовы,
включая неудачные.

**Думающая ветка задушила быструю.**
Симптом: включили режим рассуждения на 10% трафика — вырос p99 у **всех** запросов, включая
те, что идут мимо рассуждения.
Причина: длинные генерации удерживают слоты KV-кэша минутами; свободной памяти под новые запросы
не остаётся, батч мельчает, короткие запросы встают в очередь за длинными.
Что делать: разводить ветки по разным пулам или очередям с приоритетом; жёсткий лимит на число
одновременных длинных генераций; мониторить долю вытесненных запросов (preemption rate) и долю
трафика в думающей ветке как отдельные SLI.

**SLA написан на смешанный трафик.**
Симптом: p99 нарушен, при этом ни один компонент системы не менялся.
Причина: общий перцентиль по смеси двух распределений зависит от их пропорции. Роутер стал чаще
отправлять запросы в думающую ветку — и обещание перестало выполняться само по себе.
Что делать: формулировать SLO по веткам с явным условием на долю («p95 не выше 4 секунд при доле
думающих запросов не выше 12%») и ставить алерт на саму долю.

**Роутер обучен на исторических данных и не переучивается.**
Симптом: доля эскалаций поползла вверх, экономия исчезла.
Причина: распределение запросов изменилось, роутер устарел.
Что делать: мониторить долю запросов, ушедших вниз, и долю ошибок среди них; переобучать по
расписанию или по триггеру дрифта.

**Семантический кэш отдаёт неверный ответ.**
Симптом: пользователь спросил про заказ 12346, получил ответ про 12345.
Причина: близость эмбеддингов не равна эквивалентности запроса.
Что делать: не кэшировать запросы с цифрами и отрицаниями; разделять кэш по интентам; подбирать
порог по размеченной выборке; сэмплировать попадания на проверку.

**Ретраи без общего бюджета времени.**
Симптом: p99 латентности — минуты, пользователи ушли, а вы всё ещё платите за токены.
Причина: три попытки по 30 секунд укладываются в 90, что вдвое больше SLA.
Что делать: жёсткий общий бюджет; таймаут одного вызова = бюджет / число попыток; полный джиттер;
уважение к `retry-after`.

**Алиас модели вместо точной версии.**
Симптом: «ничего не меняли», а качество упало и ответы стали длиннее.
Причина: провайдер переназначил алиас на новую версию.
Что делать: пин на точную версию; обновление — отдельная выкатка с прогоном эвала и канарейкой;
версия модели пишется в каждый лог.

**Фильтры выхода убили стриминг.**
Симптом: перед релизом добавили проверку всего ответа, воспринимаемая латентность выросла в 5 раз.
Причина: проверка требует полного текста, стримить нечего.
Что делать: инкрементальная проверка по предложениям; стриминг с буфером в несколько токенов;
отзыв показанного текста при нарушении; сознательный отказ от стриминга на высокорисковых маршрутах.

**Мониторинг без эталонного периода.**
Симптом: метрики есть, но непонятно, «плохо» это или нормально.
Причина: нет зафиксированного baseline.
Что делать: фиксировать эталон после стабилизации каждой новой версии; алертить по двойному
критерию (относительное **и** абсолютное отклонение), иначе редкие события генерируют шум.

**Один провайдер без фолбэка.**
Симптом: инцидент у провайдера — полный простой продукта.
Причина: отсутствие резервного пути.
Что делать: второй провайдер или своя резервная модель; заранее написанная и **протестированная**
лестница деградации; регулярные учения с отключением основного пути.

## 14. Проверь себя

<details>
<summary><b>🎯 Вопрос.</b> Посчитайте стоимость запроса и назовите, где в ней главные деньги.</summary>

**Короткий ответ.** $c = (T_{\text{in}} p_{\text{in}} + T_{\text{out}} p_{\text{out}})/10^6$.
В RAG-сценариях главные деньги обычно во **входе**, потому что $T_{\text{in}} \gg T_{\text{out}}$,
даже при том что выходной токен дороже в 4–5 раз.

**Развёрнуто.** Пример: 4000 входных и 400 выходных токенов при ценах \$5/\$25 за миллион дают
$0.02 + 0.01 = 0.03$ за запрос — две трети приходятся на контекст. Отсюда порядок оптимизаций:
сначала сокращение контекста и префиксное кэширование, потом уже длина ответа. Кроме токенов
основной модели в счёт входят эмбеддинги, реранкер, классификаторы фильтров, судья для мониторинга
и — самое недооценённое — ретраи и лишние шаги агента. Поэтому считать надо стоимость **успешно
завершённой задачи**, а не одного вызова: это единственная величина, сопоставимая с выручкой.

**Чего ждёт интервьюер:** что вы считаете формулой и знаете структуру счёта, а не «примерно
несколько центов».

**Провал:** назвать только цену за вызов модели и забыть про ретраи, реранкер и эмбеддинги.
</details>

<details>
<summary><b>🧠 Вопрос.</b> Выведите точку безубыточности «своя модель против API».</summary>

**Короткий ответ.** $n^* = C_{\text{fix}} / (c_{\text{api}} - c_{\text{own}})$, где
$c_{\text{own}} = T_{\text{out}} c_{\text{gpu}} / (3600\, s\, u)$ — переменная стоимость запроса
на своей модели.

**Развёрнуто.** API даёт чисто линейную стоимость: $C_{\text{api}}(n) = n\, c_{\text{api}}$.
Своя модель — линейная плюс постоянная: $C_{\text{own}}(n) = n\, c_{\text{own}} + C_{\text{fix}}$,
где переменная часть выводится из требуемого времени ускорителя: $n T_{\text{out}}$ выходных токенов
делим на пропускную способность $s$ с поправкой на утилизацию $u$, переводим в часы и умножаем на
цену часа. Приравнивая, получаем точку безубыточности. Ключевые оговорки: (1) в $C_{\text{fix}}$
входят не только серверы, но и доля времени инженеров, резервная ёмкость, мониторинг,
амортизированные разовые работы — реалистично 8–15 тысяч долларов в месяц для небольшой команды;
(2) $u$ критична — при неравномерном трафике 0.3–0.5, и падение утилизации вдвое почти вдвое
увеличивает $c_{\text{own}}$; (3) $s$ надо **измерить** на своём профиле, а не взять из
маркетинговых материалов; (4) сравнение честно только **при равном качестве на вашей задаче** —
сравнивать свою 8B-модель с ценой топовой API-модели некорректно.

**Чего ждёт интервьюер:** вывод, а не заученный результат; и особенно — полный список того, что
входит в $C_{\text{fix}}$, потому что именно на нём ошибаются.

**Провал:** «своя модель дешевле, потому что не платим за токены».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Чем префиксное кэширование отличается от точного и от семантического?</summary>

**Короткий ответ.** Точный кэш хранит **ответ** по хешу входа; префиксный — **KV-кэш вычисленного
префикса промпта**, экономя prefill; семантический ищет **похожий** запрос по эмбеддингу и потому
может ошибаться.

**Развёрнуто.** Точный: попадание отдаёт готовый ответ, модель не вызывается; экономия равна
hit rate; риска для качества нет; типичный hit rate 10–30%. Префиксный: работает на каждом запросе
с общим началом промпта — системный промпт, инструменты, стабильные документы; экономит стоимость
и TTFT; чтение из кэша стоит порядка 0.1× цены входа, запись — 1.25×, поэтому уже со второго
обращения к префиксу он выгоден. Критично собирать промпт от стабильного к волатильному, потому что
кэш — это совпадение по префиксу, и байт в начале инвалидирует всё после. Семантический: ловит
перефразировки, но близость эмбеддингов не равна эквивалентности — «как отменить» и «как не
отменить», «заказ 12345» и «заказ 12346». Поэтому нужен запрет на запросы с цифрами и отрицаниями,
разделение по интентам, подбор порога по размеченной выборке и сэмплирование попаданий на проверку.
Механизмы складываются: точный → семантический → префиксный на том, что дошло до модели.

**Чего ждёт интервьюер:** различения трёх механизмов и понимания, что только семантический вносит
ошибки.

**Провал:** считать это тремя названиями одного и того же.
</details>

<details>
<summary><b>🎯 Вопрос.</b> Кэш включили, а экономии нет. Что проверять?</summary>

**Короткий ответ.** Счётчики прочитанных из кэша токенов. Если ноль — ищите «тихий инвалидатор»
в начале промпта.

**Развёрнуто.** Типичные виновники, в порядке частоты: текущая дата или время в системном промпте;
идентификатор запроса, UUID или имя пользователя в начале; недетерминированная сериализация
(`json.dumps` без `sort_keys`, итерация по множеству); документы, отсортированные по скору
релевантности вместо стабильного порядка по id — при том же наборе документов порядок меняется и
префикс ломается; динамический набор инструментов, различающийся между пользователями; смена
модели (кэш привязан к модели). Диагностика: взять два последовательных запроса, у которых префикс
должен совпадать, и сравнить сериализованные промпты побайтово — первое расхождение и есть причина.
Отдельно: короткий префикс может вообще не кэшироваться — у провайдеров есть минимальная длина
кэшируемого блока. И проверьте TTL: при редком трафике запись успевает истечь до следующего
обращения, и вы платите только за записи.

**Чего ждёт интервьюер:** что вы знаете про инвариант «совпадение по префиксу» и умеете
диагностировать по счётчикам, а не гадать.

**Провал:** «наверное, провайдер не поддерживает».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Как устроен каскадный роутинг и когда он невыгоден?</summary>

**Короткий ответ.** Сначала дешёвая модель, при непрохождении проверки — дорогая. Ожидаемая
стоимость $\mathbb{E}[c] = c_{\text{small}} + p_{\text{esc}} c_{\text{large}}$; выгоден при
$p_{\text{esc}} < 1 - c_{\text{small}}/c_{\text{large}}$. Невыгоден, когда SLA по латентности жёсткий.

**Развёрнуто.** При отношении цен 1:5 каскад окупается по деньгам даже при 80% эскалаций. Но
формула не учитывает главное: **эскалированный запрос проходит модель дважды**, и его латентность
удваивается. Если p95 бюджета и так на пределе, каскад его сломает. Второй ограничитель — качество
верификатора: чем решаем, что дешёвого ответа достаточно? По надёжности: детерминированная проверка
(валидность схемы, прохождение тестов, совпадение чисел с источником) → уверенность модели по
логарифмическим вероятностям (работает на коротких ответах) → отдельный классификатор-верификатор →
самопроверка моделью (работает хуже всего, модели плохо калиброваны). Альтернатива каскаду —
априорный роутер, который выбирает модель до генерации по признакам запроса: он не удваивает
латентность, но требует, чтобы сложность была предсказуема, и его порог надо подбирать
минимизацией ожидаемых потерь с явной ценой ошибки, а не ставить 0.5.

**Чего ждёт интервьюер:** что вы видите латентностный минус каскада и понимаете роль верификатора.

**Провал:** «всегда сначала дешёвая модель, это всегда выгодно».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Почему стриминг важен, если он не сокращает общее время?</summary>

**Короткий ответ.** Он меняет воспринимаемую задержку: вместо девяти секунд пустого экрана —
полторы секунды до первого символа. Оптимизировать поэтому надо TTFT, а не суммарное время.

**Развёрнуто.** $L_{\text{total}} = L_{\text{pre}} + \text{TTFT} + T_{\text{out}}\cdot\text{TPOT} + L_{\text{post}}$.
Стриминг скрывает третье слагаемое — самое большое, — но не скрывает первое и четвёртое.
Следствия: реранкер и фильтры входа становятся главными кандидатами на оптимизацию; фильтры
выхода, требующие полного текста, **конфликтуют** со стримингом, и приходится выбирать —
инкрементальная проверка по предложениям, буфер в несколько токенов, возможность отозвать
показанное, или сознательный отказ от стриминга на высокорисковых маршрутах. Ещё приём: первый
токен не обязан быть от модели — статусное сообщение во время retrieval психологически работает как
снижение TTFT. И отдельно про хвосты: смотреть надо p95/p99, а не среднее; главные источники
хвостов — очередь провайдера, длинные ответы, ретраи и число шагов агента.

**Чего ждёт интервьюер:** различения фактической и воспринимаемой латентности и знания конфликта
со стримингом на выходных фильтрах.

**Провал:** «стриминг ускоряет генерацию».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Сколько стоит запрос к модели с режимом рассуждения и как это заложить в SLA?</summary>

**Короткий ответ.** Это не число, а распределение: $T_{\text{out}} = T_{\text{reason}} + T_{\text{answer}}$,
и первая часть — выход модели, а не ваш параметр. Считать надо три величины: среднее (по нему
платите), p99 (по нему считаете ёмкость и латентность) и долю трафика в думающей ветке.
SLA формулируется по веткам с явным условием на эту долю.

**Развёрнуто.** Токены рассуждения тарифицируются по цене выходных, но в тексте ответа их нет —
поэтому считать надо по полю `usage`, а не по `len(text)`. Длина рассуждения приближённо
логнормальна: по медиане и $p_{99}$ восстанавливаются $\mu = \ln(\text{median})$ и
$\sigma = \ln(p_{99}/\text{median}) / z_{0.99}$, а среднее равно $\exp(\mu + \sigma^2/2)$
и потому заметно больше медианы — при медиане 800 и $p_{99}$ в 12 000 токенов ровно вдвое.
На профиле «1500 входных, 300 токенов ответа» это даёт примерно 3.6× к стоимости запроса
без рассуждения, причём верхний процент трафика съедает около 9% счёта. Дальше два разных рычага:
маршрутизация управляет средним (какая доля трафика вообще думает), потолок бюджета — хвостом
(потолок в 4096 токенов роняет p99 стоимости в 2.7 раза, а среднее всего на 14%). По железу:
длинные генерации держат KV-кэш, ёмкость по числу одновременных запросов падает в разы,
и думающая ветка душит быструю, если они делят пул. Поэтому в SLA — раздельные SLO по веткам,
доля думающих запросов как отдельный SLI с алертом, обязательный потолок бюджета (он делает
худший случай детерминированным) и таймаут, посчитанный **от** потолка, а не наоборот.

**Чего ждёт интервьюер:** что вы мыслите распределением, а не средним, и знаете, какой рычаг
на что действует.

**Провал:** умножить цену за миллион выходных токенов на длину видимого ответа.
</details>

<details>
<summary><b>🧠 Вопрос.</b> Провайдер отдаёт 429. Что делает ваш сервис?</summary>

**Короткий ответ.** Экспоненциальная задержка с полным джиттером, уважение к `retry-after`, жёсткий
общий бюджет времени, и при устойчивой перегрузке — заранее описанная лестница деградации, а не
бесконечные ретраи.

**Развёрнуто.** Задержка $d_k = \min(d_{\max}, d_0 2^k)\cdot U(0,1)$: экспонента разводит попытки,
потолок не даёт уйти в минуты, множитель $U(0,1)$ размазывает клиентов и предотвращает «громовое
стадо». Заголовок `retry-after` от провайдера приоритетнее формулы. Не ретраятся 400, 401, 403,
404 — повтор не изменит результат. Критично: **общий бюджет времени** на запрос, иначе три попытки
по 30 секунд дадут 90 и выйдут за SLA, а вы заплатите за токены ответа, который никому не нужен;
таймаут одного вызова = бюджет / число попыток. При устойчивой перегрузке ретраи только усугубляют
ситуацию — нужен размыкатель цепи и лестница деградации: фолбэк на резервного провайдера → роутинг
всего трафика на модель классом ниже → только кэшированные ответы, остальное в очередь → шаблонные
ответы с предложением оператора → честное «недоступно» с сохранением запроса. Переключение —
автоматическое по метрикам и обратимое. Плюс приоритизация: интерактивный трафик платящего
пользователя важнее фоновой переиндексации, и один арендатор не должен съедать общую квоту.

**Чего ждёт интервьюер:** и формулу с джиттером, и понимание, что ретрай не решает устойчивую
перегрузку.

**Провал:** «повторим три раза с задержкой в секунду».
</details>

<details>
<summary><b>🎯 Вопрос.</b> Как мониторить качество генерации в проде без разметки?</summary>

**Короткий ответ.** Четыре слоя: техника; дрифт входа; свойства выхода; сэмплированная оценка
судьёй. Плюс канареечный набор фиксированных запросов по расписанию.

**Развёрнуто.** Свойства выхода считаются на каждом ответе почти бесплатно и очень информативны:
средняя длина ответа, доля отказов, доля нарушений JSON-схемы, доля ответов без цитат, доля
срабатываний фильтров, число шагов агента. Их сдвиг — ранний сигнал: рост доли отказов обычно
означает поломку retrieval, а не осторожность модели; рост длины — смену версии модели.
Дрифт входа ловится длиной запроса, языком, распределением интентов, расстоянием эмбеддинга до
исторических кластеров. Сэмплированная оценка: 0.5–2% трафика через провалидированного судью с
зафиксированной версией и небольшая человеческая выборка. Канареечный набор из 50–200 фиксированных
запросов, прогоняемый ежечасно через полный продовый путь, даёт сравнимый во времени ряд — любое
изменение вызвано системой, а не составом трафика; он же немедленно ловит молчаливое обновление
модели у провайдера. Алерты — по двойному критерию (относительное и абсолютное отклонение от
зафиксированного baseline), иначе редкие события генерируют шум и мониторинг отключат.

**Чего ждёт интервьюер:** понимания, что прямой метрики нет, и умения строить систему из
косвенных сигналов.

**Провал:** «смотрим на лайки» — их ставят единицы процентов пользователей, очень смещённо.
</details>

<details>
<summary><b>🎯 Вопрос.</b> Что нужно версионировать в LLM-сервисе и почему опасны алиасы моделей?</summary>

**Короткий ответ.** Версию модели (точную, не алиас), версию промпта, параметры декодинга, схему
инструментов, конфигурацию retrieval, набор фильтров. Алиас может быть переназначен провайдером,
и система изменится без вашего участия.

**Развёрнуто.** Критерий достаточности: по логам должно однозначно восстанавливаться, какая
комбинация породила данный ответ. Без этого нельзя сопоставить изменение метрики с причиной.
Промпты должны жить в репозитории как код: ревью, прогон регрессионного эвала перед мержем, тег
версии в каждом логе, откат через откат коммита. Алиасы вида «последняя версия» — источник
классического инцидента «ничего не меняли, а качество упало»: провайдер обновил модель, ответы
стали длиннее, доля эскалаций выросла, и три недели никто не понимает почему. Правильно:
пин на точную версию, а обновление — отдельная выкатка со своим эвалом, shadow-режимом и
канарейкой. Shadow для LLM особенно ценен: он даёт пары ответов старой и новой версии на реальном
трафике, по которым можно прогнать парного судью до того, как хоть один пользователь увидит
новую версию.

**Чего ждёт интервьюер:** что вы относитесь к промпту и версии модели как к артефактам релиза.

**Провал:** «промпт лежит в админке, продакт правит его сам».
</details>

<details>
<summary><b>🧠 Вопрос.</b> Когда имеет смысл дистиллировать в свою маленькую модель?</summary>

**Короткий ответ.** Когда одновременно: задача узкая и стабильная, объём выше точки безубыточности,
есть данные и есть измеримое качество. Без любого из четырёх — не браться.

**Развёрнуто.** Процедура: собрать входы стратифицированно по типам запросов, прогнать через
учителя, **отфильтровать** выходы детерминированными проверками и судьёй (это шаг, который чаще
всего пропускают, — учить на ошибках учителя значит закрепить их навсегда; отсев обычно 15–30%),
дообучить маленькую модель (обычно LoRA), померить на эвал-наборе **по срезам**, выкатывать через
shadow и канарейку, оставить эскалацию на учителя для неуверенных случаев. Типичный результат:
студент не хуже учителя на 90% массового потока и заметно хуже на редком сложном хвосте — что и
есть обоснование гибридной схемы. Экономика: доминируют не вычисления обучения (для LoRA на 8B это
часы одного ускорителя), а сбор данных и разметка эвал-набора — то есть человеко-недели.
Порядок работ: браться за дистилляцию стоит, только пройдя более дешёвые рычаги — префиксный кэш,
сокращение контекста, точный кэш, роутинг, батч-режим.

**Чего ждёт интервьюер:** понимания, что фильтрация выходов учителя обязательна и что дистилляция —
последний по очереди рычаг, а не первый.

**Провал:** «соберём 1000 примеров и дообучим» — этого мало, и без фильтрации выйдет копия
недостатков учителя.
</details>

<details>
<summary><b>🎯 Вопрос.</b> Как вы удешевите LLM-фичу в 10 раз?</summary>

**Короткий ответ.** Сначала померить, где деньги. Затем по порядку: сокращение контекста,
префиксное кэширование, точный кэш, роутинг, батч-режим, и только потом дистилляция. Каждый шаг —
с проверкой на эвал-наборе.

**Развёрнуто.** Измерение первым: в RAG-сценариях обычно две трети счёта — вход, а не выход,
поэтому интуитивное «сделаем ответы короче» даёт мало. Дальше: (1) контекст — четыре документа
после хорошего реранкера вместо десяти, короче системный промпт, суммаризация истории вместо полной;
до 2–3×, но обязательно замерять recall; (2) префиксный кэш — до 70% стоимости входа при высоком
hit rate, при этом надо собирать промпт от стабильного к волатильному; (3) точный кэш — экономия
равна hit rate, в саппорте 10–30%; (4) роутинг простых запросов вниз с порогом, подобранным
минимизацией ожидаемых потерь с явной ценой ошибки; (5) батч-режим для всего неинтерактивного —
скидка порядка 50%; (6) дистилляция, если объём это оправдывает. Умножение эффектов даёт 10× вполне
достижимо. Обязательная оговорка: после каждого шага — прогон регрессионного эвала, иначе это не
оптимизация, а деградация с красивым отчётом.

**Чего ждёт интервьюер:** порядка действий по отношению эффекта к трудозатратам и привычки
подтверждать качество после каждой оптимизации.

**Провал:** «возьмём модель подешевле» как единственная мера.
</details>

## 15. Практика

**Задача 1. Модель стоимости (1.5 часа).**
Напишите калькулятор, который принимает профиль нагрузки (распределение $T_{\text{in}}$,
$T_{\text{out}}$, RPS с суточным профилем, долю ретраев) и выдаёт месячную стоимость для трёх
сценариев: чистый API, API + префиксный кэш при заданном hit rate, гибрид с роутингом.
*Критерий: вы можете ответить на вопрос «при каком hit rate кэша роутинг перестаёт окупаться» и
показать это графиком.*

**Задача 2. Точка безубыточности (1 час).**
Постройте график $n^*$ как функции утилизации $u \in [0.1, 0.9]$ при фиксированных остальных
параметрах, и второй график — как функции $C_{\text{fix}}$.
*Критерий: вы можете назвать, при какой утилизации своя модель перестаёт окупаться при вашем
объёме, и объяснить, почему неравномерный трафик — главный аргумент против собственного хостинга.*

**Задача 3. Диагностика префиксного кэша (2 часа).**
Соберите промпт с намеренным «тихим инвалидатором» (текущее время в системном промпте) и прогоните
100 одинаковых запросов, логируя счётчики кэша. Затем перестройте сборку по правилу «от стабильного
к волатильному» и повторите.
*Критерий: у вас есть два ряда счётчиков — нулевой и ненулевой, и вы можете посчитать фактическую
экономию по формуле $m = (1-f) + f[0.1h + 1.25(1-h)]$ и сверить её с наблюдаемой.*

**Задача 4. Роутер с экономическим порогом (2.5 часа).**
Возьмите 2000 исторических запросов, прогоните через дешёвую и дорогую модель, разметьте судьёй,
где хватило дешёвой. Обучите классификатор и подберите порог функцией из [§5.2](#52-схема-2-априорный-роутер) для трёх значений
`quality_penalty`.
*Критерий: у вас есть таблица «штраф за качество → порог → доля дешёвых → стоимость на запрос», и
вы можете объяснить продакту, какой штраф соответствует его представлению о цене плохого ответа.*

**Задача 5. Ретраи и деградация (2 часа).**
Реализуйте `call_with_retry` из [§9.2](#92-ретраи-экспоненциальная-задержка-с-джиттером) и напишите тесты: 429 с `retry-after`, серия 5xx, ошибка 400
(не должна ретраиться), исчерпание бюджета. Затем добавьте размыкатель цепи и переключение на
резервный путь.
*Критерий: тест с исчерпанием бюджета завершается за заданное время, а не за сумму таймаутов; при
серии ошибок размыкатель перестаёт стучаться в провайдера.*

**Задача 6. Канареечный набор (1.5 часа).**
Соберите 50 фиксированных запросов и настройте их ежечасный прогон через полный путь с записью
метрик из [§11.3](#113-канареечный-набор-в-проде). Внесите изменение в промпт и убедитесь, что мониторинг это увидел.
*Критерий: изменение обнаружено в течение одного цикла, и по алерту понятно, какое именно свойство
выхода сдвинулось.*

**Задача 7. Бюджет рассуждения (1.5 часа).**
Снимите с прода (или сгенерируйте прогоном на 500 запросах) распределение числа reasoning-токенов
по полю `usage`. Восстановите параметры логнормали по медиане и $p_{99}$, сравните теоретическое
$\exp(\mu + \sigma^2/2)$ с выборочным средним. Затем постройте таблицу «потолок бюджета →
доля обрезанных запросов → средняя цена → p99 цены → p99 латентности» для потолков
1024/2048/4096/8192.
*Критерий: у вас есть рабочий потолок, выбранный по заданному p99 латентности, и число —
какую долю запросов он обрезает. Проверьте отдельно на 50 обрезанных запросах, насколько просело
качество: если не просело вовсе, потолок можно опускать дальше.*

  используют дистилляцию по последовательностям.
- [Документация Anthropic по кэшированию промптов](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) —
  практические детали префиксного кэша: минимальная длина, TTL, точки останова, счётчики в ответе.
  Механика у разных провайдеров близка, читать полезно в любом случае.
- [Документация vLLM](https://docs.vllm.ai/) — разделы про непрерывный батчинг, автоматическое
  префиксное кэширование и метрики; практический ориентир при замере $s$ и $u$.
- [Amazon Builders' Library: Timeouts, retries and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) —
  каноническое изложение стратегий ретраев и джиттера; читать перед тем, как писать свой retry-слой.
- [GPTCache](https://github.com/zilliztech/GPTCache) — открытая реализация семантического кэша;
  полезно посмотреть на устройство и на то, какие предохранители там предусмотрены (и каких нет).
